Обзор

Этот раздел предоставляет информацию о настройке брандмауэра для flowtables.

set firewall flowtable …

Чтобы узнать о общем потоке трафика в брандмауэрах VyOS, см. Брандмауэр.

- set firewall
    * flowtable
         - custom_flow_table
            + ...

Flowtables позволяют определить быстрый путь через datapath flowtable. Flowtables поддерживают уровни 3 (IPv4 и IPv6) и уровень 4 (TCP и UDP) протоколы.

После того как первый пакет успешно проходит путь IP-пересылки (черный путь), вы можете перенаправить последующие пакеты на flowtable через ваш набор правил. Вы указываете, когда добавить поток в flowtable во время фильтрации прямого направления (красный круг номер 6).

Когда пакет находит совпадающую запись в flowtable (hit flowtable), система передает его на выходной netdevice. Это означает, что пакеты обходят классический путь IP-пересылки и используют Быстрый путь (оранжевые круги). В результате вы не видите эти пакеты из любого хука Netfilter после входа. Если в flowtable нет совпадающей записи (miss flowtable), пакет проходит классический путь IP-пересылки.

Примечание

Справочник по flowtable: https://docs.kernel.org/networking/nf_flowtable.html

Настройка flowtable

Для использования flowtables вам нужно настроить следующее:

  • Создайте flowtable, который включает интерфейсы, которые будут использоваться flowtable.

  • Создайте правило брандмауэра. Установите действие в offload и используйте желаемый flowtable для offload-target.

Создание flow table:

set firewall flowtable <flow_table_name> interface <iface> Specify interfaces to use in the flowtable.
set firewall flowtable <flow_table_name> description <text>

Укажите описание для flow table.

set firewall flowtable <flow_table_name> offload <hardware | software>

Укажите тип offload, который использует flowtable: hardware или software. По умолчанию используется software offload.

Примечание

Hardware offload: Убедитесь, что ваш сетевой контроллер (NIC) поддерживает аппаратное отключение и что у вас установлены необходимые драйверы до включения этого варианта.

Создание правил для использования flow tables:

set firewall [ipv4 | ipv6] forward filter rule <1-999999> action offload

Создайте правило брандмауэра в цепочке forward с действием, установленным на offload.

set firewall [ipv4 | ipv6] forward filter rule <1-999999> offload-target <flowtable>

Создайте правило брандмауэра в цепочке forward и укажите, какой flowtable использовать. Действует только если действие — offload.

Выбор интерфейса

Важно

Всегда настраивайте flowtable с интерфейсом, который наблюдает VyOS на hook forward — это не обязательно физический интерфейс. Когда трафик приходит или отправляется через логический интерфейс, VyOS отслеживает этот логический интерфейс, а не базовое физическое устройство. Регистрация неправильного интерфейса в flowtable приводит к тому, что каждый поиск потока не удается, возвращаясь к классическому пути пересылки и разрушая цель быстрого отключения.

Пример конфигурации

Рассмотрим следующее в этом наборе:

  • В этом примере используются два интерфейса в flowtables: eth0 и eth1.

  • Пример предоставляет минимальный набор правил брандмауэра с правилами фильтрации и правилами использования возможностей отключения flowtable.

Первый пакет оценивается путем брандмауэра, поэтому желаемое соединение должно быть явно принято. То же самое должно происходить для трафика в обратном порядке. В большинстве случаев политики состояния используются для принятия соединения в обратном направлении.

В следующем примере принимается только трафик, приходящий с интерфейса eth0, протокол TCP и порт назначения 1122. Все остальные трафик к роутеру отбрасываются.

Команды

set firewall flowtable FT01 interface 'eth0'
set firewall flowtable FT01 interface 'eth1'
set firewall ipv4 forward filter default-action 'drop'
set firewall ipv4 forward filter rule 10 action 'offload'
set firewall ipv4 forward filter rule 10 offload-target 'FT01'
set firewall ipv4 forward filter rule 10 state 'established'
set firewall ipv4 forward filter rule 20 action 'accept'
set firewall ipv4 forward filter rule 20 state 'established'
set firewall ipv4 forward filter rule 20 state 'related'
set firewall ipv4 forward filter rule 110 action 'accept'
set firewall ipv4 forward filter rule 110 destination address '192.0.2.100'
set firewall ipv4 forward filter rule 110 destination port '1122'
set firewall ipv4 forward filter rule 110 inbound-interface name 'eth0'
set firewall ipv4 forward filter rule 110 protocol 'tcp'

Объяснение

Вот что происходит для желаемого соединения:

  1. Пакет приходит на eth0 с адресом назначения 192.0.2.100, протоколом TCP и портом назначения 1122. Предположим, что этот адрес достижим через интерфейс eth1.

  2. Для этого первого пакета состояние соединения — новое. Ни правило 10 ни правило 20 не применяются.

  3. Правило 110 совпадает, поэтому соединение принимается.

  4. Когда сервер 192.0.2.100 отвечает, состояние соединения становится установленным, и правило 20 принимает ответ.

  5. Роутер получает второй пакет для этого соединения. Поскольку состояние соединения — установленное, правило 10 совпадает и добавляет новую запись в flowtable FT01 для этого соединения.

  6. Последующие пакеты пропускают традиционный путь и используют Быстрый путь для отключения.

Настройка flowtable на логических и подинтерфейсах

Настройте flowtable с именем интерфейса, которое вы использовали в конфигурации VyOS. Когда задействованы VLAN, bonds или bridges, это логический интерфейс (bond0, br0, eth0.10) — не физический порт.

Например:

  • Если bond0 настроен, VyOS видит bond0 — не eth0 или eth1

  • Если br0 настроен, VyOS видит br0 — не его членские интерфейсы

  • Flowtable должен ссылаться на то же имя интерфейса, которое видит VyOS

Два формата принимаются, но рекомендуется регистрировать родителя:

  • Регистрация bond1 отключает родительский интерфейс и все его подинтерфейсы VLAN (bond1.10, bond1.20, и т.д.) — ядро автоматически обнаруживает их, анализируя заголовки L2 (Linux 5.13+).

  • Регистрация bond1.10 напрямую отключает только трафик VLAN 10. Однако подинтерфейс должен существовать во время коммита; если он еще не существует во время загрузки набора правил, конфигурация может не сработать.

# Отключение bond1 и всех подинтерфейсов (bond1.10, bond1.20, ...)
set firewall flowtable FT01 interface 'bond1'

# Отключение только VLAN 10: зарегистрируйте подинтерфейс напрямую
set firewall flowtable FT01 interface 'bond1.10'

Пример: Смешанная регистрация родительского и подинтерфейса

Рассмотрим настройку, где:

  • Трафик входит на bond1.10 (VLAN 10)

  • Трафик исходит на bond2.20 (VLAN 20)

set firewall flowtable FT01 interface 'bond1'
set firewall flowtable FT01 interface 'bond2.20'
set firewall ipv4 forward filter default-action 'drop'
set firewall ipv4 forward filter rule 10 action 'offload'
set firewall ipv4 forward filter rule 10 offload-target 'FT01'
set firewall ipv4 forward filter rule 10 state 'established'
set firewall ipv4 forward filter rule 20 action 'accept'
set firewall ipv4 forward filter rule 20 state 'established'
set firewall ipv4 forward filter rule 20 state 'related'
set firewall ipv4 forward filter rule 200 action 'accept'
set firewall ipv4 forward filter rule 200 inbound-interface name 'bond*'

В этой конфигурации:

  • bond1 охватывает входящий трафик с bond1.10 и любые другие подинтерфейсы bond1.

  • bond2.20 отключает только VLAN 20 — другие подинтерфейсы bond2 остаются на стандартном пути пересылки. Это показывает, как выбрать отключение одного VLAN, оставив другие на медленном пути.

  • Правило 200 использует маску для приема любого трафика, поступающего на любой интерфейс bond или подинтерфейс до того, как поток достигнет состояния established и будет пригоден для отключения

  • Как только поток установлен, правило 10 добавляет его в flowtable, и последующие пакеты полностью пропускают хук forward через быстрый путь

Примечание

Направления интерфейсов в этом примере с точки зрения клиент-серверного трафика. На практике каждый интерфейс обрабатывает трафик в обоих направлениях, и flowtable управляет отключением симметрично, как только поток установлен. Чтобы подтвердить входящие и исходящие интерфейсы, включите log в правило в forward hook и проверьте журналы брандмауэра — см. раздел Брандмауэр для настройки.

Проверки

Проверьте таблицу conntrack, чтобы убедиться, что система приняла и правильно отключила соединения.

Идентификация интерфейса

Чтобы убедиться, что VyOS идентифицирует трафик по его логическому подинтерфейсу и не по underlying физическому устройству, проверьте журнал брандмауэра:

vyos@FlowTables:~$ show log firewall
Jun 18 22:22:00 kernel: [ipv4-FWD-filter-200-A] IN=bond1.10 OUT=bond2.20 \
  MAC=00:53:00:00:00:02:00:53:00:00:00:01:08:00 SRC=192.168.10.2 \
  DST=192.168.20.2 LEN=84 PROTO=ICMP TYPE=8 CODE=0 ID=3572 SEQ=1

Поля IN и OUT показывают bond1.10 и bond2.20 — логические подинтерфейсы — а не underlying физическое устройство или bond.

Отключение flowtable

Выполните следующую команду, чтобы убедиться, что соединения отключены на fast path flowtable:

vyos@FlowTables:~$ show conntrack table ipv4
Original src        Original dst       Reply src          Reply dst           Protocol    State    Timeout    Mark    Zone
------------------  -----------------  -----------------  ------------------  ----------  -------  ---------  ------  ------
192.168.10.2:45140  192.168.20.2:5201  192.168.20.2:5201  192.168.10.2:45140  tcp                  n/a        0
192.168.10.2:45124  192.168.20.2:5201  192.168.20.2:5201  192.168.10.2:45124  tcp                  n/a        0


vyos@FlowTables:~$ show conntrack table ipv4
Original src        Original dst       Reply src          Reply dst           Protocol    State      Timeout    Mark    Zone
------------------  -----------------  -----------------  ------------------  ----------  ---------  ---------  ------  ------
192.168.10.2:45124  192.168.20.2:5201  192.168.20.2:5201  192.168.10.2:45124  tcp         TIME_WAIT  105        0

Записи с Timeout, отображаемыми как n/a, и пустым State подтверждают, что потоки отключены на fast path flowtable — последующие пакеты полностью пропускают брандмауэр. Как только сессия TCP закрывается, запись переходит в TIME_WAIT и счетчик таймаута возобновляется.
