NAT44

NAT — это распространенный метод переназначения одного пространства IP-адресов в другое путем изменения сетевой информации об адресе в заголовке IP-пакета, пока они проходят через устройство маршрутизации трафика. Этот метод изначально использовался как способ избежать необходимости перепрограммирования каждого хоста при перемещении сети. Он стал популярным и необходимым инструментом для сохранения глобального адресного пространства в условиях истощения IPv4-адресов. Один IP-адрес, доступный в интернете, может использоваться для целой частной сети.

Маскарадинг — это техника, скрывающая все пространство IP-адресов, обычно состоящее из частных IP-адресов, за одним IP-адресом в другом, обычно публичном адресном пространстве. Скрытые адреса преобразуются в один (общедоступный) IP-адрес как исходный адрес исходящих IP-пакетов, поэтому они кажутся происходящими не от скрытого хоста, а от самого устройства маршрутизации. Из-за популярности этого метода для сохранения IPv4-адресного пространства термин NAT стал почти синонимом маскарадинга.

Поскольку преобразование сетевых адресов изменяет информацию о IP-адресе в пакетах, реализации NAT могут различаться по своему поведению в различных случаях адресации и их влиянии на сетевой трафик. Конкретные особенности поведения NAT обычно не документируются производителями оборудования, содержащего реализации NAT.

Компьютеры на внутренней сети могут использовать любой из адресов, зарезервированных IANA для частичного адресирования (см. RFC 1918). Эти зарезервированные IP-адреса не используются в интернете, поэтому внешняя машина не будет напрямую направлять их. Следующие адреса зарезервированы для частного использования:

  • 10.0.0.0 до 10.255.255.255 (CIDR: 10.0.0.0/8)

  • 172.16.0.0 до 172.31.255.255 (CIDR: 172.16.0.0/12)

  • 192.168.0.0 до 192.168.255.255 (CIDR: 192.168.0.0/16)

Если провайдер использует CGN, и использует RFC 1918 адресное пространство для нумерации шлюзов клиентов, риск коллизии адресов, а значит, ошибок маршрутизации возникает, когда сети клиента уже используют RFC 1918 адресное пространство.

Это побудило некоторые провайдеры разработать политику внутри ARIN для выделения нового частного адресного пространства для CGN, но ARIN отложил реализацию политики, указав, что вопрос не является типичной задачей распределения, а резервированием адресов для технических целей (по RFC 2860).

IETF опубликовал RFC 6598, подробно описывающий общее адресное пространство для использования в развертываниях CGN провайдера, которое может обрабатывать те же сетевые префиксы, которые встречаются как на входных, так и на выходных интерфейсах. ARIN вернул адресное пространство в IANA для этого распределения.

Выделенный блок адресов — 100.64.0.0/10.

Устройствам, оценивающим, является ли IPv4-адрес публичным, необходимо обновить их, чтобы распознавать новое адресное пространство. Выделение дополнительного частного IPv4-адресного пространства для устройств NAT может продлить переход к IPv6.

Обзор

Разные типы NAT

SNAT

SNAT — наиболее распространенная форма NAT и обычно называется просто NAT. Чтобы быть более точным, то, что большинство людей называют NAT, на самом деле является процессом PAT, или NAT-перегрузка. SNAT обычно используется внутренними пользователями/частными хостами для доступа в интернет — исходный адрес преобразуется и таким образом остается частным.

DNAT

DNAT меняет адрес назначения пакетов, проходящих через маршрутизатор, в то время как SNAT меняет исходный адрес пакетов. DNAT обычно используется, когда внешний (публичный) хост должен инициировать сессию с внутренним (частным) хостом. Клиенту нужно получить доступ к частной службе за маршрутизатором его публичного IP. Соединение устанавливается с помощью публичного IP-адреса маршрутизатора на хорошо известном порту, и таким образом весь трафик для этого порта перезаписывается, чтобы адресовать внутренний (частный) хост.

Двунаправленный NAT

Это распространенная ситуация, когда одновременно настроены SNAT и DNAT. Он часто используется, когда внутренние (частные) хосты должны установить соединение с внешними ресурсами, а внешние системы должны получить доступ к внутренним (частным) ресурсам.

Набор правил NAT

NAT полностью настраивается на серии так называемых правил. Правила пронумерованы и оцениваются операционной системой в числовом порядке! Номера правил можно изменить, используя команды rename и copy.

Примечание

Изменения в системе NAT влияют только на новые установленные соединения. Уже существующие соединения не затрагиваются.

Совет

При проектировании набора правил NAT оставьте некоторое пространство между последовательными правилами для последующего расширения. Ваш набор правил может начинаться с чисел 10, 20, 30. Таким образом, вы сможете позже расширить набор правил и разместить новые правила между существующими.

Правила будут созданы как для SNAT, так и для DNAT.

Для Двунаправленного NAT необходимо создать правило как для SNAT, так и для DNAT.

Фильтры трафика

Фильтры трафика используются для контроля того, какие пакеты будут применять определенные правила NAT. В рамках одного правила NAT можно применить пять различных фильтров.

  • outbound-interface - применимо только к SNAT. Определяет интерфейс, используемый для внешнего трафика, к которому применяется это правило преобразования. Также поддерживаются группы интерфейсов, обратный выбор и подстановочные знаки.

    Примеры:

    set nat source rule 20 outbound-interface name eth0
set nat source rule 30 outbound-interface name bond1*
set nat source rule 20 outbound-interface name !vtun2
set nat source rule 20 outbound-interface group GROUP1
set nat source rule 20 outbound-interface group !GROUP2

  • inbound-interface - применимо только к DNAT. Определяет интерфейс, используемый для внутреннего трафика, к которому применяется правило преобразования. Также поддерживаются группы интерфейсов, обратный выбор и подстановочные знаки.

    Пример:

    set nat destination rule 20 inbound-interface name eth0
set nat destination rule 30 inbound-interface name bond1*
set nat destination rule 20 inbound-interface name !vtun2
set nat destination rule 20 inbound-interface group GROUP1
set nat destination rule 20 inbound-interface group !GROUP2

  • protocol - указывает, к каким типам протоколов применяется это правило преобразования. Только пакеты, соответствующие указанному протоколу, подвергаются NAT. По умолчанию это относится ко всем протоколам.

    Пример:

    • Установите правило SNAT 20, чтобы NAT-преобразовывать только пакеты TCP и UDP

    • Установите правило DNAT 20, чтобы NAT-преобразовывать только пакеты UDP

    set nat source rule 20 protocol tcp_udp
set nat destination rule 20 protocol udp

  • source - указывает, к каким пакетам применяется правило преобразования NAT, основываясь на исходном IP-адресе и/или исходном порте пакета. Только совпадающие пакеты рассматриваются для NAT.

    Пример:

    • Установите правило SNAT 20, чтобы NAT-преобразовывать только пакеты, приходящие с сети 192.0.2.0/24

    • Установите правило SNAT 30, чтобы NAT-преобразовывать только пакеты, приходящие с сети 203.0.113.0/24 с исходным портом 80 и 443

    set nat source rule 20 source address 192.0.2.0/24
set nat source rule 30 source address 203.0.113.0/24
set nat source rule 30 source port 80,443

  • destination - указывает, к каким пакетам применяется преобразование, основываясь только на конфигурированном адресе и/или порте назначения.

    Примечание

    Если не указано назначение, правило будет соответствовать любому адресу назначения и порту.

    Пример:

    • Настройте правило SNAT (40), чтобы NAT-преобразовывать только пакеты с адресом назначения 192.0.2.1.

    set nat source rule 40 destination address 192.0.2.1

Преобразование адресов

Каждое правило NAT имеет определенную команду преобразования. Адрес, определенный для преобразования, используется, когда информация об адресе в пакете заменяется.

Исходный адрес

Для правил SNAT исходный адрес пакета будет заменен на адрес, указанный в команде преобразования. Также можно указать преобразование порта, которое является частью преобразования адреса.

Примечание

Адрес преобразования должен быть установлен на один из доступных адресов на настроенном outbound-interface, или он должен быть установлен на masquerade, который будет использовать основной IP-адрес outbound-interface как адрес преобразования.

Примечание

При использовании NAT для большого количества систем хостов рекомендуется использовать минимум 1 IP-адрес для NAT на каждые 256 частных систем хостов. Это связано с ограничением 65 000 портов, доступных для уникальных преобразований, и средним количеством 200-300 сеансов на хост.

Пример:

  • Определите отдельный исходный IP-адрес 100.64.0.1 для правила SNAT 20

  • Используйте адрес masquerade (основной адрес интерфейса) в правиле 30

  • Если у вас большое количество частных машин за NAT, ваш адресный диапазон может быть больше. Используйте любой адрес в диапазоне 100.64.0.10 - 100.64.0.20 на правиле SNAT 40 при выполнении преобразования

set nat source rule 20 translation address 100.64.0.1
set nat source rule 30 translation address 'masquerade'
set nat source rule 40 translation address 100.64.0.10-100.64.0.20

Адрес назначения

Для правил DNAT адрес назначения пакета будет заменен указанным адресом в команде translation address.

Пример:

  • Правило DNAT 10 заменяет адрес назначения входящего пакета на 192.0.2.10

set nat destination rule 10 translation address 192.0.2.10

Также в DNAT поддерживается перенаправление на локальный хост. Команда перенаправления — это специальная форма DNAT, которая всегда преобразует адрес назначения в локальный хост.

Пример перенаправления:

set nat destination rule 10 translation redirect port 22

NAT балансировка нагрузки

Для применения исходного или целевого NAT, а также для определения нескольких преобразованных адресов в пределах одного правила, можно использовать расширенную конфигурацию, чтобы NAT распределял преобразования между ними.

NAT балансировки нагрузки использует алгоритм, генерирующий хэш и, на основе него, применяет соответствующее преобразование. Этот хэш может генерироваться случайно или может использовать данные из заголовка IP: исходный адрес, адрес назначения, исходный порт и/или порт назначения. По умолчанию хэш генерируется случайно.

При определении преобразованного адреса, называемого backends, необходимо настроить weight. Это позволяет пользователю определить распределение балансировки нагрузки в соответствии с их потребностями. Сумма всех весов, определенных для backends, должна быть равна 100. Другими словами, вес, определенный для backend, представляет собой процент соединений, которые получат такой backend.

set nat [source | destination] rule <rule> load-balance hash [source-address | destination-address | source-port | destination-port | random]
set nat [source | destination] rule <rule> load-balance backend <x.x.x.x> weight <1-100>

Примеры конфигурации

Для настройки SNAT, нам нужно знать:

  • Внутренние IP-адреса, которые мы хотим преобразовать

  • Выходной интерфейс для выполнения преобразования

  • Внешний IP-адрес, на который нужно преобразовать

В примере, использованном для быстрого старта выше, мы демонстрируем следующую конфигурацию:

set nat source rule 100 outbound-interface name 'eth0'
set nat source rule 100 source address '192.168.0.0/24'
set nat source rule 100 translation address 'masquerade'

Это генерирует следующую конфигурацию:

rule 100 {
    outbound-interface {
        name eth0
    }
    source {
        address 192.168.0.0/24
    }
    translation {
        address masquerade
    }
}

В этом примере мы используем masquerade как адрес преобразования вместо IP-адреса. Цель masquerade эффективно означает «использовать любой IP-адрес на исходном интерфейсе», а не статически настроенный IP-адрес. Это полезно, если вы используете DHCP для вашего исходного интерфейса и не знаете, какой будет внешний адрес.

При использовании NAT для большого количества систем хостов рекомендуется использовать минимальное количество 1 IP-адреса для NAT на каждые 256 систем хостов. Это связано с ограничением 65 000 портов, доступных для уникальных преобразований, и средним количеством 200-300 сеансов на хост.

Пример: для сети ~8000 хостов рекомендуется использовать 32 IP-адреса для пула SNAT.

Пул адресов можно определить, используя дефис между двумя IP-адресами:

set nat source rule 100 translation address '203.0.113.32-203.0.113.63'

Избегание «утекающего» NAT

Linux netfilter не NAT-преобразует трафик, помеченный как INVALID. Это часто вызывает недоумение у людей, думающих, что Linux (или конкретно VyOS) имеет сломанную реализацию NAT, потому что не-NAT-преобразованный трафик виден, покидающий внешний интерфейс. На самом деле это работает как задумано, и захват пакетов «утекающего» трафика должен показать, что трафик либо является дополнительным TCP «RST», «FIN,ACK», или «RST,ACK», отправленным клиентскими системами после того, как Linux netfilter считает соединение закрытым. Самый распространенный случай — дополнительный TCP RST, который некоторые реализации хостов отправляют после завершения соединения (что зависит от реализации).

Другими словами, отслеживание соединений уже наблюдало закрытие соединения и перевело поток в INVALID, чтобы предотвратить попытки атакующих повторно использовать соединение.

Вы можете избежать «утекающего» поведения, используя политику брандмауэра, которая отбрасывает пакеты с состоянием «invalid».

Иметь контроль над совпадением пакетов с состоянием «invalid», например, возможность выборочной регистрации, является важным инструментом для наблюдения за неправильным поведением протокола. По этой причине VyOS не глобально отбрасывает пакеты с недопустимым состоянием, вместо этого позволяя оператору решить, как обрабатывать этот трафик.

Hairpin NAT/NAT Reflection

Типичная проблема при использовании NAT и размещении публичных серверов — способность внутренних систем получить доступ к внутреннему серверу с помощью его внешнего IP-адреса. Решение этой проблемы обычно состоит в использовании разделенного DNS, чтобы правильно указать хостам внутренний адрес при запросах, сделанных внутренне. Поскольку многие маленькие сети не имеют инфраструктуры DNS, часто применяется обходной путь для обеспечения трафика, NAT-преобразовывая запрос от внутренних хостов в исходный адрес внутреннего интерфейса на фаерволе.

Этот метод обычно называется NAT Reflection или Hairpin NAT.

Пример:

  • Перенаправьте трафик Microsoft RDP с внешнего (WAN, внешнего) мира через DNAT в правило 100 на внутренний, частный хост 192.0.2.40.

  • Перенаправьте трафик Microsoft RDP с внутренней (LAN, частной) сети через DNAT в правило 110 на внутренний, частный хост 192.0.2.40. Также нам нужно правило SNAT 110 для обратного пути трафика. Сеть внутренних 192.0.2.0/24 доступна через интерфейс eth0.10.

set nat destination rule 100 description 'Regular destination NAT from external'
set nat destination rule 100 destination port '3389'
set nat destination rule 100 inbound-interface name 'pppoe0'
set nat destination rule 100 protocol 'tcp'
set nat destination rule 100 translation address '192.0.2.40'

set nat destination rule 110 description 'NAT Reflection: INSIDE'
set nat destination rule 110 destination port '3389'
set nat destination rule 110 inbound-interface name 'eth0.10'
set nat destination rule 110 protocol 'tcp'
set nat destination rule 110 translation address '192.0.2.40'

set nat source rule 110 description 'NAT Reflection: INSIDE'
set nat source rule 110 destination address '192.0.2.0/24'
set nat source rule 110 outbound-interface name 'eth0.10'
set nat source rule 110 protocol 'tcp'
set nat source rule 110 source address '192.0.2.0/24'
set nat source rule 110 translation address 'masquerade'

Это приводит к конфигурации:

vyos@vyos# show nat

     rule 100 {
         description "Regular destination NAT from external"
         destination {
             port 3389
         }
         inbound-interface {
             name pppoe0
         }
         protocol tcp
         translation {
             address 192.0.2.40
         }
     }
     rule 110 {
         description "NAT Reflection: INSIDE"
         destination {
             port 3389
         }
         inbound-interface {
             name eth0.10
         }
         protocol tcp
         translation {
             address 192.0.2.40
         }
     }
 }
 source {
     rule 110 {
         description "NAT Reflection: INSIDE"
         destination {
             address 192.0.2.0/24
         }
         outbound-interface {
             name eth0.10
         }
         protocol tcp
         source {
             address 192.0.2.0/24
         }
         translation {
             address masquerade
         }
     }
 }

Целевое NAT

DNAT обычно называется Перенаправление порта. При использовании VyOS как маршрутизатора NAT и брандмауэра, часто выполняемой задачей является перенаправление входящего трафика на систему за брандмауэром.

В этом примере мы будем использовать приведенную выше конфигурацию Quick Start в качестве отправной точки.

Для настройки правила DNAT нам нужно собрать:

  • Интерфейс, на котором будет поступать трафик;

  • Протокол и порт, которые мы хотим перенаправить;

  • IP-адрес внутренней системы, на которую мы хотим перенаправить трафик.

В нашем примере мы будем перенаправлять веб-серверный трафик на внутренний веб-сервер на 192.168.0.100. Трафик HTTP использует протокол TCP на порту 80. Для других распространенных номеров портов см.: https://en.wikipedia.org/wiki/List_of_TCP_and_UDP_port_numbers

Наши команды конфигурации будут:

set nat destination rule 10 description 'Port Forward: HTTP to 192.168.0.100'
set nat destination rule 10 destination port '80'
set nat destination rule 10 inbound-interface name 'eth0'
set nat destination rule 10 protocol 'tcp'
set nat destination rule 10 translation address '192.168.0.100'

Это создаст следующую конфигурацию NAT для целевого назначения:

nat {
    destination {
        rule 10 {
            description "Port Forward: HTTP to 192.168.0.100"
            destination {
                port 80
            }
            inbound-interface {
                name eth0
            }
            protocol tcp
            translation {
                address 192.168.0.100
            }
        }
    }
}

Примечание

Если вы перенаправляете трафик на другой порт, чем тот, на котором он прибывает, вы также можете настроить порт преобразования, используя set nat destination rule [n] translation port.

Это устанавливает правило перенаправления порта, но если вы создали политику брандмауэра, она, скорее всего, заблокирует трафик.

Правила брандмауэра для Destination NAT

Важно отметить, что при создании правил брандмауэра, преобразование DNAT происходит до того, как трафик проходит через брандмауэр. То есть, адрес назначения уже был преобразован в 192.168.0.100.

Поэтому в нашем наборе правил брандмауэра мы хотим разрешить трафик, который ранее соответствовал правилу DNAT. Чтобы избежать создания множества правил, одного для каждого правила DNAT, мы можем принять все ‘dnat’ соединения одним простым правилом, используя connection-status matcher:

set firewall ipv4 forward filter rule 10 action accept
set firewall ipv4 forward filter rule 10 connection-status nat destination
set firewall ipv4 forward filter rule 10 state new

Это сгенерирует следующую конфигурацию:

ipv4 {
    forward {
        filter {
            rule 10 {
                action accept
                connection-status {
                    nat destination
                }
                state new
            }
        }
    }
}

1-к-1 NAT

Другое название для DNAT — 1-к-1 NAT. Для конфигурации 1-к-1 NAT используются как DNAT, так и SNAT для преобразования всего трафика с внешнего IP-адреса на внутренний IP-адрес и наоборот.

Обычно правило 1-к-1 NAT опускает порт назначения (все порты) и заменяет протокол на all или ip.

Затем создается соответствующее правило SNAT для преобразования исходящего трафика для внутреннего IP-адреса в зарезервированный внешний IP. Это выделяет внешний IP-адрес для внутреннего IP-адреса и полезно для протоколов, которые не имеют понятия о портах, таких как GRE.

Вот фрагмент простой конфигурации 1-к-1 NAT с одним внутренним и одним внешним интерфейсом:

set interfaces ethernet eth0 address '192.168.1.1/24'
set interfaces ethernet eth0 description 'Inside interface'
set interfaces ethernet eth1 address '192.0.2.30/24'
set interfaces ethernet eth1 description 'Outside interface'
set nat destination rule 2000 description '1-to-1 NAT example'
set nat destination rule 2000 destination address '192.0.2.30'
set nat destination rule 2000 inbound-interface name 'eth1'
set nat destination rule 2000 translation address '192.168.1.10'
set nat source rule 2000 description '1-to-1 NAT example'
set nat source rule 2000 outbound-interface name 'eth1'
set nat source rule 2000 source address '192.168.1.10'
set nat source rule 2000 translation address '192.0.2.30'

Правила брандмауэра создаются как обычно, используя внутренний IP-адрес как источник исходящих правил и назначение входящих правил.

NAT до VPN

Некоторые поставщики услуг приложений (ASPs) эксплуатируют шлюз VPN для предоставления доступа к своим внутренним ресурсам и требуют, чтобы организация, подключающаяся, переводила весь трафик к сети поставщика услуг в исходный адрес, предоставленный ASP.

Балансировка нагрузки

Вот два примера того, как применить NAT балансировки нагрузки.

Первый сценарий: применить целевой NAT для всего трафика HTTP, поступающего через интерфейс eth0, и использовать 4 бэкенда. Первый бэкенд должен получить 30% запросов, второй — 20%, третий — 15%, четвертый — 35%. Мы будем использовать исходный и целевой адрес для генерации хэша.

set nat destination rule 10 inbound-interface name eth0
set nat destination rule 10 protocol tcp
set nat destination rule 10 destination port 80
set nat destination rule 10 load-balance hash source-address
set nat destination rule 10 load-balance hash destination-address
set nat destination rule 10 load-balance backend 198.51.100.101 weight 30
set nat destination rule 10 load-balance backend 198.51.100.102 weight 20
set nat destination rule 10 load-balance backend 198.51.100.103 weight 15
set nat destination rule 10 load-balance backend 198.51.100.104 weight 35

Второй сценарий: применить исходный NAT для всех исходящих соединений с LAN 10.0.0.0/8, используя 3 публичных адреса и равномерное распределение. Мы будем генерировать хэш случайно.

set nat source rule 10 outbound-interface name eth0
set nat source rule 10 source address 10.0.0.0/8
set nat source rule 10 load-balance hash random
set nat source rule 10 load-balance backend 192.0.2.251 weight 33
set nat source rule 10 load-balance backend 192.0.2.252 weight 33
set nat source rule 10 load-balance backend 192.0.2.253 weight 34

Пример сети

Вот один пример сети для ASP. ASP просит, чтобы все соединения от этой компании приходили с 172.29.41.89 — адреса, который назначен ASP и не используется на стороне клиента.

Конфигурация

Необходимая конфигурация может быть разделена на 4 основных части:

  • Виртуальный интерфейс для IP-адреса, предоставленного поставщиком;

  • NAT (в частности, Source NAT);

  • Группы IKE и ESP IPSec;

  • Туннели IPSec.

Виртуальный интерфейс

Виртуальный интерфейс позволяет иметь эквивалент интерфейса Loopback Cisco IOS — внутренний интерфейс маршрутизатора, который мы можем использовать для IP-адресов, которые должен знать маршрутизатор, но которые не привязаны к реальной сети.

Нам нужно только одно действие для этого интерфейса:

set interfaces dummy dum0 address '172.29.41.89/32'
Конфигурация NAT
set nat source rule 110 description 'Internal to ASP'
set nat source rule 110 destination address '172.27.1.0/24'
set nat source rule 110 source address '192.168.43.0/24'
set nat source rule 110 translation address '172.29.41.89'
set nat source rule 120 description 'Internal to ASP'
set nat source rule 120 destination address '10.125.0.0/16'
set nat source rule 120 source address '192.168.43.0/24'
set nat source rule 120 translation address '172.29.41.89'
IPSec IKE и ESP

ASP документировал свои требования к IPSec:

  • Фаза IKE:

    • Шифрование aes256

    • Хеши sha256

  • Фаза ESP:

    • Шифрование aes256

    • Хеши sha256

    • Группа DH 14

Кроме того, мы хотим использовать VPN только на нашем интерфейсе eth1 (внешний интерфейс на изображении выше)

set vpn ipsec ike-group my-ike key-exchange 'ikev1'
set vpn ipsec ike-group my-ike lifetime '7800'
set vpn ipsec ike-group my-ike proposal 1 dh-group '14'
set vpn ipsec ike-group my-ike proposal 1 encryption 'aes256'
set vpn ipsec ike-group my-ike proposal 1 hash 'sha256'

set vpn ipsec esp-group my-esp lifetime '3600'
set vpn ipsec esp-group my-esp mode 'tunnel'
set vpn ipsec esp-group my-esp pfs 'disable'
set vpn ipsec esp-group my-esp proposal 1 encryption 'aes256'
set vpn ipsec esp-group my-esp proposal 1 hash 'sha256'

set vpn ipsec interface 'eth1'
Туннели IPSec

Мы будем использовать группы IKE и ESP, созданные выше, для этого VPN. Так как нам нужно получить доступ к двум разным подсетям на дальней стороне, нам понадобятся два разных туннеля. Если вы изменили имена группы ESP и IKE на предыдущем шаге, убедитесь, что вы используете правильные имена здесь тоже.

set vpn ipsec authentication psk vyos id '203.0.113.46'
set vpn ipsec authentication psk vyos id '198.51.100.243'
set vpn ipsec authentication psk vyos secret 'MYSECRETPASSWORD'
set vpn ipsec site-to-site peer branch authentication local-id '203.0.113.46'
set vpn ipsec site-to-site peer branch authentication mode 'pre-shared-secret'
set vpn ipsec site-to-site peer branch authentication remote-id '198.51.100.243'
set vpn ipsec site-to-site peer branch connection-type 'initiate'
set vpn ipsec site-to-site peer branch default-esp-group 'my-esp'
set vpn ipsec site-to-site peer branch ike-group 'my-ike'
set vpn ipsec site-to-site peer branch ikev2-reauth 'inherit'
set vpn ipsec site-to-site peer branch local-address '203.0.113.46'
set vpn ipsec site-to-site peer branch remote-address '198.51.100.243'
set vpn ipsec site-to-site peer branch tunnel 0 local prefix '172.29.41.89/32'
set vpn ipsec site-to-site peer branch tunnel 0 remote prefix '172.27.1.0/24'
set vpn ipsec site-to-site peer branch tunnel 1 local prefix '172.29.41.89/32'
set vpn ipsec site-to-site peer branch tunnel 1 remote prefix '10.125.0.0/16'
