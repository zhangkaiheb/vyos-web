RPKI

RPKI — это архитектура, предназначенная для обеспечения безопасности инфраструктуры маршрутизации интернета. Она криптографически связывает префиксы IP-адресов с правильными исходящими ASNs. Маршрутизаторы BGP могут использовать эту информацию для проверки источника каждого маршрута против соответствующего ROA на соответствие требованиям. RPKI описана в RFC 6480.

Маршрутизаторы BGP могут получать информацию ROA из программного обеспечения RPKI Relying Party, также известного как сервер RPKI или валидатор, с использованием протокола RTR. Открытое программное обеспечение включает Routinator (Rust) от NLnet Labs, rpki-client (C) от OpenBSD и StayRTR (Go). Протокол RTR описан в RFC 8210.

Совет

Если вы новичок в области безопасности маршрутизации, документация по RPKI, поддерживаемая NLnet Labs, быстро поможет вам освоиться. Она охватывает все, от основных понятий до развертывания в производственной среде.

Начало работы

Сначала вам нужно развернуть валидатор RPKI для ваших маршрутизаторов. Документация по RPKI, поддерживаемая NLnet Labs, предоставляет подробный список открытого программного обеспечения, которое вы можете сравнить и выбрать. После запуска выбранного сервера, ваши маршрутизаторы смогут начать проверку объявлений.

После проверки импортированные маршруты могут иметь один из следующих состояний:

  • valid: Префикс и исходящий ASN совпадают с подписанным ROA. Эти объявления маршрутов считаются надежными.

  • invalid: Префикс, длина префикса или исходящий ASN не совпадают ни с одним существующим ROA. Это может указывать на захват префикса или неправильную конфигурацию и должно рассматриваться как недоверенное.

  • notfound: Нет ROA, покрывающего префикс. На начало 2024 года это относится примерно к 40%–50% префиксов, объявленных в DFZ.

Примечание

Если вы управляете глобальными IP-адресами для вашей сети, убедитесь, что их префиксы имеют связанные ROA, чтобы предотвратить их отметку как notfound в RPKI.

Для большинства сетевых операторов это включает публикацию ROA через соответствующие RIR, такие как ARIN, RIPE NCC, APNIC, LACNIC или AFRINIC. Очень рекомендуется создавать ROA для любых IP-префиксов, которые вы планируете объявлять в DFZ.

Особенно крупные сети могут выбрать запуск собственного центра сертификации RPKI и сервера публикации вместо публикации ROA через свой RIR. Эта тема выходит за рамки документации VyOS. Для получения дополнительной информации рассмотрите ресурсы о Krill.

Текущая реализация

Текущая реализация включает следующие функции:

  • Маршрутизатор BGP подключается к одному или нескольким серверам кэша RPKI для получения проверенных сопоставлений префикса с источником AS. Для реализации продвинутой отказоустойчивости можно настроить несколько серверов кэша с разными значениями приоритета.

  • Если соединение с сервером кэша RPKI не установлено после заданного времени ожидания, маршрутизатор обрабатывает маршруты без проверки источника префикса. Он будет продолжать попытки подключения к серверу кэша RPKI в фоновом режиме.

  • По умолчанию включение RPKI не влияет на выбор лучшего пути. Неверные префиксы все еще рассматриваются при выборе лучшего пути, но вы можете настроить маршрутизатор так, чтобы он игнорировал их.

  • Вы можете настроить карты маршрутов для соответствия определенному состоянию проверки RPKI. Это позволяет создавать локальные политики, которые обрабатывают маршруты BGP на основе результатов проверки источника префикса.

  • Обновления от серверов кэша RPKI применяются напрямую, и выбор пути обновляется соответственно. Примечание: необходимо включить мягкую переконфигурацию BGP для этой функции.

Конфигурация

set protocols rpki polling-period <1-86400>

Настройте интервал, в секундах, через который маршрутизатор опрашивает сервер кэша RPKI на наличие обновлений.

Значение по умолчанию составляет 300 секунд.

Пример:

set protocols rpki polling-period 600
set protocols rpki expire-interval <600-172800>

Настройте интервал, в секундах, через который маршрутизатор истекает срок действия своего кэшированного RPKI-данных.

Значение по умолчанию составляет 7200 секунд.

Пример:

set protocols rpki expire-interval 14400
set protocols rpki retry-interval <1-7200>

Настройте интервал, в секундах, перед повторной попыткой подключения к серверу кэша RPKI после неудачного подключения.

Значение по умолчанию составляет 600 секунд.

Пример:

set protocols rpki retry-interval 60
set protocols rpki cache <address> port <1-65535>

Настройте адрес и порт сервера кэша RPKI.

Адрес можно указать как IPv4 или IPv6-адрес, или как FQDN.

Примечание

Вам нужно настроить оба параметра port и preference для каждого IP-адреса сервера кэша.

Пример:

set protocols rpki cache 192.0.2.1 port 3323
set protocols rpki cache <address> preference <1-255>

Настройте значение приоритета для сервера кэша RPKI.

При настройке нескольких серверов кэша маршрутизатор приоритетно подключается к серверу с наименьшим значением приоритета.

Примечание

Вам нужно настроить оба параметра port и preference для каждого IP-адреса сервера кэша.

Примечание

Значения preference должны быть уникальны среди серверов кэша.

Пример:

set protocols rpki cache 192.0.2.1 preference 1

SSH

Вы можете подключиться к серверу кэша RPKI с помощью протокола RTR через обычный TCP или через SSH. SSH обеспечивает целостность и конфиденциальность транспорта. Используйте SSH, если ваша программа проверки поддерживает этот вариант.

Чтобы использовать аутентификацию SSH, выполните следующие шаги:

Шаг 1. Создайте пару ключей SSH клиента:

generate ssh client-key /config/auth/id_rsa_rpki

Шаг 2. Извлеките часть base64 из обоих ключей, а также идентификатор алгоритма публичного ключа:

   grep -v "PRIVATE KEY" /config/auth/id_rsa_rpki | tr -d '\n'
   awk '{print $2}' /config/auth/id_rsa_rpki.pub
   awk '{print $1}' /config/auth/id_rsa_rpki.pub

Примечание

Подсистема PKI принимает только часть base64 каждого ключа, без PEM/OpenSSH заголовков, подвалов или разрывов строк. Если вы вставите содержимое файла напрямую, коммит не удастся.

Шаг 3. Импортируйте пару ключей в подсистему PKI:

   set pki openssh <name> private key <base64-encoded-private-key>
   set pki openssh <name> public key <base64-encoded-public-key>
   set pki openssh <name> public type <type>

После импорта пары ключей настройте соединение SSH, используя приведенные ниже команды.

set protocols rpki cache <address> ssh username <user>

Настройте имя пользователя SSH для аутентификации на сервере кэша RPKI.

Пример:

set protocols rpki cache 192.0.2.1 ssh username rpki-user
set protocols rpki cache <address> ssh key <name>

Настройте имя пары ключей OpenSSH, используемой для аутентификации на сервере кэша RPKI.

Параметр <name> должен совпадать с именем пары ключей, ранее определенным в командах set pki openssh.

Пример:

set protocols rpki cache 192.0.2.1 ssh key rpki

Пример

Следующий пример демонстрирует, как подключиться к серверу кэша RPKI (например, Routinator) и создать маршрут импорта для фильтрации префиксов на основе их состояния проверки.

Сначала настройте подключение к серверу кэша RPKI по адресу 192.0.2.1:

set protocols rpki cache 192.0.2.1 port '3323'
set protocols rpki cache 192.0.2.1 preference '1'

Далее создайте карту маршрутов для применения к вашим входящим обновлениям BGP. Эта политика определяет следующее поведение:

  • Разрешает valid префиксы и назначает высокий локальный приоритет (300).

  • Разрешает notfound префиксы, но назначает более низкий локальный приоритет (125).

  • Отклоняет префиксы со статусом invalid.

set policy route-map ROUTES-IN rule 10 action 'permit'
set policy route-map ROUTES-IN rule 10 match rpki 'valid'
set policy route-map ROUTES-IN rule 10 set local-preference '300'

set policy route-map ROUTES-IN rule 20 action 'permit'
set policy route-map ROUTES-IN rule 20 match rpki 'notfound'
set policy route-map ROUTES-IN rule 20 set local-preference '125'

set policy route-map ROUTES-IN rule 30 action 'deny'
set policy route-map ROUTES-IN rule 30 match rpki 'invalid'

После настройки ваших маршрутизаторов на отклонение RPKI-недопустимых префиксов, проверьте настройку, используя веб-сайт Cloudflare.

Примечание

Убедитесь, что нет маршрутов по умолчанию или других путей, которые направляли бы трафик к RPKI-недопустимым пунктам назначения. В противном случае тест может сообщить, что маршрутизатор является небезопасным.
