RPKI

RPKI ist eine Architektur, die entwickelt wurde, um das Internet-Routing-Infrastruktur zu sichern. Sie kryptografisch IP-Adresspräfixe mit dem richtigen ursprünglichen ASNs verknüpft. BGP-Router können diese Daten verwenden, um die Herkunft jedes Routens gegen den entsprechenden ROA auf Gültigkeit zu prüfen. RPKI wird in RFC 6480 beschrieben.

BGP-Router können ROA-Informationen aus RPKI Relying Party-Software, auch als RPKI-Server oder Validator bekannt, über das RTR-Protokoll abrufen. Open-source-Implementierungen umfassen NLnet Labs’ Routinator (Rust), OpenBSD’s rpki-client (C) und StayRTR (Go). Das RTR-Protokoll wird in RFC 8210 beschrieben.

Tipp

Wenn Sie neu in der Routing-Sicherheit sind, wird die RPKI-Dokumentation, die von NLnet Labs gepflegt wird, Sie schnell auf den neuesten Stand bringen. Sie deckt alles ab, von grundlegenden Konzepten bis hin zur Produktionsbereitstellung.

Erste Schritte

Zuerst müssen Sie einen RPKI-Validator für Ihre Router bereitstellen. Die RPKI-Dokumentation, die von NLnet Labs gepflegt wird, bietet eine umfassende Liste von Open-Source-Software-Paketen, die Sie vergleichen und wählen können. Sobald Ihr gewählter Server läuft, können Ihre Router mit der Validierung von Anmeldeinformationen beginnen.

Nach der Validierung können importierte Routen einen der folgenden Zustände haben:

  • valid: Das Präfix und die ursprüngliche ASN stimmen mit einem signierten ROA überein. Diese Routenanmeldungen werden als vertrauenswürdig angesehen.

  • invalid: Das Präfix, Präfixlänge oder die ursprüngliche ASN stimmen nicht mit irgendeinem vorhandenen ROA überein. Dies kann auf ein Präfix-Hijacking oder eine Fehlkonfiguration hinweisen und sollte als unvertrauenswürdig behandelt werden.

  • notfound: Kein ROA deckt das Präfix ab. Bis Anfang 2024 gilt dies für etwa 40 % bis 50 % der Präfixe, die an das DFZ gemeldet werden.

Hinweis

Wenn Sie globale IP-Adressen für Ihr Netzwerk verwalten, stellen Sie sicher, dass ihre Präfixe mit ROAs verbunden sind, um zu verhindern, dass sie von RPKI als notfound markiert werden.

Für die meisten Netzwerkbetreiber bedeutet dies, ROAs über ihre jeweiligen RIR, wie ARIN, RIPE NCC, APNIC, LACNIC oder AFRINIC, zu veröffentlichen. Es wird dringend empfohlen, ROAs für alle IP-Präfixe zu erstellen, die Sie in das DFZ anmelden möchten.

Besonders große Netzwerke können stattdessen ihre eigenen RPKI-Zertifikatsbehörde und Veröffentlichungsserver betreiben, anstatt ROAs über ihre RIR zu veröffentlichen. Dieses Thema liegt außerhalb des Umfangs der VyOS-Dokumentation. Für weitere Informationen betrachten Sie bitte Ressourcen zu Krill.

Aktuelle Implementierung

Die aktuelle Implementierung umfasst folgende Funktionen:

  • Der BGP-Router verbindet sich mit einem oder mehreren RPKI-Cache-Servern, um validierte Präfix-zu-Origins AS-Zuordnungen zu erhalten. Fortschrittliche Failover-Optionen können durch die Konfiguration mehrerer Cache-Server mit unterschiedlichen Präferenzwerten implementiert werden.

  • Wenn nach einem vordefinierten Timeout keine Verbindung zu einem RPKI-Cache-Server hergestellt wird, verarbeitet der Router Routen ohne Präfix-Origins-Überprüfung. Er versucht weiterhin, im Hintergrund eine Verbindung zu einem RPKI-Cache-Server herzustellen.

  • Standardmäßig beeinflusst das Aktivieren von RPKI die Auswahl des besten Pfades nicht. Ungültige Präfixe werden weiterhin bei der Auswahl des besten Pfades berücksichtigt, aber Sie können den Router so konfigurieren, dass er sie ignoriert.

  • Sie können Route-Maps konfigurieren, um einen bestimmten RPKI-Validierungsstatus zu matchen. Dies ermöglicht die Erstellung lokaler Richtlinien, die BGP-Routen basierend auf Ergebnissen der Präfix-Origins-Überprüfung verarbeiten.

  • Updates von RPKI-Cache-Servern werden direkt angewandt, und die Pfadauswahl wird entsprechend aktualisiert. Hinweis: Für diese Funktion muss die BGP-Soft-Rekonfiguration aktiviert sein.

Konfiguration

set protocols rpki polling-period <1-86400>

Konfigurieren Sie das Intervall in Sekunden, mit dem der Router den RPKI-Cache-Server nach Updates abfragt.

Der Standardwert beträgt 300 Sekunden.

Beispiel:

set protocols rpki polling-period 600
set protocols rpki expire-interval <600-172800>

Konfigurieren Sie das Intervall in Sekunden, nach dem der Router seine zwischengespeicherten RPKI-Daten ablaufen lässt.

Der Standardwert beträgt 7200 Sekunden.

Beispiel:

set protocols rpki expire-interval 14400
set protocols rpki retry-interval <1-7200>

Konfigurieren Sie das Intervall in Sekunden, bevor der Router einen fehlgeschlagenen Verbindungsaufbau zum RPKI-Cache-Server wiederholt.

Der Standardwert beträgt 600 Sekunden.

Beispiel:

set protocols rpki retry-interval 60
set protocols rpki cache <address> port <1-65535>

Konfigurieren Sie die Adresse und den Port eines RPKI-Cache-Servers.

Die Adresse kann als IPv4- oder IPv6-Adresse oder als FQDN angegeben werden.

Hinweis

Sie müssen für jede Cache-Server-IP-Adresse sowohl port als auch preference konfigurieren.

Beispiel:

set protocols rpki cache 192.0.2.1 port 3323
set protocols rpki cache <address> preference <1-255>

Konfigurieren Sie den Präferenzwert für einen RPKI-Cache-Server.

Wenn mehrere Cache-Server konfiguriert sind, priorisiert der Router die Verbindung zum Server mit dem niedrigsten Präferenzwert.

Hinweis

Sie müssen für jede Cache-Server-IP-Adresse sowohl port als auch preference konfigurieren.

Hinweis

preference-Werte müssen eindeutig über die Cache-Server sein.

Beispiel:

set protocols rpki cache 192.0.2.1 preference 1

SSH

Sie können sich mit dem RPKI-Cache-Server über das RTR-Protokoll über reines TCP oder über SSH verbinden. SSH bietet Transportintegrität und Vertraulichkeit. Nutzen Sie SSH, wenn Ihre Validierungssoftware diese Option unterstützt.

Um SSH-Authentifizierung zu verwenden, führen Sie die folgenden Schritte aus:

Schritt 1. Generieren Sie ein SSH-Client-Key-Paar:

generate ssh client-key /config/auth/id_rsa_rpki

Schritt 2. Extrahieren Sie den Base64-Teil aus beiden Schlüsseln sowie den Algorithmus-Identifier des öffentlichen Schlüssels:

   grep -v "PRIVATE KEY" /config/auth/id_rsa_rpki | tr -d '\n'
   awk '{print $2}' /config/auth/id_rsa_rpki.pub
   awk '{print $1}' /config/auth/id_rsa_rpki.pub

Hinweis

Das PKI-Subsystem akzeptiert nur den Base64-Teil jedes Schlüssels, ohne PEM/OpenSSH-Kopfzeilen, Fußzeilen oder Zeilenumbrüche. Wenn Sie den Dateiinhalt direkt einfügen, schlägt der Commit fehl.

Schritt 3. Importieren Sie das Schlüsselpaar in das PKI-Subsystem:

   set pki openssh <name> private key <base64-encoded-private-key>
   set pki openssh <name> public key <base64-encoded-public-key>
   set pki openssh <name> public type <type>

Einmal importiert, richten Sie die SSH-Verbindung mit den unten stehenden Befehlen ein.

set protocols rpki cache <address> ssh username <user>

Konfigurieren Sie den SSH-Benutzernamen für die Authentifizierung beim RPKI-Cache-Server.

Beispiel:

set protocols rpki cache 192.0.2.1 ssh username rpki-user
set protocols rpki cache <address> ssh key <name>

Konfigurieren Sie den Namen des OpenSSH-Schlüsselpaars, das zum Authentifizieren beim RPKI-Cache-Server verwendet wird.

Der <name> muss einem Schlüsselpaarnamen entsprechen, der zuvor unter den set pki openssh-Befehlen definiert wurde.

Beispiel:

set protocols rpki cache 192.0.2.1 ssh key rpki

Beispiel

Das folgende Beispiel zeigt, wie man sich mit einem RPKI-Cache-Server (wie Routinator) verbindet und eine Import-Route-Map erstellt, um Präfixe anhand ihres Validierungsstatus zu filtern.

Zuerst konfigurieren Sie die Verbindung zum RPKI-Cache-Server unter 192.0.2.1:

set protocols rpki cache 192.0.2.1 port '3323'
set protocols rpki cache 192.0.2.1 preference '1'

Anschließend erstellen Sie eine Route-Map, die auf Ihre eingehenden BGP-Updates angewandt wird. Diese Richtlinie legt folgendes Verhalten fest:

  • Erlaubt valid Präfixe und weist eine hohe Local-Preference (300) zu.

  • Erlaubt notfound Präfixe, weist jedoch eine niedrigere Local-Preference (125) zu.

  • Verweigert Präfixe mit einem invalid Status.

set policy route-map ROUTES-IN rule 10 action 'permit'
set policy route-map ROUTES-IN rule 10 match rpki 'valid'
set policy route-map ROUTES-IN rule 10 set local-preference '300'

set policy route-map ROUTES-IN rule 20 action 'permit'
set policy route-map ROUTES-IN rule 20 match rpki 'notfound'
set policy route-map ROUTES-IN rule 20 set local-preference '125'

set policy route-map ROUTES-IN rule 30 action 'deny'
set policy route-map ROUTES-IN rule 30 match rpki 'invalid'

Nachdem Sie Ihre Router so konfiguriert haben, dass sie RPKI-ungültige Präfixe ablehnen, überprüfen Sie die Einrichtung mit der Testwebsite von Cloudflare.

Hinweis

Stellen Sie sicher, dass es keine Standardrouten oder andere Pfade gibt, die den Verkehr zu RPKI-ungültigen Zielen leiten. Andernfalls könnte der Test den Router als unsicher melden.
