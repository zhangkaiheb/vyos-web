Konfigurations-Synchronisation

Die Konfigurations-Synchronisation (config-sync) ist ein VyOS-Dienst, der ausgewählte Abschnitte der Konfiguration eines Routers auf einen anderen Router repliziert. Sie entlastet die manuelle Nachbildung von Konfigurationsänderungen vom primären Router auf den sekundären.

Die Synchronisation erfolgt durch einen post-commit-Hook auf dem primären Router. Der Hook überwacht die ausgewählten Abschnitte für die Synchronisation. Wenn einer davon durch einen Commit verändert wird, ruft der Hook die HTTPS-API des sekundären Routers auf und sendet den aktuellen Zustand aller ausgewählten Abschnitte in einem der folgenden Modi:

  • load: Ersetzt die ausgewählten Abschnitte auf dem sekundären mit der Version des primären. Alles, was nur auf dem sekundären innerhalb dieser Abschnitte existiert, wird gelöscht.

  • set: Fügt die Version des primären der ausgewählten Abschnitte in den sekundären ein. Konfliktierende Werte werden durch den primären überschrieben. Einträge, die nur auf dem sekundären existieren, bleiben erhalten.

Die Synchronisation erfolgt streng einseitig vom primären zum sekundären; Änderungen, die auf dem sekundären vorgenommen werden, werden nicht zurückgesendet.

Beide Router müssen während eines Commits auf dem primären, der einen konfigurierten Abschnitt verändert, online sein. Wenn der sekundäre nicht erreichbar ist, schlägt der Commit des primären erfolgreich, aber die Konfiguration wird nicht synchronisiert, und der Fehler wird in das Systemprotokoll geschrieben.

Konfiguration

Sekundär-Router-Parameter

set service config-sync secondary address <address>

Konfigurieren Sie die Adresse des sekundären Routers.

Der primäre Router sendet die synchronisierte Konfiguration über die HTTPS-API des sekundären an diese Adresse. Der Wert kann eine IPv4-Adresse, eine IPv6-Adresse oder ein FQDN sein. Dieser Wert ist obligatorisch.

Hinweis

Die Adresse muss immer dann festgelegt werden, wenn service config-sync konfiguriert wird. Andernfalls wird der Commit abgelehnt.

Beispiel:

set service config-sync secondary address 192.0.2.112
set service config-sync secondary port <1-65535>

Konfigurieren Sie den TCP-Port, auf dem die HTTPS-API des sekundären Routers lauscht.

Der Wert muss mit dem Port übereinstimmen, der unter service https port auf dem sekundären Router konfiguriert ist. Wenn sie sich unterscheiden, schlägt der Commit des primären erfolgreich, aber die Post-Commit-Synchronisation fehlschlägt. Der sekundäre wird nicht aktualisiert, und der primäre protokolliert den Fehler im Systemprotokoll.

Der Standardwert ist 443, was dem Standardwert von service https port entspricht.

Beispiel:

set service config-sync secondary port 8443
set service config-sync secondary key <key>

Konfigurieren Sie den HTTPS-API-Key, den der primäre Router verwendet, um sich bei der HTTPS-API des sekundären Routers zu authentifizieren.

Der Wert muss mit einem Schlüssel übereinstimmen, der unter service https api keys id <ID> key auf dem sekundären konfiguriert ist. Wenn kein entsprechender Schlüssel auf dem sekundären vorhanden ist, schlägt der Commit des primären erfolgreich, aber die Post-Commit-Synchronisation fehlschlägt. Der sekundäre wird nicht aktualisiert, und der primäre protokolliert den Fehler im Systemprotokoll.

Hinweis

Dieser Wert muss immer dann festgelegt werden, wenn service config-sync konfiguriert wird. Andernfalls wird der Commit abgelehnt.

Beispiel:

set service config-sync secondary key 'foo'
set service config-sync secondary timeout <1-3600>

Konfigurieren Sie, wie lange der primäre Router nach einer HTTPS-Antwort vom sekundären wartet, nachdem die Konfiguration gesendet wurde.

Der Standardwert beträgt 60 Sekunden.

Beispiel:

set service config-sync secondary timeout 120

Synchronisationsmodus

set service config-sync mode <load | set>

Konfigurieren Sie, wie der sekundäre Router die Konfiguration anwendet, die vom primären gesendet wird:

  • load: Ersetzt die ausgewählten Abschnitte auf dem sekundären mit der Version des primären. Alles, was nur auf dem sekundären innerhalb dieser Abschnitte existiert, wird gelöscht.

  • set: Fügt die Version des primären der ausgewählten Abschnitte in den sekundären ein. Konfliktierende Werte werden durch den primären überschrieben. Einträge, die nur auf dem sekundären existieren, bleiben erhalten.

Hinweis

Dieser Wert muss immer dann festgelegt werden, wenn service config-sync konfiguriert wird. Andernfalls wird der Commit abgelehnt.

Beispiel:

set service config-sync mode load

Abschnitte zur Synchronisation

set service config-sync section <section>

Konfigurieren Sie einen oder mehrere Konfigurationsabschnitte, die vom primären zum sekundären Router synchronisiert werden sollen.

Wiederholen Sie den Befehl, um zusätzliche Abschnitte hinzuzufügen. Wenn ein konfiguriertes Stück durch einen Commit auf dem primären verändert wird, sendet der Hook den aktuellen Zustand aller konfigurierten Abschnitte an den sekundären. Wenn keiner der konfigurierten Abschnitte verändert wurde, tut der Hook nichts.

Unterstützte Abschnitte:

  • firewall

  • interfaces <bonding | bridge | dummy | ethernet | geneve | input | l2tpv3 | loopback | macsec | openvpn | pppoe | pseudo-ethernet | sstpc | tunnel | virtual-ethernet | vti | vxlan | wireguard | wireless | wwan>

  • nat

  • nat66

  • pki

  • policy

  • protocols <babel | bfd | bgp | failover | igmp-proxy | isis | mpls | nhrp | ospf | ospfv3 | pim | pim6 | rip | ripng | rpki | segment-routing | static>

  • qos <interface | policy>

  • service <console-server | dhcp-relay | dhcp-server | dhcpv6-relay | dhcpv6-server | dns | lldp | mdns | monitoring | ndp-proxy | ntp | snmp | tftp-server | webproxy>

  • system <conntrack | flow-accounting | login | option | sflow | static-host-mapping | sysctl | time-zone>

  • vpn

  • vrf

Hinweis

Es muss mindestens ein Abschnitt festgelegt werden, wenn service config-sync konfiguriert wird. Andernfalls wird der Commit abgelehnt.

Beispiel:

set service config-sync section protocols ospf
set service config-sync section system time-zone

Betrieb

show configuration secondary sync [commands] [running | candidate | saved [<config-node-path>]]

Zeigen Sie den Unterschied zwischen der lokalen Konfiguration auf dem primären und der laufenden Konfiguration auf dem sekundären an.

Der Befehl ruft die laufende Konfiguration des sekundären live über die HTTPS-API ab, daher muss der sekundäre erreichbar sein.

Die lokale Konfiguration ist standardmäßig auf running eingestellt und kann auf candidate (unveröffentlichte Änderungen) oder saved (letzte gespeicherte Konfiguration) gesetzt werden. Die entfernte Seite ist immer die laufende Konfiguration des sekundären.

Standardmäßig wird der Unterschied im curly-brace-Konfigurationsformat angezeigt, wobei Zeilen, die nur auf dem sekundären existieren, mit - präfixiert und Zeilen, die nur auf dem primären existieren, mit + präfixiert werden. Das optionale commands-Schlüsselwort rendert denselben Unterschied als Sequenz von set und delete-Konfigurationsbefehlen, wobei set Pfade anzeigt, die nur auf dem primären vorhanden sind, und delete Pfade anzeigt, die nur auf dem sekundären vorhanden sind.

Das optionale <config-node-path>-Argument begrenzt den Unterschied auf einen einzelnen Abschnitt und muss einer der bereits unter set service config-sync section konfigurierten Abschnitte sein. Wenn es weggelassen wird, deckt der Unterschied alle konfigurierten Abschnitte ab.

Beispiele:

# Vergleichen Sie die vollständige laufende Konfiguration mit dem sekundären
show configuration secondary sync

# Vergleichen Sie nur die OSPF-Protokollkonfiguration mit dem sekundären
show configuration secondary sync running protocols ospf

# Vergleichen Sie die Kandidaten-Konfiguration mit dem sekundären,
# als Befehle dargestellt
show configuration secondary sync commands candidate

Beispiel

Das folgende Beispiel synchronisiert die system time-zone und protocols ospf Abschnitte von Router A (primär, 192.0.2.1) zu Router B (sekundär, 192.0.2.112). Die HTTPS-API von Router B lauscht auf TCP-Port 8443.

Aktivieren und konfigurieren Sie den HTTPS-API-Dienst auf Router B:

set service https listen-address '192.0.2.112'
set service https port '8443'
set service https api keys id primary key 'foo'
set service https api rest

Konfigurieren Sie den Config-Sync-Dienst auf Router A:

set service config-sync mode 'load'
set service config-sync secondary address '192.0.2.112'
set service config-sync secondary port '8443'
set service config-sync secondary key 'foo'
set service config-sync section protocols 'ospf'
set service config-sync section system 'time-zone'

Machen Sie Änderungen auf Router A, die zu einem der synchronisierten Abschnitte gehören. Der Post-Commit-Hook feuert automatisch beim Commit:

vyos@vyos-A# set system time-zone 'America/Los_Angeles'
vyos@vyos-A# commit
INFO:vyos_config_sync:Config synchronization: Mode=load, Secondary=192.0.2.112
vyos@vyos-A# save

vyos@vyos-A# set protocols ospf area 0 network '198.51.100.0/30'
vyos@vyos-A# commit
INFO:vyos_config_sync:Config synchronization: Mode=load, Secondary=192.0.2.112
vyos@vyos-A# save

Jeder Commit auf Router A ändert einen Abschnitt, aber da der Hook alle konfigurierten Abschnitte sendet, sobald einer davon geändert wird, ersetzen beide Commits den vollständigen Zustand von system und protocols ospf auf Router B.

Überprüfen Sie, ob die Änderungen auf Router B angewandt wurden:

vyos@vyos-B:~$ show configuration commands | match time-zone
set system time-zone 'America/Los_Angeles'

vyos@vyos-B:~$ show configuration commands | match ospf
set protocols ospf area 0 network '198.51.100.0/30'
