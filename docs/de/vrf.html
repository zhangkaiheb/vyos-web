VRF

VRF Geräte in Verbindung mit IP-Regeln ermöglichen die Erstellung von virtuellen Routen und Weiterleitungsdomänen (auch VRFs, VRF-Lite im Speziellen) im Linux-Netzwerkstack. Ein Anwendungsfall ist das Problem der Multi-Tenancy, bei dem jeder Mieter über eigene eindeutige Routing-Tabellen verfügt und zumindest unterschiedliche Standard-Gateways benötigt.

Konfiguration

Eine VRF-Gerät wird mit einer zugehörigen Route-Tabelle erstellt. Netzwerkschnittstellen werden dann an ein VRF-Gerät gebunden.

set vrf name <name> table <id>

Erstellt eine neue VRF-Instanz mit <name> und <id>. Der Name wird verwendet, um individuelle Schnittstellen in die VRF einzufügen.

Hinweis

Eine Routing-Tabellen-ID kann nicht geändert werden, nachdem sie zugewiesen wurde. Sie kann nur geändert werden, indem die VRF-Instanz gelöscht und neu hinzugefügt wird.

set vrf bind-to-all

Standardmäßig ist der Umfang der Port-Bindungen für ungebundene Sockets auf die Standard-VRF beschränkt. Das heißt, es wird nicht durch Pakete übereinstimmen, die auf Schnittstellen angemeldet sind, die zu einer VRF gehören, und Prozesse können auf denselben Port binden, wenn sie sich auf eine VRF beziehen.

TCP- und UDP-Dienste, die im Standard-VRF-Kontext laufen (dh nicht an eine VRF-Schnittstelle gebunden), können über alle VRF-Bereiche arbeiten, indem diese Option aktiviert wird.

Zebra/Kernel route filtering

Zebra unterstützt Präfixlisten und Route Maps, um Routen zu filtern, die aus anderen FRR-Komponenten empfangen werden. Die erlaubten/verbotenen Funktionen, die durch diese Befehle bereitgestellt werden, können verwendet werden, um zu filtern, welche Routen Zebra in den Kernel installiert.

set vrf <name> ip protocol <protocol> route-map <route-map>

Anwenden eines Route-Map-Filter auf Routen für das angegebene Protokoll.

Folgende Protokolle können verwendet werden: any, babel, bgp, eigrp, isis, ospf, rip, static

Hinweis

Wenn Sie any als Option wählen, wird dies alle Protokolle bewirken, die Routen an Zebra senden.

set vrf <name> ipv6 protocol <protocol> route-map <route-map>

Anwenden eines Route-Map-Filter auf Routen für das angegebene Protokoll.

Folgende Protokolle können verwendet werden: any, babel, bgp, isis, ospfv3, ripng, static

Hinweis

Wenn Sie any als Option wählen, wird dies alle Protokolle bewirken, die Routen an Zebra senden.

Nexthop Tracking

Nexthop Tracking löst Nexthops standardmäßig über die Standardroute auf. Dies ist standardmäßig für ein traditionelles Profil von FRR aktiviert, das wir verwenden. Es kann deaktiviert werden, wenn Sie z.B. nicht möchten, dass BGP über die Standardroute peert.

set vrf name <name> ip nht no-resolve-via-default

Erlaubt nicht, dass IPv4-Nexthop-Tracking über die Standardroute aufgelöst wird. Dieser Parameter wird pro-VRF konfiguriert, sodass der Befehl auch im VRF-Unterknoten verfügbar ist.

set vrf name <name> ipv6 nht no-resolve-via-default

Erlaubt nicht, dass IPv6-Nexthop-Tracking über die Standardroute aufgelöst wird. Dieser Parameter wird pro-VRF konfiguriert, sodass der Befehl auch im VRF-Unterknoten verfügbar ist.

Schnittstellen

Wenn VRFs verwendet werden, ist es nicht nur erforderlich, eine VRF zu erstellen, sondern die VRF selbst muss auch einer Schnittstelle zugewiesen werden.

set interfaces <dummy | ethernet | bonding | bridge | pppoe> <interface> vrf <name>

Weist die Schnittstelle, die durch <interface> identifiziert wird, der VRF mit dem Namen <name> zu.

Routing

Hinweis

VyOS 1.4 (sagitta) hat dynamisches Routing für VRFs eingeführt.

Derzeit wird dynamisches Routing für folgende Protokolle unterstützt:

  • BGP

  • routing-isis

  • OSPF

  • OSPFv3 (IPv6)

  • Static

Die CLI-Konfiguration ist dieselbe wie in oben genannten Artikeln erwähnt. Der einzige Unterschied besteht darin, dass jedes verwendete Routing-Protokoll mit dem Befehl vrf name <name> präfixiert werden muss.

Beispiel

Die folgenden Befehle sind erforderlich, um Optionen für ein bestimmtes dynamisches Routing-Protokoll innerhalb eines bestimmten VRF festzulegen:

  • BGP: set vrf name <name> protocols bgp ...

  • routing-isis: set vrf name <name> protocols isis ...

  • OSPF: set vrf name <name> protocols ospf ...

  • OSPFv3 (IPv6): set vrf name <name> protocols ospfv3 ...

  • Static: set vrf name <name> protocols static ...

Dienste

Derzeit können folgende Dienste isoliert in VRFs erstellt werden

  • DHCP Server

Die CLI-Konfiguration ist dieselbe wie in oben genannten Artikeln erwähnt. Der einzige Unterschied besteht darin, dass jeder verwendete Dienst mit dem Befehl vrf name <name> präfixiert werden muss.

Beispiel

Die folgenden Befehle sind erforderlich, um Optionen für einen bestimmten Dienst innerhalb eines bestimmten VRF festzulegen:

  • DHCP Server: set vrf name <name> service dhcp-server ...

  • DHCP Server: set vrf name <name> service dhcpv6-server ...

ping <host> vrf <name>

Der ping-Befehl wird verwendet, um zu testen, ob ein Netzwerkhost erreichbar ist oder nicht.

Ping verwendet das obligatorische ECHO_REQUEST-Datagramm des ICMP-Protokolls, um ein ICMP ECHO_RESPONSE von einem Host oder Gateway zu erzeugen. ECHO_REQUEST-Datagramme (Pings) werden einen IP- und ICMP-Header haben, gefolgt von „struct timeval“ und einer beliebigen Anzahl von Füllbytes, um das Paket zu vervollständigen.

Bei der Fehlerisolierung mit ping sollten Sie zunächst auf dem lokalen Host laufen, um sicherzustellen, dass die lokale Netzwerkschnittstelle aktiv und in Betrieb ist. Dann weiter mit Hosts und Gateways weiter unten auf dem Weg zu Ihrem Ziel. Round-trip-Zeit und Paketverluststatistiken werden berechnet.

Doppelte Pakete werden nicht in die Berechnung des Paketverlusts einbezogen, obwohl die Round-trip-Zeit dieser Pakete zur Berechnung der minimalen/average/maximalen Round-trip-Zeit-Werte verwendet wird.

traceroute vrf <name> [ipv4 | ipv6] <host>

Zeigt den Weg an, den Pakete nehmen, um einen Netzwerkhost mit Hilfe der VRF-Instanz zu erreichen, die durch <name> identifiziert wird. Diese Option ist nützlich, wenn der Host als Hostname statt als IP-Adresse angegeben wird.

Verbindet mit einem gegebenen VRF. Dies öffnet eine neue Subshell innerhalb des angegebenen VRF.

Das Prompt wird entsprechend geändert, sowohl in der Konfigurations- als auch in der Betriebsmodus.

vyos@vyos(vrf:blue):~$

Beispiel

VRF Route Leaking

Das folgende Beispiel-Topologie wurde mit EVE-NG erstellt.

  • PC1 befindet sich in der default VRF und fungiert als z.B. „fileserver“

  • PC2 befindet sich in der VRF blue, was der Entwicklungsabteilung entspricht

  • PC3 und PC4 sind an einem Brückengerät auf Router R1 angeschlossen, das in der VRF red ist. Sagen wir, dies ist die HR-Abteilung.

  • R1 wird über ein Out-of-band-Netzwerk verwaltet, das in der VRF mgmt liegt

Konfiguration

set interfaces bridge br10 address '10.30.0.254/24'
set interfaces bridge br10 member interface eth3
set interfaces bridge br10 member interface eth4
set interfaces bridge br10 vrf 'red'

set interfaces ethernet eth0 address 'dhcp'
set interfaces ethernet eth0 vrf 'mgmt'
set interfaces ethernet eth1 address '10.0.0.254/24'
set interfaces ethernet eth2 address '10.20.0.254/24'
set interfaces ethernet eth2 vrf 'blue'

set protocols static route 10.20.0.0/24 interface eth2 vrf 'blue'
set protocols static route 10.30.0.0/24 interface br10 vrf 'red'

set service ssh disable-host-validation
set service ssh vrf 'mgmt'

set system name-server 'eth0'

set vrf name blue protocols static route 10.0.0.0/24 interface eth1 vrf 'default'
set vrf name blue table '3000'
set vrf name mgmt table '1000'
set vrf name red protocols static route 10.0.0.0/24 interface eth1 vrf 'default'
set vrf name red table '2000'

L3VPN VRFs

L3VPN VRFs bgpd supports for IPv4 RFC 4364 and IPv6 RFC 4659. L3VPN routes, and their associated VRF MPLS labels, can be distributed to VPN SAFI neighbors in the default, i.e., non VRF, BGP instance. VRF MPLS labels are reached using core MPLS labels which are distributed using LDP or BGP labeled unicast. bgpd also supports inter-VRF route leaking.

VRF Route Leaking

BGP routes may be leaked (i.e. copied) between a unicast VRF RIB and the VPN SAFI RIB of the default VRF for use in MPLS-based L3VPNs. Unicast routes may also be leaked between any VRFs (including the unicast RIB of the default BGP instance). A shortcut syntax is also available for specifying leaking from one VRF to another VRF using the default instance’s VPN RIB as the intermediary. A common application of the VRF-VRF feature is to connect a customer’s private routing domain to a provider’s VPN service. Leaking is configured from the point of view of an individual VRF: import refers to routes leaked from VPN to a unicast VRF, whereas export refers to routes leaked from a unicast VRF to VPN.

Hinweis

Routes exported from a unicast VRF to the VPN RIB must be augmented by two parameters:

an RD / RTLIST

Configuration for these exported routes must, at a minimum, specify these two parameters.

Konfiguration

Configuration of route leaking between a unicast VRF RIB and the VPN SAFI RIB of the default VRF is accomplished via commands in the context of a VRF address-family.

set vrf name <name> protocols bgp address-family <ipv4-unicast|ipv6-unicast> rd vpn export <asn:nn|address:nn>

Specifies the route distinguisher to be added to a route exported from the current unicast VRF to VPN.

set vrf name <name> protocols bgp address-family <ipv4-unicast|ipv6-unicast> route-target vpn <import|export|both> [RTLIST]

Specifies the route-target list to be attached to a route (export) or the route-target list to match against (import) when exporting/importing between the current unicast VRF and VPN.The RTLIST is a space-separated list of route-targets, which are BGP extended community values as described in Extended Communities Attribute.

set vrf name <name> protocols bgp address-family <ipv4-unicast|ipv6-unicast> label vpn export <0-1048575|auto>

Enables an MPLS label to be attached to a route exported from the current unicast VRF to VPN. If the value specified is auto, the label value is automatically assigned from a pool maintained.

set vrf name <name> protocols bgp address-family <ipv4-unicast|ipv6-unicast> label vpn allocation-mode per-nexthop

Select how labels are allocated in the given VRF. By default, the per-vrf mode is selected, and one label is used for all prefixes from the VRF. The per-nexthop will use a unique label for all prefixes that are reachable via the same nexthop.

set vrf name <name> protocols bgp address-family <ipv4-unicast|ipv6-unicast> route-map vpn <import|export> [route-map <name>]

Specifies an optional route-map to be applied to routes imported or exported between the current unicast VRF and VPN.

set vrf name <name> protocols bgp address-family <ipv4-unicast|ipv6-unicast> <import|export> vpn

Enables import or export of routes between the current unicast VRF and VPN.

set vrf name <name> protocols bgp address-family <ipv4-unicast|ipv6-unicast> import vrf <name>

Shortcut syntax for specifying automatic leaking from vrf VRFNAME to the current VRF using the VPN RIB as intermediary. The RD and RT are auto derived and should not be specified explicitly for either the source or destination VRF’s.

set vrf name <name> protocols bgp address-family <ipv4-unicast|ipv6-unicast> route-map vrf import [route-map <name>]

Specifies an optional route-map to be applied to routes imported from VRFs.

set vrf name <name> protocols bgp interface <interface> mpls forwarding

It is possible to permit BGP install VPN prefixes without transport labels. This configuration will install VPN prefixes originated from an e-bgp session, and with the next-hop directly connected.
