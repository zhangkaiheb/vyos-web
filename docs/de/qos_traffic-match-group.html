Verkehrsrichtlinie

QoS

Der allgemeine Name für Quality of Service oder Traffic Control beinhaltet Dinge wie das Formen des Verkehrs, die Planung oder das Löschen von Paketen, was die Art von Dingen ist, mit denen Sie spielen können, wenn Sie beispielsweise eine Bandbreitenengstelle auf einer Verbindung haben und möchten, dass einige Arten von Verkehr über andere priorisiert werden.

tc ist ein leistungsstarkes Werkzeug für Traffic Control, das im Linux-Kernel gefunden wird. Seine Konfiguration wird jedoch oft als mühsam betrachtet. Glücklicherweise erleichtert VyOS diese Aufgabe durch seine CLI, während es tc als Backend verwendet.

Wie funktioniert es?

Um VyOS Traffic Control funktionieren zu lassen, müssen Sie zwei Schritte befolgen:

  1. Eine Verkehrsrichtlinie erstellen.

  2. Die Verkehrsrichtlinie auf eine Schnittstelle eingang oder ausgehend anwenden.

Bevor Sie lernen, Ihre Richtlinie zu konfigurieren, warnen wir Sie über die verschiedenen Einheiten, die Sie verwenden können, und zeigen Ihnen auch, was Klassen sind und wie sie funktionieren, da einige Richtlinien möglicherweise erforderlich sind, um sie zu konfigurieren.

Einheiten

Bei der Konfiguration Ihrer Verkehrsrichtlinie müssen Sie Datenratenwerte festlegen, achten Sie auf die Einheiten, die Sie verwalten, es ist leicht, sich mit den verschiedenen Präfixen und Suffixen zu verwirren, die Sie verwenden können. VyOS zeigt Ihnen immer die verschiedenen Einheiten an, die Sie verwenden können.

Präfixe

Sie können dezimale Präfixe verwenden.

kbit  (10^3)    Kilobit pro Sekunde
mbit  (10^6)    Megabit pro Sekunde
gbit  (10^9)    Gigabit pro Sekunde
tbit  (10^12)   Terabit pro Sekunde

kbps  (8*10^3)  Kilobyte pro Sekunde
mbps  (8*10^6)  Megabyte pro Sekunde
gbps  (8*10^9)  Gigabyte pro Sekunde
tbps  (8*10^12) Terabyte pro Sekunde

Oder binäre Präfixe.

kibit (2^10 = 1024)    Kibibit pro Sekunde
mibit (2^20 = 1024^2)  Mebibit pro Sekunde
gibit (2^30 = 1024^3)  Gibibit pro Sekunde
tbit  (2^40 = 1024^4)  Tebibit pro Sekunde

kibps (1024*8)         Kibibyte (KiB) pro Sekunde
mibps (1024^2*8)       Mebibyte (MiB) pro Sekunde
gibps (1024^3*8)       Gibibyte (GiB) pro Sekunde
tibps (1024^4*8)       Tebibyte (TiB) pro Sekunde

Suffixe

Ein Bit wird als bit geschrieben,

kbit (Kilobits pro Sekunde)
mbit (Megabits pro Sekunde)
gbit (Gigabits pro Sekunde)
tbit (Terabits pro Sekunde)

während ein Byte als einzelner b geschrieben wird.

kbps (Kilobytes pro Sekunde)
mbps (Megabytes pro Sekunde)
gbps (Gigabytes pro Sekunde)

Klassen

In dem Abschnitt zur Erstellung einer Verkehrsrichtlinie werden Sie sehen, dass einige der Richtlinien Klassen verwenden. Diese Richtlinien ermöglichen es Ihnen, den Verkehr entsprechend verschiedenen Parametern zu verteilen, die Sie wählen können. Eine Klasse ist also einfach eine spezifische Art von Verkehr, den Sie auswählen.

Das endgültige Ziel der Klassifizierung des Verkehrs ist es, jeder Klasse eine unterschiedliche Behandlung zu geben.

Verkehr abgleichen

Um zu definieren, welcher Verkehr in welche Klasse geht, definieren Sie Filter (das heißt, die Übereinstimmungskriterien). Pakete durchlaufen diese Übereinstimmungsregeln (wie die Regeln eines Feuerwalls) und, wenn ein Paket den Filter trifft, wird es dieser Klasse zugeordnet.

In VyOS wird eine Klasse durch eine Nummer identifiziert, die Sie bei der Konfiguration wählen können.

Hinweis

Die Bedeutung der Klassen-ID ist nicht für jede Art von Richtlinie gleich. Normalerweise benötigen Richtlinien nur eine sinnlose Zahl, um eine Klasse (Klassen-ID) zu identifizieren, aber dies gilt nicht für jede Richtlinie. Die Nummer einer Klasse in einer Prioritätswarteschlange identifiziert sie nicht nur, sondern definiert auch ihre Priorität.

set qos policy <policy> <policy-name> class <class-ID> match <class-matching-rule-name>

Im obigen Befehl legen wir den Typ der Richtlinie fest, mit der wir arbeiten, und den Namen, den wir dafür wählen; eine Klasse (damit wir bestimmten Verkehr unterscheiden können) und eine identifizierbare Nummer für diese Klasse; dann konfigurieren wir eine Übereinstimmungsregel (oder einen Filter) und einen Namen dafür.

Eine Klasse kann mehrere Übereinstimmungsfilter haben:

set qos policy shaper MY-SHAPER class 30 match HTTP
set qos policy shaper MY-SHAPER class 30 match HTTPs

Eine Übereinstimmungsregel kann mehrere Kriterien enthalten und passt zum Verkehr, wenn alle diese Kriterien wahr sind.

Zum Beispiel:

set qos policy shaper MY-SHAPER class 30 match HTTP ip protocol tcp
set qos policy shaper MY-SHAPER class 30 match HTTP ip source port 80

Dieser Befehl passt TCP-Verkehr mit Quellport 80.

Es gibt viele Parameter, die Sie verwenden können, um den Verkehr zu matchen, den Sie für eine Klasse wollen:

  • Ethernet (Protokoll, Zieladresse oder Quelladresse)

  • Schnittstellenname

  • IPv4 (DSCP-Wert, maximale Paketlänge, Protokoll, Quelladresse, Zieladresse, Quellport, Zielport oder TCP-Flags)

  • IPv6 (DSCP-Wert, maximale Nutzlastlänge, Protokoll, Quelladresse, Zieladresse, Quellport, Zielport oder TCP-Flags)

  • Firewall-Markierung

  • VLAN-ID

Beim Konfigurieren Ihres Filters können Sie die Tab-Taste verwenden, um die vielen verschiedenen Parameter anzuzeigen, die Sie konfigurieren können.

vyos@vyos# set qos policy shaper MY-SHAPER class 30 match MY-FIRST-FILTER 
Possible completions:
   description  Description
 > ether        Ethernet header match
   interface    Interface to use
 > ip           Match IP protocol header
 > ipv6         Match IPV6 protocol header
   mark         Match on mark applied by firewall
   vif          Virtual Local Area Network (VLAN) ID for this match

Wie in dem Beispiel oben gezeigt, ist eines der Möglichkeiten, Pakete zu matchen, basierend auf Markierungen, die vom Firewall durchgeführt werden, was Ihnen eine große Flexibilität bieten kann.

Sie können auch eine Beschreibung für einen Filter schreiben:

set qos policy shaper MY-SHAPER class 30 match MY-FIRST-FILTER description "My filter description"

Hinweis

Eine IPv4 TCP-Filter wird nur Pakete mit einer IPv4-Header-Länge von 20 Bytes (was die meisten IPv4-Pakete ist) matchen.

Hinweis

IPv6 TCP-Filter passen nur IPv6-Pakete ohne Header-Erweiterung an, siehe https://en.wikipedia.org/wiki/IPv6_packet#Extension_headers

Verkehrs-Match-Gruppe

In einigen Fällen, in denen wir eine Organisation unserer Auswahl von Matches benötigen, um flexibler zu sein und unsere Filterdefinition zu organisieren, können wir Verkehrs-Match-Gruppen anwenden, um uns zu ermöglichen, verschiedene Filtergruppen innerhalb unserer Richtlinie zu erstellen und für jede Gruppe verschiedene Parameter zu definieren:

set qos traffic-match-group <group_name> match <match_name>
Possible completions:
   description          Description
 > ip                   Match IP protocol header
 > ipv6                 Match IPv6 protocol header
   mark                 Match on mark applied by firewall
   vif                  Virtual Local Area Network (VLAN) ID for this match

Erben Sie Matches aus einer anderen Gruppe

set qos traffic-match-group <group_name> match-group <match_group_name>

Eine Match-Gruppe kann mehrere Kriterien enthalten und diese in derselben Richtlinie erben.

Zum Beispiel:

set qos traffic-match-group Mission-Critical match AF31 ip dscp 'AF31'
set qos traffic-match-group Mission-Critical match AF32 ip dscp 'AF42'
set qos traffic-match-group Mission-Critical match CS3 ip dscp 'CS3'
set qos traffic-match-group Streaming-Video match AF11 ip dscp 'AF11'
set qos traffic-match-group Streaming-Video match AF41 ip dscp 'AF41'
set qos traffic-match-group Streaming-Video match AF43 ip dscp 'AF43'
set qos policy shaper VyOS-HTB class 10 bandwidth '30%'
set qos policy shaper VyOS-HTB class 10 description 'Multimedia'
set qos policy shaper VyOS-HTB class 10 match CS4 ip dscp 'CS4'
set qos policy shaper VyOS-HTB class 10 match-group 'Streaming-Video'
set qos policy shaper VyOS-HTB class 10 priority '1'
set qos policy shaper VyOS-HTB class 10 queue-type 'fair-queue'
set qos policy shaper VyOS-HTB class 20 description 'MC'
set qos policy shaper VyOS-HTB class 20 match-group 'Mission-Critical'
set qos policy shaper VyOS-HTB class 20 priority '2'
set qos policy shaper VyOS-HTB class 20 queue-type 'fair-queue'
set qos policy shaper VyOS-HTB default bandwidth '20%'
set qos policy shaper VyOS-HTB default queue-type 'fq-codel'

In diesem Beispiel können wir beobachten, dass verschiedene DSCP-Kriterien basierend auf unserer QoS-Konfiguration innerhalb der gleichen Richtliniengruppe definiert werden.

Standard

Wenn Sie oft auch Ihre Standard-Verkehrsrichtlinie konfigurieren müssen, so wie Sie es mit einer Klasse tun. Standard kann als Klasse betrachtet werden, da es sich so verhält. Es enthält jeden Verkehr, der keine der definierten Klassen getroffen hat, also ist es wie eine offene Klasse, eine Klasse ohne Matching-Filter.

Klassen-Behandlung

Einrichtung einer Richtlinie in eine andere Richtlinie

Oft brauchen wir es, eine Richtlinie in eine andere Richtlinie einzubauen. Es ist möglich, dies auf klassenbasierten Richtlinien zu tun, indem man eine neue Richtlinie in eine Klasse anhängt. Zum Beispiel könnten Sie verschiedene Richtlinien auf die verschiedenen Klassen einer Round-Robin-Richtlinie anwenden, die Sie konfiguriert haben.

Eine häufige Anwendung ist der Fall, bei dem einige Richtlinien, um effektiv zu sein, auf eine Schnittstelle angewandt werden müssen, die direkt verbunden ist, wo die Engstelle ist. Wenn Ihr Router nicht direkt an die Engstelle angeschlossen ist, sondern ein Hop vorher, können Sie die Engstelle simulieren, indem Sie Ihre nicht-formende Richtlinie in eine klassenbasierte formende Richtlinie einbetten, damit sie wirkt.

Sie können eine Richtlinie in eine Klasse durch die queue-type-Einstellung konfigurieren.

set qos policy shaper FQ-SHAPER bandwidth 4gbit
set qos policy shaper FQ-SHAPER default bandwidth 100%
set qos policy shaper FQ-SHAPER default queue-type fq-codel

Wie in dem letzten Befehl des Beispiels oben gezeigt, ermöglicht die queue-type-Einstellung diese Kombinationen. Sie können sie in vielen Richtlinien verwenden.

Hinweis

Einige Richtlinien beinhalten bereits andere eingebettete Richtlinien. Das ist der Fall bei Shaper: Jede seiner Klassen verwendet fair-queue, es sei denn, Sie ändern es.

Erstellung einer Verkehrsrichtlinie

VyOS ermöglicht es Ihnen, den Verkehr auf viele verschiedene Weisen zu kontrollieren, hier werden wir jede Möglichkeit behandeln. Sie können so viele Richtlinien konfigurieren, wie Sie wollen, aber Sie können nur eine Richtlinie pro Schnittstelle und Richtung (eingehend oder ausgehend) anwenden.

Einige Richtlinien können kombiniert werden, Sie können eine andere Richtlinie konfigurieren, die auf eine Klasse der Hauptrichtlinie angewandt wird.

Hinweis

Wenn Sie nach einer Richtlinie für Ihren ausgehenden Verkehr suchen aber Sie wissen nicht, welche Sie benötigen und möchten nicht durch jede mögliche Richtlinie gehen, die hier gezeigt wird, unsere Wette ist, dass Sie wahrscheinlich eine Shaper Richtlinie suchen und Sie Ihre Warteschlangen einstellen möchten als FQ-CoDel.

Drop Tail

Warteschlange Disziplin: PFIFO (Packet First In First Out).
Wird angewandt auf: Ausgehender Verkehr.

Dies ist die einfachste Warteschlange, die Sie auf Ihren Verkehr anwenden können. Der Verkehr muss eine endliche Warteschlange durchlaufen, bevor er tatsächlich gesendet wird. Sie müssen definieren, wie viele Pakete diese Warteschlange enthalten kann.

Wenn ein Paket gesendet werden muss, muss es durch diese Warteschlange gehen, also wird das Paket an das Ende gestellt. Wenn das Paket vollständig durch diese Warteschlange gegangen ist, wird es aus der Warteschlange entfernt und wird schließlich an die NIC weitergegeben, um tatsächlich gesendet zu werden.

Trotzdem, dass die Drop-Tail-Richtlinie keine Pakete verlangsamt, können viele Pakete abgewiesen werden, wenn sie versuchen, am Ende der Warteschlange eingeordnet zu werden. Dies kann passieren, wenn die Warteschlange noch nicht genug Pakete aus ihrem Kopf freigegeben hat.

Diese Richtlinie benötigt die geringsten Ressourcen für denselben Verkehr. Aber sehr wahrscheinlich benötigen Sie es nicht, da Sie nicht viel davon bekommen können. Manchmal wird es nur verwendet, um Logging zu ermöglichen.

set qos policy drop-tail <policy-name> queue-limit <number-of-packets>

Verwenden Sie diesen Befehl, um eine Drop-Tail-Richtlinie (PFIFO) zu konfigurieren. Wählen Sie einen eindeutigen Namen für diese Richtlinie und die Größe der Warteschlange, indem Sie die Anzahl der Pakete festlegen, die sie enthalten kann (maximal 4294967295).

Fair Queue

Warteschlange Disziplin: SFQ (Stochastic Fairness Queuing).
Wird angewandt auf: Ausgehender Verkehr.

Fair Queue ist ein work-conserving Scheduler, der die Übertragung von Paketen auf Basis von Flows plant, das heißt, es balanciert den Verkehr, indem es ihn über verschiedene Unterklassen verteilt, um Gerechtigkeit sicherzustellen, sodass jeder Flow in der Lage ist, Daten nacheinander zu senden, und verhindert, dass ein einzelner Flow den Rest übertönt.

set qos policy fair-queue <policy-name>

Verwenden Sie diesen Befehl, um eine Fair-Queue-Richtlinie zu erstellen und ihr einen Namen zu geben. Sie basiert auf dem Stochastic Fairness Queueing und kann auf ausgehenden Verkehr angewandt werden.

Um den Verkehr zu trennen, verwendet Fair Queue einen Classifier, der auf Quelladresse, Zieladresse und Quellport basiert. Das Algorithmus fügt Pakete basierend auf diesen drei Parametern in Hash-Buckets ein. Jeder dieser Buckets sollte einen eindeutigen Flow darstellen. Da mehrere Flows möglicherweise in denselben Bucket hashen, wird das Hashingalgorithmus zu konfigurierbaren Intervallen gestört, sodass die Unfairness nur für kurze Zeit besteht. Die Störung kann jedoch zu unabsichtlicher Paketumordnung führen. Ein empfehlenswerter Wert könnte 10 Sekunden sein.

Eine der Verwendungen von Fair Queue könnte die Minderung von Denial-of-Service-Angriffen sein.

set qos policy fair-queue <policy-name> hash-interval <seconds>

Verwenden Sie diesen Befehl, um eine Fair-Queue-Richtlinie zu definieren, basierend auf dem Stochastic Fairness Queueing, und setzen Sie die Anzahl der Sekunden, zu denen ein neues Warteschlange-Algorithmen-Störung stattfinden wird (maximal 4294967295).

Beim Entfernen aus der Warteschlange wird jede Hash-Bucket mit Daten in einem Round-Robin-Verfahren abgefragt. Sie können die Länge der Warteschlange konfigurieren.

set qos policy fair-queue <policy-name> queue-limit <limit>

Verwenden Sie diesen Befehl, um eine Fair-Queue-Richtlinie zu definieren, basierend auf dem Stochastic Fairness Queueing, und setzen Sie die maximale Anzahl der Pakete, die in der Warteschlange warten dürfen. Jedes weitere Paket wird abgewiesen.

Hinweis

Fair Queue ist eine nicht-formende (work-conserving) Richtlinie, also wird sie nur dann nützlich sein, wenn Ihr ausgehender Schnittstelle wirklich voll ist. Wenn nicht, wird VyOS die Warteschlange nicht besitzen und Fair Queue wird keine Wirkung haben. Wenn es Bandbreite auf dem physischen Link gibt, können Sie Fair-Queue in eine klassenbasierte formende Richtlinie einbetten, um sicherzustellen, dass sie die Warteschlange besitzt.

FQ-CoDel

Warteschlange Disziplin: Fair/Flow Queue CoDel.
Wird angewandt auf: Ausgehender Verkehr.

Die FQ-CoDel-Richtlinie verteilt den Verkehr in 1024 FIFO-Warteschlangen und versucht, gute Dienste zwischen allen von ihnen zu gewährleisten. Sie versucht auch, die Länge aller Warteschlangen kurz zu halten.

FQ-CoDel kämpft gegen Bufferbloat und reduziert die Latenz, ohne komplexe Konfigurationen zu benötigen. Es ist zur neuen Standard-Warteschlange Disciplin für die Schnittstellen einiger GNU/Linux-Distributionen geworden.

Es verwendet ein stochastisches Modell, um ankommende Pakete in verschiedene Flows zu klassifizieren und bietet allen Flows, die die Warteschlange nutzen, einen fairen Anteil an der Bandbreite. Jeder Flow wird von der CoDel-Warteschlange verwaltet. Paketumordnung innerhalb eines Flows wird vermieden, da Codel intern eine FIFO-Warteschlange verwendet.

FQ-CoDel basiert auf einem modifizierten Deficit Round Robin (DRR)-Warteschlange-Scheduler mit dem CoDel Active Queue Management (AQM)-Algorithmus, der auf jeder Warteschlange operiert.

Hinweis

FQ-Codel ist eine nicht-formende (work-conserving) Richtlinie, also wird sie nur dann nützlich sein, wenn Ihr ausgehender Schnittstelle wirklich voll ist. Wenn nicht, wird VyOS die Warteschlange nicht besitzen und FQ-Codel wird keine Wirkung haben. Wenn es Bandbreite auf dem physischen Link gibt, können Sie FQ-Codel in eine klassenbasierte formende Richtlinie einbetten, um sicherzustellen, dass sie die Warteschlange besitzt. Wenn Sie sich nicht sicher sind, ob Sie Ihre FQ-CoDel-Richtlinie in einen Shaper einbetten müssen, tun Sie es.

FQ-CoDel ist für 10Gbit-Geschwindigkeiten mit seinen Standardparametern gut geeignet. Es könnte auch bei anderen Geschwindigkeiten ohne Konfiguration gut funktionieren, aber hier erklären wir einige Fälle, in denen Sie seine Parameter anpassen möchten.

Wenn Sie es bei 1Gbit und niedrigerer Geschwindigkeit laufen lassen, möchten Sie vielleicht die queue-limit auf 1000 Pakete oder weniger reduzieren. Bei Geschwindigkeiten wie 10Mbit möchten Sie sie auf 600 Pakete setzen.

Wenn Sie FQ-CoDel in Shaper einbetten und hohe Geschwindigkeiten (100Mbit und höher) haben, können Sie den quantum auf 8000 oder höher erhöhen, damit der Scheduler CPU spart.

Auf niedrigen Geschwindigkeiten (unter 40Mbit) möchten Sie den quantum auf etwas wie 300 Byte heruntersetzen.

Bei sehr niedrigen Geschwindigkeiten (unter 3Mbit) möchten Sie neben der Anpassung des quantum (300 bleibt gut) auch den target auf etwas wie 15ms erhöhen und den interval auf etwa 150 ms erhöhen.

set qos policy fq-codel <policy name> codel-quantum <bytes>

Verwenden Sie diesen Befehl, um eine fq-codel-Richtlinie zu konfigurieren, ihren Namen festzulegen und die maximale Anzahl von Bytes (Standard: 1514) festzulegen, die aus einer Warteschlange gleichzeitig dekodiert werden.

set qos policy fq-codel <policy name> flows <number-of-flows>

Verwenden Sie diesen Befehl, um eine fq-codel-Richtlinie zu konfigurieren, ihren Namen festzulegen und die Anzahl der Unter-Warteschlangen (Standard: 1024), in die Pakete klassifiziert werden.

set qos policy fq-codel <policy name> interval <milliseconds>

Verwenden Sie diesen Befehl, um eine fq-codel-Richtlinie zu konfigurieren, ihren Namen festzulegen und die Zeitspanne, die vom CoDel-Steuerungsloop verwendet wird, um zu erkennen, wann eine persistente Warteschlange entwickelt wird, sicherzustellen, dass die gemessene minimale Verzögerung nicht zu alt wird (Standard: 100ms).

set qos policy fq-codel <policy-name> queue-limit <number-of-packets>

Verwenden Sie diesen Befehl, um eine fq-codel-Richtlinie zu konfigurieren, ihren Namen festzulegen und eine feste Grenze für die tatsächliche Warteschlange festzulegen. Wenn diese Grenze erreicht wird, werden neue Pakete abgewiesen (Standard: 10240 Pakete).

set qos policy fq-codel <policy-name> target <milliseconds>

Verwenden Sie diesen Befehl, um eine fq-codel-Richtlinie zu konfigurieren, ihren Namen festzulegen und die akzeptable minimale stehende/persistente Warteschlange Verzögerung festzulegen. Diese minimale Verzögerung wird identifiziert, indem der lokale Mindestverzögerungswert erfasst wird, den Pakete erfahren (Standard: 5ms).

Beispiel

Ein einfaches Beispiel für eine FQ-CoDel-Richtlinie, die innerhalb einer Shaper-Richtlinie funktioniert.

set qos policy shaper FQ-CODEL-SHAPER bandwidth 2gbit
set qos policy shaper FQ-CODEL-SHAPER default bandwidth 100%
set qos policy shaper FQ-CODEL-SHAPER default queue-type fq-codel

Limiter

Warteschlange Disziplin: Eingangspolicer.
Wird angewandt auf: Eingehender Verkehr.

Limiter ist eine solche Richtlinie, die Klassen verwendet (Eingang qdisc ist eigentlich eine klassenlose Richtlinie, aber Filter funktionieren darin).

Der Limiter führt grundlegende Eingangspolicing von Verkehrsflüssen durch. Mehrere Klassen von Verkehr können definiert werden und Verkehrsbeschränkungen können auf jede Klasse angewandt werden. Obwohl der Policer ein Token-Bucket-Mechanismus intern verwendet, hat er nicht die Fähigkeit, ein Paket zu verzögern, wie es ein Formungsmechanismus tut. Verkehr, der die definierten Bandbreitenbegrenzungen überschreitet, wird direkt abgewiesen. Auch eine maximale erlaubte Burst kann konfiguriert werden.

Sie können Klassen (bis zu 4090) mit unterschiedlichen Einstellungen und eine Standardrichtlinie konfigurieren, die auf jeden Verkehr angewandt wird, der keine der konfigurierten Klassen trifft.

Hinweis

Wenn Sie eine Formung für Ihren eingehenden Verkehr anwenden möchten, prüfen Sie den Abschnitt zu Eingangsschaltung.

set qos policy limiter <policy-name> class <class ID> match <match-name> description <description>

Verwenden Sie diesen Befehl, um einen Eingangspolicer zu konfigurieren, seinen Namen festzulegen, eine Klassen-ID (1-4090), einen Klassen-Überprüfungsnamen und seine Beschreibung.

Wenn die Übereinstimmungsregeln für eine Klasse festgelegt sind, können Sie beginnen, wie Sie das übereinstimmende Verkehrsverhalten konfigurieren möchten.

set qos policy limiter <policy-name> class <class-ID> bandwidth <rate>

Verwenden Sie diesen Befehl, um einen Eingangspolicer zu konfigurieren, seinen Namen festzulegen, eine Klassen-ID (1-4090) und die maximale erlaubte Bandbreite für diese Klasse.

set qos policy limiter <policy-name> class <class-ID> burst <burst-size>
