Tunnel

Tunnel-Schnittstellen sind virtuelle Verbindungen, die verschlüsselten Datenverkehr zwischen privaten Netzwerken oder Hosts über öffentliche Infrastruktur, wie das Internet, übertragen. Sie verwenden Verschlüsselungsprotokolle, um den ursprünglichen Datenverkehr für die Übertragung zu verpacken. Die unterstützten Protokolle umfassen GRE, IPIP, IPIP6, IP6IP6 und 6in4 (SIT).

Obwohl GRE aufgrund seiner Vielseitigkeit oft die bevorzugte Lösung ist, können andere Verschlüsselungsprotokolle für bestimmte Anwendungsfälle besser geeignet sein.

VyOS verwendet eine einzige Tunnel-Schnittstelltabelle für alle diese Protokolle. Es gibt keine separaten GRE, IPIP oder IP6IP6-Schnittstellen; stattdessen wird das gewünschte Verschlüsselungsprotokoll innerhalb der Konfiguration set interfaces tunnel ausgewählt.

Konfigurationsoptionen für jedes Protokoll werden unten beschrieben.

Warnung

Ändern Sie nicht den Verschlüsselungstyp für bereits konfigurierte Tunnel-Schnittstellen, da dies deren abhängige Konfigurationen beeinträchtigen könnte.

Gemeinsame Schnittstellenkonfiguration

set interfaces tunnel <interface> address <address>

Konfigurieren Sie eine oder mehrere Schnittstellen-IP-Adressen.

<address> unterstützt IPv4 und IPv6 in CIDR-Schreibweise. Zum Beispiel verwenden Sie 192.0.2.1/24 für IPv4 oder 2001:db8::1/64 für IPv6.

Beispiel:

set interfaces tunnel tun0 address 192.0.2.1/24
set interfaces tunnel tun0 address 2001:db8::1/64
set interfaces tunnel <interface> description <description>

Konfigurieren Sie ein klares, beschreibendes Alias für die Schnittstelle.

Dieses Alias erscheint im Befehl show interfaces und in SNMP-basierten Überwachungstools.

Beispiel:

set interfaces tunnel tun0 description 'This is an interface running on VyOS.'
set interfaces tunnel <interface> disable

Schalten Sie die Schnittstelle aus.

Die Schnittstelle wird auf den administrativ heruntergefahrenen Zustand (A/D) gesetzt.

Beispiel:

set interfaces tunnel tun0 disable
set interfaces tunnel <interface> disable-flow-control

Deaktivieren Sie die Ethernet-Flusssteuerung (IEEE 802.3x Pause Frames) auf der Schnittstelle.

Die Ethernet-Flusssteuerung, definiert durch das IEEE 802.3x-Standard, unterbricht vorübergehend die Datenübertragung, um Paketverluste während der Netzwerkbelastung zu vermeiden. Zum Beispiel, wenn ein Sender Daten schneller überträgt, als der Empfänger verarbeiten kann.

Das Deaktivieren der Ethernet-Flusssteuerung bedeutet, dass die Schnittstelle kein Signal an das verbundene Gerät sendet, um die Übertragung zu pausieren, und Pakete abwirft, wenn sie überfordert ist.

Beispiel:

set interfaces tunnel tun0 disable-flow-control
set interfaces tunnel <interface> disable-link-detect

Deaktivieren Sie die Erkennung physischer Link-Zustandsänderungen auf der Schnittstelle, z. B. wenn ein Kabel entfernt wird.

Standardmäßig erkennt die Schnittstelle physische Link-Zustandsänderungen.

Beispiel:

set interfaces tunnel tun0 disable-link-detect
set interfaces tunnel <interface> mtu <mtu>

Konfigurieren Sie das MTU auf der Schnittstelle.

Der Wert definiert die größte Paketgröße in Bytes, die die Schnittstelle ohne Fragmentierung überträgt.

Beispiel:

set interfaces tunnel tun0 mtu 1600
set interfaces tunnel <interface> ip adjust-mss <mss | clamp-mss-to-pmtu>

Konfigurieren Sie den MSS , der in ausgehenden TCP SYN-Paketen auf der angegebenen Schnittstelle angegeben wird.

Durch das Begrenzen des MSS-Werts in TCP SYN-Paketen informieren Sie den Remote-Partner explizit, dass keine Pakete größer als dieser Wert gesendet werden sollen. Dies verhindert Verbindungsprobleme, die auftreten, wenn die Pfad-MTU-Erkennung (PMTUD) fehlschlägt.

Die folgenden Optionen sind verfügbar:

  • mss: Legt den MSS auf einen spezifischen Wert in Bytes fest. Nutzen Sie diese Option, wenn Sie einen spezifischen MSS erzwingen müssen, z. B. zur Fehlerbehebung von Verbindungsproblemen oder zur Berücksichtigung spezifischer Netzwerkanforderungen.

  • clamp-mss-to-pmtu: Der Router berechnet den MSS automatisch als den MTU der Schnittstelle minus 40 Bytes für IPv4-Datenverkehr (20 Bytes für den IPv4-Header und 20 Bytes für den TCP-Header). Diese Option wird empfohlen, um den richtigen Wert automatisch zu setzen.

set interfaces tunnel <interface> ip arp-cache-timeout

Konfigurieren Sie, wie lange ein ARP-Eintrag gültig bleibt, nachdem eine IP-zu-MAC-Adresse-Zuordnung auf dieser Schnittstelle gelernt wurde.

Die Standarddauer beträgt 30 Sekunden.

Eine ARP-Eintrag bleibt gültig, wenn er positive Rückmeldungen von höheren Protokollen erhält.

Beispiel:

set interfaces tunnel tun0 ip arp-cache-timeout 180
set interfaces tunnel <interface> ip disable-arp-filter

Konfigurieren Sie die ARP-Filterung auf dieser Schnittstelle.

Standardverhalten: Das Kernel antwortet auf ARP-Anfragen auf dieser Schnittstelle nur dann, wenn der Datenverkehr über diese spezifische Schnittstelle zurück zum ARP-Sender gerichtet wird.

Wenn konfiguriert: Das Kernel antwortet auf ARP-Anfragen auf dieser Schnittstelle für jede IP-Adresse, die auf dem lokalen Host konfiguriert ist, unabhängig davon, welche spezifische Schnittstelle diese IP-Adresse zugewiesen ist, und unabhängig vom Routing-Tabellen. Dies spiegelt das Linux-Konzept wider, dass IP-Adressen dem Host gehören, nicht einzelnen Schnittstellen.

Beispiel:

set interfaces tunnel tun0 ip disable-arp-filter
set interfaces tunnel <interface> ip disable-forwarding

Konfigurieren Sie die Schnittstelle für Host- oder Router-Verhalten.

Wenn konfiguriert, wechselt die Schnittstelle in Hostmodus, und IPv4-Weiterleitung wird auf ihr deaktiviert.

Beispiel:

set interfaces tunnel tun0 ip disable-forwarding
set interfaces tunnel <interface> ip enable-directed-broadcast

Konfigurieren Sie, ob IP-gerichtete Broadcast-Pakete, die auf dieser Schnittstelle empfangen werden, weitergeleitet werden.

Standardverhalten: IP-gerichtete Broadcast-Pakete werden abgeworfen.

Wenn konfiguriert: IP-gerichtete Broadcast-Pakete werden an alle Hosts auf dem Ziel-Subnetz weitergeleitet, wie in RFC 1812 und RFC 2644 definiert.

Beispiel:

set interfaces tunnel tun0 ip enable-directed-broadcast
set interfaces tunnel <interface> ip enable-arp-accept

Konfigurieren Sie, wie mit kostenlosen ARPs auf dieser Schnittstelle umgegangen wird.

Wenn konfiguriert, wird eine IP-zu-MAC-Zuordnung basierend auf kostenlosen ARP-Anfragen oder Antworten in die ARP-Tabelle eingefügt.

Hinweis

Wenn die ARP-Tabelle bereits eine IP-Adresse aus einem kostenlosen ARP enthält, wird der Eintrag aktualisiert, unabhängig davon, ob diese Einstellung konfiguriert ist.

Beispiel:

set interfaces tunnel tun0 ip enable-arp-accept
set interfaces tunnel <interface> ip enable-arp-announce

Konfigurieren Sie die Quell-IP-Auswahl für ARP-Anfragen auf dieser Schnittstelle.

Standardverhalten: Das Kernel kann jede IP-Adresse verwenden, die der Host besitzt, als Quell-IP-Adresse in ARP-Anfragen auf dieser Schnittstelle.

Wenn konfiguriert: Das Kernel versucht zunächst, eine Quell-IP-Adresse zu wählen, die auf der Schnittstelle konfiguriert ist und eine gemeinsame Subnetz mit der Ziel-IP-Adresse hat. Wenn es keine solche Subnetz gibt, wählt das Kernel die IP-Adresse aus, die es normalerweise verwenden würde (basierend auf der Routing-Tabelle, um das Zielziel zu erreichen).

Beispiel:

set interfaces tunnel tun0 ip enable-arp-announce
set interfaces tunnel <interface> ip enable-arp-ignore

Konfigurieren Sie, welche ARP-Anfragen auf dieser Schnittstelle ignoriert werden.

Standardverhalten: Das Kernel antwortet auf ARP-Anfragen für beliebige lokale IP-Adressen, unabhängig davon, welcher Schnittstelle sie zugewiesen sind.

Wenn konfiguriert: Das Kernel antwortet nur auf ARP-Anfragen, wenn die Ziel-IP-Adresse dieser spezifischen Schnittstelle zugewiesen ist.

Beispiel:

set interfaces tunnel tun0 ip enable-arp-ignore
set interfaces tunnel <interface> ip enable-proxy-arp

Konfigurieren Sie Proxy-ARP auf dieser Schnittstelle.

Wenn konfiguriert, greift der Router (Kernel) auf ARP-Anfragen für nicht lokale IP-Adressen zu und antwortet mit der MAC-Adresse der Schnittstelle, die die Anfrage empfangen hat. Danach werden Pakete, die an diese IP-Adressen gerichtet sind, an ihre tatsächlichen Ziele auf entfernten Subnetzen weitergeleitet.

Beispiel:

set interfaces tunnel tun0 ip enable-proxy-arp
set interfaces tunnel <interface> ip proxy-arp-pvlan

Konfigurieren Sie lokale Proxy-ARP auf der Schnittstelle.

Wenn konfiguriert, antwortet der Router (Kernel) auf ARP-Anfragen auf dieser VLAN-Schnittstelle, auch wenn die Ziel-IP-Adresse auf dem gleichen Subnetz und der gleichen Schnittstelle liegt.

Dies wird verwendet, um Netzwerkisolationsanforderungen (RFC 3069) für private VLANs (PVLANs) zu unterstützen. In PVLAN-Konfigurationen dürfen Hosts auf isolierten Ports nicht direkt miteinander kommunizieren, aber sie können mit dem Upstream-Router kommunizieren.

Durch die Antwort auf interne ARP-Anfragen mit ihrer eigenen MAC-Adresse leitet der Router den inter-HOST-Datenverkehr durch sich selbst anstatt direkt zwischen Hosts.

Hinweis

Dieser Befehl funktioniert unabhängig und erfordert nicht, dass der Standard-Proxy-ARP auf der Schnittstelle aktiviert wird.

Lokaler Proxy-ARP ist auch bekannt als:

  • VLAN-Aggregation (RFC 3069).

  • Private VLAN (Cisco, Allied Telesyn).

  • Quellport-Filterung oder Port-Isolation (Hewlett-Packard).

  • MAC-Forced Forwarding (Ericsson).

set interfaces tunnel <interface> ip source-validation <strict | loose | disable>

Konfigurieren Sie die Quell-IP-Adressen-Überprüfung mit RPF auf dieser Schnittstelle, wie in RFC 3704 angegeben.

Die folgenden Optionen sind verfügbar:

  • strict: Jedes ankommende Paket wird auf seine Quell-IP-Adresse gegen die Forwarding Information Base (FIB) geprüft. Wenn die Schnittstelle nicht der beste Weg zurück zu dieser Quelle ist, schlägt die Validierung fehl und das Paket wird abgeworfen.

  • loose: Jedes ankommende Paket wird auf seine Quell-IP-Adresse gegen die FIB geprüft. Wenn die Quell-IP-Adresse durch irgendeine Schnittstelle nicht erreichbar ist, schlägt die Validierung fehl.

  • disable: Keine Quell-IP-Adressen-Überprüfung wird durchgeführt. Alle ankommenden Pakete werden akzeptiert.

RFC 3704 empfiehlt, den strengen Modus zu aktivieren, um IP-Spoofing, wie DDoS-Angriffe, zu verhindern. Für asynchrone oder komplexe Routing-Szenarien verwenden Sie den lockeren Modus.

set interfaces tunnel <interface> ipv6 address autoconf

Konfigurieren Sie die Schnittstelle, um automatisch eine IPv6-Adresse mit SLAAC, zu erhalten, wie in RFC 4862 festgelegt.

IPv6-Hosts können sich automatisch konfigurieren, wenn sie sich einem IPv6-Netzwerk anschließen, indem sie das Neighbor Discovery Protocol über ICMPv6-Router-Discovery-Nachrichten verwenden. Bei der ersten Verbindung zu einem Netzwerk sendet ein Host eine Link-Local-Router-Solicitation-Multicast-Anfrage für seine Konfigurationsparameter. Der Router antwortet mit einer Router-Advertisement-Paket, das Internet-Layer-Konfigurationsparameter enthält.

Hinweis

Diese Methode deaktiviert automatisch die IPv6-Verkehrsweiterleitung auf der Schnittstelle.

Beispiel:

set interfaces tunnel tun0 ipv6 address autoconf
set interfaces tunnel <interface> ipv6 address eui64 <prefix>

Konfigurieren Sie die Schnittstelle, um sich selbst eine IPv6-Adresse mit dem EUI-64 -Methode zu zuweisen, wie in RFC 4291 festgelegt.

Beispiel:

set interfaces tunnel tun0 ipv6 address eui64 2001:db8:beef::/64
set interfaces tunnel <interface> ipv6 address no-default-link-local

Deaktivieren Sie die automatische Zuweisung einer link-lokalen IPv6-Adresse zu dieser Schnittstelle.

Beispiel:

set interfaces tunnel tun0 ipv6 address no-default-link-local
set interfaces tunnel <interface> ipv6 disable-forwarding

Konfigurieren Sie die Schnittstelle für Host- oder Router-Verhalten.

Wenn konfiguriert, wechselt die Schnittstelle in Hostmodus, und IPv6-Weiterleitung wird auf ihr deaktiviert.

Beispiel:

set interfaces tunnel tun0 ipv6 disable-forwarding
set interfaces tunnel <interface> ipv6 adjust-mss <mss | clamp-mss-to-pmtu>

Konfigurieren Sie den MSS , der in ausgehenden TCP SYN-Paketen auf der angegebenen Schnittstelle angegeben wird.

Durch das Begrenzen des MSS-Werts in TCP SYN-Paketen informieren Sie den Remote-Partner explizit, dass keine Pakete größer als dieser Wert gesendet werden sollen. Dies verhindert Verbindungsprobleme, die auftreten, wenn die Pfad-MTU-Erkennung (PMTUD) fehlschlägt.

Die folgenden Optionen sind verfügbar:

  • mss: Setzt den MSS auf einen spezifischen Wert in Bytes. Nutzen Sie diese Option, um einen spezifischen MSS zu erzwingen, z. B. zur Fehlerbehebung von Verbindungsproblemen oder zur Berücksichtigung spezifischer Netzwerkbedürfnisse.

  • clamp-mss-to-pmtu: Der Router berechnet den MSS als den MTU der Schnittstelle minus 60 Bytes für IPv6-Datenverkehr (40 Bytes für den IPv6-Header und 20 Bytes für den TCP-Header). Diese Option wird empfohlen, um den richtigen Wert automatisch zu setzen.

set interfaces tunnel <interface> ipv6 accept-dad <0 | 1 | 2>

Konfigurieren Sie IPv6 DAD auf der Schnittstelle.

Die folgenden Optionen sind verfügbar:

  • 0: Deaktiviert DAD. Es wird keine Duplicate Address Detection durchgeführt.

  • 1: Aktiviert DAD (Standard). Duplicate Addresses werden erkannt. Die IPv6-Operation der Schnittstelle wird für gültige IPv6-Adressen fortgesetzt.

  • 2: Aktiviert DAD und, falls eine MAC-basierte doppelte Link-Local-Adresse gefunden wird, deaktiviert IPv6-Operation auf dieser Schnittstelle.

Beispiel:

set interfaces tunnel tun0 ipv6 accept-dad 2
set interfaces tunnel <interface> ipv6 dup-addr-detect-transmits <n>

Konfigurieren Sie die Anzahl der DAD -Nachrichten, die der Router (Kernel) während der IPv6-Adresszuweisung auf dieser Schnittstelle sendet.

Der Standardwert ist 1.

Beispiel:

set interfaces tunnel tun0 ipv6 dup-addr-detect-transmits 5
set interfaces tunnel <interface> vrf <vrf>

Weisen Sie die Schnittstelle einem spezifischen VRF Instanz zu.

Siehe auch

Für Informationen zur Konfiguration eines VRF, siehe den VRF-Abschnitt.

Beispiel:

set interfaces tunnel tun0 vrf red

IPIP

IPIP ist ein einfaches Verschlüsselungsprotokoll, das in RFC 2003 definiert ist. Es umschließt ein IPv4-Paket innerhalb eines anderen IPv4-Pakets.

Tunnels mit IPIP-Verschlüsselung haben keine protokollspezifischen Konfigurationsoptionen, außer dass der Verschlüsselungstyp als IPIP explizit definiert wird (siehe das Beispiel unten).

Beispiel:

set interfaces tunnel tun0 encapsulation ipip
set interfaces tunnel tun0 source-address 192.0.2.10
set interfaces tunnel tun0 remote 203.0.113.20
set interfaces tunnel tun0 address 192.168.100.200/24

IP6IP6

IP6IP6 ist das IPv6-Entgegengesetzte zu IPIP. Es umschließt ein IPv6-Paket innerhalb eines anderen IPv6-Pakets.

Ähnlich wie bei ihren IPIP-Gegenstücken haben Tunnels mit IP6IP6-Verschlüsselung keine protokollspezifischen Konfigurationsoptionen, außer dass der Verschlüsselungstyp als IP6IP6 explizit definiert wird.

Beispiel:

set interfaces tunnel tun0 encapsulation ip6ip6
set interfaces tunnel tun0 source-address 2001:db8:aa::1
set interfaces tunnel tun0 remote 2001:db8:aa::2
set interfaces tunnel tun0 address 2001:db8:bb::1/64

IPIP6

IPIP6 ist ein Verschlüsselungsprotokoll, das IPv4-Pakete in IPv6-Pakete einwickelt.

Ähnlich wie IPIP und IP6IP6 benötigt die Konfiguration für Tunnels mit IPIP6-Verschlüsselung nur die Definition des Verschlüsselungstyps als IP6IP6.

Beispiel:

set interfaces tunnel tun0 encapsulation ipip6
set interfaces tunnel tun0 source-address 2001:db8:aa::1
set interfaces tunnel tun0 remote 2001:db8:aa::2
set interfaces tunnel tun0 address 192.168.70.80/24

6in4 (SIT)

6in4, auch bekannt als SIT, ist ein Verschlüsselungsprotokoll, das in RFC 4213 definiert ist, das IPv6-Pakete in IPv4-Pakete einwickelt. Die umschließenden IPv4-Header verwenden die IP-Protokollnummer 41, die ausschließlich für IPv6-Verschlüsselung reserviert ist.

Der Verschlüsselungsprozess fügt jedem IPv6-Paket einen 20-Byte-IPv4-Header hinzu. Daher können 6in4-Tunnel-Schnittstellen IPv6-Pakete bis zu 1480 Byte über ein zugrunde liegendes Netzwerk mit einem Standard-MTU von 1500 Byte ohne Fragmentierung übertragen.

6in4-Tunnel-Schnittstellen werden häufig von IPv6-Tunnel-Brokers (wie Hurricane Electric) verwendet, um isolierte IPv6-Netzwerke oder einzelne Hosts mit dem IPv6-Internet zu verbinden.

Beispiel:

set interfaces tunnel tun0 encapsulation sit
set interfaces tunnel tun0 source-address 192.0.2.10
set interfaces tunnel tun0 remote 192.0.2.20
set interfaces tunnel tun0 address 2001:db8:bb::1/64

Siehe auch

Für ein praktisches Konfigurationsbeispiel siehe den Tunnelbroker.net (IPv6)-Abschnitt.

Generic Routing Encapsulation (GRE)

GRE ist ein vielseitiges Verschlüsselungsprotokoll, das in RFC 2784 definiert ist. Im Gegensatz zu einfachen Protokollen wie IPIP ermöglicht es GRE, sowohl IPv4 als auch IPv6 über denselben Tunnel zu transportieren.

GRE umschließt ursprüngliche Datenpakete, indem ein GRE-Header hinzugefügt wird, gefolgt von einem IP-Header (dem Lieferheader). Der Lieferheader verwendet die IP-Protokollnummer 47, um GRE-kapselten Datenverkehr zu identifizieren.

In VyOS können GRE-Tunnel über IPv4 (Kapselung gre) und IPv6 (Kapselung ip6gre) Transportnetze eingerichtet werden.

Konfiguration

Um einen GRE-Tunnel zu konfigurieren, müssen Sie eine Quell-IP-Adresse des Tunnels, eine Ziel-IP-Adresse des Tunnels, einen Kapselungstyp (GRE) und eine IP-Adresse der Tunnel-Schnittstelle definieren.

Beispiel:

Das folgende Beispiel zeigt, wie ein IPv4/IPv6-over-IPv6 GRE-Tunnel zwischen einem VyOS-Router und einem Linux-Host, der systemd-networkd ausführt, konfiguriert wird.

VyOS-Router:

set interfaces tunnel tun101 address '2001:db8:feed:beef::1/126'
set interfaces tunnel tun101 address '192.168.5.1/30'
set interfaces tunnel tun101 encapsulation 'ip6gre'
set interfaces tunnel tun101 source-address '2001:db8:babe:face::3afe:3'
set interfaces tunnel tun101 remote '2001:db8:9bb:3ce::5'

Linux systemd-networkd:

Die systemd-networkd-Einrichtung erfordert zwei Konfigurationsdateien: xxx.netdev, um die GRE-Tunnel-Schnittstelle zu erstellen, und xxx.network, um IP-Adressen darauf zuzuweisen.

# cat /etc/systemd/network/gre-example.netdev
[NetDev]
Name=gre-example
Kind=ip6gre
MTUBytes=14180

[Tunnel]
Remote=2001:db8:babe:face::3afe:3


# cat /etc/systemd/network/gre-example.network
[Match]
Name=gre-example

[Network]
Address=2001:db8:feed:beef::2/126

[Address]
Address=192.168.5.2/30

GRE-Schlüssel

Ein GRE-Schlüssel ist ein optionaler 32-Bit-Field im GRE-Header, der es ermöglicht, mehrere GRE-Tunnel zwischen denselben Quell- und Zielendpunkten zu betreiben. Wenn ein Paket eintrifft, prüft der Empfänger den GRE-Schlüssel, um zu bestimmen, welche Tunnel-Schnittstelle es verarbeiten sollte.

Obwohl es klingt, als wäre es sicherheitsrelevant, ist der GRE-Schlüssel nur ein Identifikator und bietet keine Verschlüsselung oder DatenSchutz.

Beispiel:

set interfaces tunnel tun0 source-address 192.0.2.10
set interfaces tunnel tun0 remote 192.0.2.20
set interfaces tunnel tun0 address 10.40.50.60/24
set interfaces tunnel tun0 parameters ip key 10

set interfaces tunnel tun1 source-address 192.0.2.10
set interfaces tunnel tun1 remote 192.0.2.20
set interfaces tunnel tun1 address 172.16.17.18/24
set interfaces tunnel tun1 parameters ip key 20

GRETAP

Im Gegensatz zu GRE, das nur Layer 3 (IP) Traffic kapselt, kapselt GRETAP Layer 2 (Ethernet)-Frames.

Das bedeutet, dass GRETAP-Tunnel-Schnittstellen Mitglieder einer Brückenschnittstelle sein können. Dies ermöglicht es zwei geografisch entfernten Standorten, sich so zu verbinden, als wären sie auf demselben LAN.

GRETAP-Tunnel können über IPv4- und IPv6-Transportnetze eingerichtet werden.

Beispiel:

set interfaces bridge br0 member interface eth0
set interfaces bridge br0 member interface tun0
set interfaces tunnel tun0 encapsulation gretap
set interfaces tunnel tun0 source-address 198.51.100.2
set interfaces tunnel tun0 remote 203.0.113.10

Problembehandlung

GRE ist ein standardisiertes Tunnel-Protokoll, das in vielen Netzwerkumgebungen verwendet wird.

Obwohl die GRE-Tunnel-Konfiguration einfach ist, treten häufig Verbindungsfehler auf, weil ACLs oder Firewall-Regeln das IP-Protokoll 47 blockieren oder direkte Kommunikation zwischen den Tunnel-Endpunkten verhindern.

Wenn Ihr GRE-Tunnel nicht hergestellt wird, führen Sie diese Diagnose-Schritte durch:

1. Stellen Sie sicher, dass der Remote-Partner von der konfigurierten source-address erreichbar ist.

Dies stellt sicher, dass der zugrunde liegende physische Weg zwischen den beiden Endpunkten funktionsfähig ist.
