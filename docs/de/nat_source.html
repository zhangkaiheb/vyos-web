NAT44

NAT ist eine gängige Methode, um einen IP-Adressraum in einen anderen umzuwandeln, indem man die Netzwerkadressinformationen im IP-Kopf von Paketen während ihrer Übertragung durch ein Verkehrsleitungsgerät ändert. Die Technik wurde ursprünglich als Kurzweg verwendet, um den Bedarf an einer Neubeschreibung jedes Hosts zu vermeiden, wenn ein Netzwerk verschoben wurde. Sie ist zu einem beliebten und unverzichtbaren Werkzeug geworden, um den globalen Adressraum bei der IPv4-Adressauslastung zu schonen. Eine Internet-routbare IP-Adresse eines NAT-Gateways kann für ein gesamtes privates Netzwerk verwendet werden.

IP-Masquerading ist eine Technik, die ein ganzes IP-Adressnetzwerk, normalerweise bestehend aus privaten IP-Adressen, hinter einer einzelnen IP-Adresse in einem anderen, meist öffentlichen Adressbereich versteckt. Die versteckten Adressen werden in eine einzelne (öffentliche) IP-Adresse geändert, als Quelladresse der ausgehenden IP-Pakete, sodass sie als stammend nicht vom versteckten Host, sondern vom Routing-Gerät selbst erscheinen. Aufgrund der Popularität dieser Technik zur Einsparung des IPv4-Adressraums ist der Begriff NAT praktisch synonym mit IP-Masquerading geworden.

Da die Netzwerkadressübersetzung die IP-Adressinformationen in Paketen modifiziert, können NAT-Implementierungen sich in ihrer spezifischen Verhaltensweise in verschiedenen Adressierungsfällen und ihrem Einfluss auf den Netzwerkverkehr unterscheiden. Die Details des NAT-Verhaltens sind bei Geräten mit NAT-Implementierungen selten von den Herstellern dokumentiert.

Die Computer auf einem internen Netzwerk können eine der von der IANA für private Adressierung festgelegten Adressen verwenden (siehe RFC 1918). Diese reservierten IP-Adressen werden im Internet nicht verwendet, daher wird eine externe Maschine sie nicht direkt weiterleiten. Die folgenden Adressen sind für den privaten Gebrauch reserviert:

  • 10.0.0.0 bis 10.255.255.255 (CIDR: 10.0.0.0/8)

  • 172.16.0.0 bis 172.31.255.255 (CIDR: 172.16.0.0/12)

  • 192.168.0.0 bis 192.168.255.255 (CIDR: 192.168.0.0/16)

Wenn ein ISP ein CGN einsetzt und RFC 1918 Adressbereiche für die Nummerierung von Kunden-Gateways verwendet, entsteht das Risiko von Adresskollisionen und damit verbundenen Routingschwierigkeiten, wenn das Kundennetzwerk bereits einen RFC 1918 Adressbereich verwendet.

Dies veranlasste einige ISPs, eine Richtlinie innerhalb der ARIN zu entwickeln, um neuen privaten Adressraum für CGNs zu allozieren, doch ARIN verwies auf die IETF, bevor die Richtlinie implementiert wurde, wobei angegeben wurde, dass es sich nicht um ein typisches Allokationsproblem handelte, sondern um eine Reservierung von Adressen für technische Zwecke (gemäß RFC 2860).

IETF veröffentlichte RFC 6598, welches einen gemeinsamen Adressraum für die Nutzung in ISP-CGN-Deployment beschreibt, der gleiche Netzwerkprefixe sowohl auf eingehenden als auch ausgehenden Schnittstellen verarbeiten kann. ARIN gab den Adressraum für diese Zuordnung an die IANA zurück.

Der zugewiesene Adressblock ist 100.64.0.0/10.

Geräte, die beurteilen, ob eine IPv4-Adresse öffentlich ist, müssen aktualisiert werden, um den neuen Adressraum zu erkennen. Die Zuweisung eines zusätzlichen privaten IPv4-Adressraums für NAT-Geräte könnte die Übergangsphase zu IPv6 verlängern.

Übersicht

Verschiedene NAT-Typen

SNAT

SNAT ist die häufigste Form von NAT und wird normalerweise einfach als NAT bezeichnet. Um genauer zu sein, was die meisten Leute als NAT bezeichnen, ist eigentlich der Prozess der PAT, oder NAT-Overload. SNAT wird typischerweise von internen Benutzern/privaten Hosts verwendet, um auf das Internet zuzugreifen – die Quelladresse wird übersetzt und bleibt dadurch privat.

DNAT

DNAT ändert die Zieladresse der Pakete, die durch den Router gehen, während SNAT die Quelladresse der Pakete ändert. DNAT wird typischerweise verwendet, wenn ein externes (öffentliches) Host eine Sitzung mit einem internen (privaten) Host initiieren muss. Ein Kunde muss auf einen privaten Dienst hinter den öffentlichen IP-Adresse des Routers zugreifen. Eine Verbindung wird mit der öffentlichen IP-Adresse des Routers auf einem bekannten Port hergestellt und somit wird der gesamte Datenverkehr für diesen Port so umgeschrieben, dass er den internen (privaten) Host adressiert.

Zweirichtung-NAT

Dies ist ein häufiges Szenario, bei dem SNAT und DNAT gleichzeitig konfiguriert werden. Es wird häufig verwendet, wenn interne (private) Hosts eine Verbindung mit externen Ressourcen herstellen müssen und externe Systeme auf interne (private) Ressourcen zugreifen müssen.

NAT-Regelsatz

NAT wird vollständig auf einer Reihe sogenannter Regeln konfiguriert. Regeln sind nummeriert und werden vom zugrunde liegenden Betriebssystem in numerischer Reihenfolge bewertet! Die Regelnummern können durch Verwendung der rename und copy Befehle geändert werden.

Hinweis

Änderungen am NAT-System wirken sich nur auf neu etablierte Verbindungen aus. Bereits bestehende Verbindungen werden nicht beeinflusst.

Tipp

Beim Entwurf Ihres NAT-Regelsatzes lassen Sie etwas Platz zwischen aufeinanderfolgenden Regeln für spätere Erweiterungen. Ihr Regelsatz könnte mit Zahlen wie 10, 20, 30 beginnen. So können Sie später den Regelsatz erweitern und neue Regeln zwischen vorhandenen einfügen.

Regeln werden für SNAT und DNAT erstellt.

Für Bidirektionale NAT muss eine Regel für SNAT und DNAT erstellt werden.

Verkehrsfilter

Verkehrsfilter werden verwendet, um zu steuern, welche Pakete die definierten NAT-Regeln anwenden. Fünf verschiedene Filter können innerhalb einer NAT-Regel angewandt werden.

  • outbound-interface - nur für SNAT anwendbar. Es konfiguriert die Schnittstelle, die für den außenliegenden Verkehr verwendet wird, auf den diese Übersetzungsregel angewandt wird. Schnittstellengruppen, invertierte Auswahl und Wildcards werden ebenfalls unterstützt.

    Beispiele:

    set nat source rule 20 outbound-interface name eth0
set nat source rule 30 outbound-interface name bond1*
set nat source rule 20 outbound-interface name !vtun2
set nat source rule 20 outbound-interface group GROUP1
set nat source rule 20 outbound-interface group !GROUP2

  • inbound-interface - nur für DNAT anwendbar. Es konfiguriert die Schnittstelle, die für den innenliegenden Verkehr verwendet wird, auf den diese Übersetzungsregel angewandt wird. Schnittstellengruppen, invertierte Auswahl und Wildcards werden ebenfalls unterstützt.

    Beispiel:

    set nat destination rule 20 inbound-interface name eth0
set nat destination rule 30 inbound-interface name bond1*
set nat destination rule 20 inbound-interface name !vtun2
set nat destination rule 20 inbound-interface group GROUP1
set nat destination rule 20 inbound-interface group !GROUP2

  • protocol - gibt an, welche Protokolltypen diese Übersetzungsregel betrifft. Nur Pakete, die dem angegebenen Protokoll entsprechen, werden übersetzt. Standardmäßig gilt dies für alle Protokolle.

    Beispiel:

    • Setzen Sie SNAT-Regel 20, um nur TCP- und UDP-Pakete zu übersetzen

    • Setzen Sie DNAT-Regel 20, um nur UDP-Pakete zu übersetzen

    set nat source rule 20 protocol tcp_udp
set nat destination rule 20 protocol udp

  • source - gibt an, welche Pakete die NAT-Übersetzungsregel anwenden, basierend auf der Quell-IP-Adresse und/oder Quellportnummer der Pakete. Nur passende Pakete werden für die NAT betrachtet.

    Beispiel:

    • Setzen Sie SNAT-Regel 20, um nur Pakete zu übersetzen, die aus dem Netzwerk 192.0.2.0/24 kommen

    • Setzen Sie SNAT-Regel 30, um nur Pakete zu übersetzen, die aus dem Netzwerk 203.0.113.0/24 mit einer Quellportnummer von 80 und 443 kommen

    set nat source rule 20 source address 192.0.2.0/24
set nat source rule 30 source address 203.0.113.0/24
set nat source rule 30 source port 80,443

  • destination - gibt an, welche Pakete der Übersetzung unterworfen werden, nur basierend auf der Zieladresse und/oder Portnummer, die konfiguriert wurden.

    Hinweis

    Wenn keine Zieladresse angegeben wird, passt die Regel auf jede Zieladresse und jeden Port.

    Beispiel:

    • Konfigurieren Sie SNAT-Regel (40), um nur Pakete mit einer Zieladresse von 192.0.2.1 zu übersetzen.

    set nat source rule 40 destination address 192.0.2.1

Adresskonvertierung

Jede NAT-Regel hat einen Übersetzungs-Befehl definiert. Der für die Übersetzung definierte Adressraum ist der Adressraum, der verwendet wird, wenn die Adressinformationen in einem Paket ersetzt werden.

Quelladresse

Bei SNAT-Regeln wird die Quelladresse der Pakete durch die in dem Übersetzungs-Befehl angegebene Adresse ersetzt. Ein Port-Übersetzung kann auch angegeben werden und ist Teil der Übersetzungs-Adresse.

Hinweis

Die Übersetzungs-Adresse muss auf eine der verfügbaren Adressen auf dem konfigurierten outbound-interface gesetzt werden oder auf masquerade, das die primäre IP-Adresse des outbound-interface als Übersetzungs-Adresse verwendet.

Hinweis

Wenn NAT für eine große Anzahl von Host-Systemen verwendet wird, wird empfohlen, mindestens eine IP-Adresse pro 256 private Host-Systeme zu verwenden. Dies liegt daran, dass es 65.000 Portnummern für eindeutige Übersetzungen gibt und ein Durchschnitt von 200-300 Sitzungen pro Host-System reserviert wird.

Beispiel:

  • Definieren Sie eine diskrete Quell-IP-Adresse von 100.64.0.1 für SNAT-Regel 20

  • Verwenden Sie die Adresse masquerade (die primäre Adresse der Schnittstelle) auf Regel 30

  • Wenn Sie viele private Maschinen hinter dem NAT haben, könnte Ihr Adresspool größer sein. Verwenden Sie bei der Übersetzung auf SNAT-Regel 40 eine beliebige Adresse im Bereich 100.64.0.10 - 100.64.0.20

set nat source rule 20 translation address 100.64.0.1
set nat source rule 30 translation address 'masquerade'
set nat source rule 40 translation address 100.64.0.10-100.64.0.20

Zieladresse

Bei DNAT-Regeln wird die Zieladresse der Pakete durch die im translation address Befehl angegebene Adresse ersetzt.

Beispiel:

  • DNAT-Regel 10 ersetzt die Zieladresse eines eingehenden Pakets mit 192.0.2.10

set nat destination rule 10 translation address 192.0.2.10

Außerdem wird bei DNAT die Weiterleitung an localhost unterstützt. Der Redirect-Befehl ist eine besondere Form von DNAT, die immer die Zieladresse auf die lokale Host-Adresse übersetzt.

Beispiel für Weiterleitung:

set nat destination rule 10 translation redirect port 22

NAT-Lastverteilung

Fortgeschrittene Konfiguration kann verwendet werden, um Quell- oder Ziel-NAT anzuwenden und innerhalb einer einzigen Regel mehrere übersetzte Adressen zu definieren, sodass NAT die Übersetzungen unter ihnen verteilt.

NAT-Lastverteilung verwendet ein Algorithmus, der einen Hash generiert und basierend darauf die entsprechende Übersetzung anwendet. Dieser Hash kann zufällig generiert werden oder kann Daten aus dem IP-Header verwenden: Quell-Adresse, Ziel-Adresse, Quell-Port und/oder Ziel-Port. Standardmäßig wird der Hash zufällig generiert.

Beim Definieren der übersetzten Adresse, genannt backends, muss ein weight konfiguriert werden. Dies ermöglicht dem Benutzer, die Lastverteilung gemäß seinen Bedürfnissen zu definieren. Die Summe aller Gewichte, die für die Backends definiert wurden, muss 100 betragen. Mit anderen Worten, das Gewicht, das für das Backend definiert wird, ist der Prozentsatz der Verbindungen, die dieses Backend erhalten werden.

set nat [source | destination] rule <rule> load-balance hash [source-address | destination-address | source-port | destination-port | random]
set nat [source | destination] rule <rule> load-balance backend <x.x.x.x> weight <1-100>

Konfigurationsbeispiele

Um SNAT einzurichten, benötigen wir Folgendes:

  • Die internen IP-Adressen, die übersetzt werden sollen

  • Die Ausgangsschnittstelle, auf der die Übersetzung durchgeführt wird

  • Die externe IP-Adresse, auf die übersetzt werden soll

In dem Beispiel, das wir für die Quick Start-Konfiguration oben verwenden, demonstrieren wir die folgende Konfiguration:

set nat source rule 100 outbound-interface name 'eth0'
set nat source rule 100 source address '192.168.0.0/24'
set nat source rule 100 translation address 'masquerade'

Was folgende Konfiguration erzeugt:

rule 100 {
    outbound-interface {
        name eth0
    }
    source {
        address 192.168.0.0/24
    }
    translation {
        address masquerade
    }
}

In diesem Beispiel verwenden wir masquerade als Übersetzungsadresse statt einer IP-Adresse. Das masquerade Ziel ist effektiv ein Alias dafür, „verwende die IP-Adresse, die auf der Ausgangsschnittstelle ist“, anstatt eine statisch konfigurierte IP-Adresse. Dies ist nützlich, wenn Sie DHCP für Ihre Ausgangsschnittstelle verwenden und nicht wissen, was die externe Adresse sein wird.

Wenn NAT für eine große Anzahl von Host-Systemen verwendet wird, wird empfohlen, mindestens eine IP-Adresse pro 256 Host-Systeme zu verwenden. Dies liegt daran, dass es 65.000 Portnummern für eindeutige Übersetzungen gibt und ein Durchschnitt von 200-300 Sitzungen pro Host-System reserviert wird.

Beispiel: Für ein Netzwerk mit etwa 8000 Hosts wird ein Quell-NAT-Pool von 32 IP-Adressen empfohlen.

Eine Gruppe von Adressen kann durch die Verwendung eines Bindestrichs zwischen zwei IP-Adressen definiert werden:

set nat source rule 100 translation address '203.0.113.32-203.0.113.63'

Vermeiden von „leaky“ NAT

Linux netfilter wird keinen Verkehr markieren, der als INVALID bezeichnet wird. Dies verwirrt oft Menschen, die denken, dass Linux (insbesondere VyOS) eine gebrochene NAT-Implementierung hat, weil nicht-NAT-Verkehr sieht, wie er über eine externe Schnittstelle verlässt. Dies funktioniert tatsächlich wie beabsichtigt, und eine Paket-Aufzeichnung des „leaky“ Verkehrs sollte zeigen, dass der Verkehr entweder ein zusätzliches TCP „RST“, „FIN,ACK“ oder „RST,ACK“ ist, das von Client-Systemen nach dem Schließen der Verbindung gesendet wird. Das häufigste ist das zusätzliche TCP RST, das einige Host-Implementierungen nach Beendigung einer Verbindung senden (was implementationspezifisch ist).

Im Wesentlichen hat die Verbindungsverfolgung bereits beobachtet, dass die Verbindung geschlossen wurde und hat den Fluss in INVALID umgewandelt, um Angriffe zu verhindern, die versuchen, die Verbindung wiederzuverwenden.

Sie können das „leaky“ Verhalten vermeiden, indem Sie eine Firewall-Richtlinie verwenden, die „invalid“ Zustandspakete löscht.

Die Kontrolle über das Abgleichen von „invalid“ Zustand Traffic, z. B. die Fähigkeit, selektiv zu protokollieren, ist ein wichtiges Troubleshooting-Werkzeug für das Beobachten von gebrochenem Protokollverhalten. Aus diesem Grund löscht VyOS nicht global „invalid“ Zustand Traffic, sondern lässt es dem Operator überlassen, zu entscheiden, wie der Traffic behandelt wird.

Hairpin NAT/NAT-Reflexion

Ein typisches Problem beim Verwenden von NAT und Hosting öffentlicher Server ist die Fähigkeit, interne Systeme mit ihrer externen IP-Adresse zu erreichen. Die Lösung dafür ist normalerweise die Verwendung von Split-DNS, um Host-Systeme korrekt auf die interne Adresse zu verweisen, wenn Anfragen intern gestellt werden. Da viele kleinere Netzwerke keine DNS-Infrastruktur haben, wird häufig ein Workaround eingesetzt, um den Verkehr zu ermöglichen, indem der Antrag von internen Hosts an die Quelladresse der internen Schnittstelle des Firewalls übersetzt wird.

Diese Technik wird häufig als NAT-Reflexion oder Hairpin NAT bezeichnet.

Beispiel:

  • Leiten Sie Microsoft RDP-Verkehr von der Außenseite (WAN, extern) über DNAT in Regel 100 an den internen, privaten Host 192.0.2.40 weiter.

  • Leiten Sie Microsoft RDP-Verkehr von der internen (LAN, privaten) Netzwerk über DNAT in Regel 110 an den internen, privaten Host 192.0.2.40 weiter. Wir benötigen außerdem eine SNAT Regel 110 für den umgekehrten Weg des Verkehrs. Das interne Netzwerk 192.0.2.0/24 ist über die Schnittstelle eth0.10 erreichbar.

set nat destination rule 100 description 'Regular destination NAT from external'
set nat destination rule 100 destination port '3389'
set nat destination rule 100 inbound-interface name 'pppoe0'
set nat destination rule 100 protocol 'tcp'
set nat destination rule 100 translation address '192.0.2.40'

set nat destination rule 110 description 'NAT Reflection: INSIDE'
set nat destination rule 110 destination port '3389'
set nat destination rule 110 inbound-interface name 'eth0.10'
set nat destination rule 110 protocol 'tcp'
set nat destination rule 110 translation address '192.0.2.40'

set nat source rule 110 description 'NAT Reflection: INSIDE'
set nat source rule 110 destination address '192.0.2.0/24'
set nat source rule 110 outbound-interface name 'eth0.10'
set nat source rule 110 protocol 'tcp'
set nat source rule 110 source address '192.0.2.0/24'
set nat source rule 110 translation address 'masquerade'

Ziel-NAT

DNAT wird normalerweise als Port-Weiterleitung bezeichnet. Wenn Sie VyOS als NAT-Router und -Firewall verwenden, ist eine häufige Konfigurationsaufgabe, eingehenden Verkehr an ein System hinter dem Firewall weiterzuleiten.

In diesem Beispiel verwenden wir das Beispiel Quick Start-Konfiguration oben als Ausgangspunkt.

Um eine Ziel-NAT-Regel einzurichten, benötigen wir:

  • Die Schnittstelle, auf der der Verkehr eingeht;

  • Das Protokoll und den Port, den wir weiterleiten möchten;

  • Die IP-Adresse des internen Systems, an das wir den Verkehr weiterleiten möchten.

In unserem Beispiel leiten wir Webserver-Verkehr an einen internen Webserver auf 192.168.0.100 weiter. HTTP-Verkehr verwendet das TCP-Protokoll auf Port 80. Für andere gängige Portnummern siehe: https://en.wikipedia.org/wiki/List_of_TCP_and_UDP_port_numbers

Unsere Konfigurationsbefehle wären:

set nat destination rule 10 description 'Port Forward: HTTP to 192.168.0.100'
set nat destination rule 10 destination port '80'
set nat destination rule 10 inbound-interface name 'eth0'
set nat destination rule 10 protocol 'tcp'
set nat destination rule 10 translation address '192.168.0.100'

Was folgende NAT-Ziel-Konfiguration erzeugt:

nat {
    destination {
        rule 10 {
            description "Port Forward: HTTP to 192.168.0.100"
            destination {
                port 80
            }
            inbound-interface {
                name eth0
            }
            protocol tcp
            translation {
                address 192.168.0.100
            }
        }
    }
}

Hinweis

Wenn Sie Verkehr an einen anderen Port als den, an dem er ankommt, weiterleiten, können Sie auch die Übersetzungsportnummer mit set nat destination rule [n] translation port konfigurieren.

Dies stellt unsere Port-Weiterleitungsregel her, aber wenn wir eine Firewall-Richtlinie erstellen, wird sie wahrscheinlich den Verkehr blockieren.

Firewall-Regeln für Ziel-NAT

Es ist wichtig zu beachten, dass bei der Erstellung von Firewall-Regeln die DNAT-Übersetzung vor dem Verkehr erfolgt, der die Firewall durchläuft. Mit anderen Worten, die Zieladresse wurde bereits auf 192.168.0.100 übersetzt.

Also wollen wir in unserem Firewall-Regelsatz den Verkehr erlauben, der zuvor eine Ziel-NAT-Regel getroffen hat. Um viele Regeln zu vermeiden, eine für jede Ziel-NAT-Regel, können wir alle ‘dnat’ Verbindungen mit einer einfachen Regel akzeptieren, mithilfe des connection-status Matchers:

set firewall ipv4 forward filter rule 10 action accept
set firewall ipv4 forward filter rule 10 connection-status nat destination
set firewall ipv4 forward filter rule 10 state new

Dies würde folgende Konfiguration erzeugen:

ipv4 {
    forward {
        filter {
            rule 10 {
                action accept
                connection-status {
                    nat destination
                }
                state new
            }
        }
    }
}

1-zu-1-NAT

Ein anderer Begriff, der oft für DNAT verwendet wird, ist 1-zu-1-NAT. Bei einer 1-zu-1-NAT-Konfiguration werden sowohl DNAT als auch SNAT verwendet, um den gesamten Verkehr von einer externen IP-Adresse auf eine interne IP-Adresse und umgekehrt zu übersetzen.

Typischerweise lässt eine 1-zu-1-NAT-Regel die Zielportnummer aus (alle Ports) und ersetzt das Protokoll mit entweder all oder ip.

Anschließend wird eine entsprechende SNAT-Regel erstellt, um den ausgehenden Verkehr für die interne IP-Adresse auf eine reservierte externe IP-Adresse zu übersetzen. Dies weist eine externe IP-Adresse einer internen IP-Adresse zu und ist nützlich für Protokolle, die kein Konzept von Ports haben, wie z. B. GRE.

Hier ist ein Auszug einer einfachen 1-zu-1-NAT-Konfiguration mit einer internen und einer externen Schnittstelle:

set interfaces ethernet eth0 address '192.168.1.1/24'
set interfaces ethernet eth0 description 'Inside interface'
set interfaces ethernet eth1 address '192.0.2.30/24'
set interfaces ethernet eth1 description 'Outside interface'
set nat destination rule 2000 description '1-to-1 NAT example'
set nat destination rule 2000 destination address '192.0.2.30'
set nat destination rule 2000 inbound-interface name 'eth1'
set nat destination rule 2000 translation address '192.168.1.10'
set nat source rule 2000 description '1-to-1 NAT example'
set nat source rule 2000 outbound-interface name 'eth1'
set nat source rule 2000 source address '192.168.1.10'
set nat source rule 2000 translation address '192.0.2.30'

Firewall-Regeln werden normalerweise geschrieben, wobei die interne IP-Adresse als Quelle für ausgehende Regeln und als Ziel für eingehende Regeln verwendet wird.

NAT vor VPN

Einige Anbieter von Anwendungsdiensten (ASPs) betreiben ein VPN-Gateway, um Zugriff auf ihre internen Ressourcen zu bieten, und verlangen, dass eine verbindende Organisation den gesamten Verkehr zum Dienstanbieter-Netzwerk auf eine von ASP bereitgestellte Quelladresse übersetzt.

Lastverteilung

Hier geben wir zwei Beispiele an, wie NAT-Lastverteilung angewandt werden kann.

Erster Szenario: Ziel-NAT für alle HTTP-Verkehr, der durch die Schnittstelle eth0 kommt, und vier Backends. Das erste Backend sollte 30 % der Anfragen empfangen, das zweite Backend 20 %, das dritte 15 % und das vierte 35 %. Wir verwenden Quell- und Zieladresse für die Hash-Generierung.

set nat destination rule 10 inbound-interface name eth0
set nat destination rule 10 protocol tcp
set nat destination rule 10 destination port 80
set nat destination rule 10 load-balance hash source-address
set nat destination rule 10 load-balance hash destination-address
set nat destination rule 10 load-balance backend 198.51.100.101 weight 30
set nat destination rule 10 load-balance backend 198.51.100.102 weight 20
set nat destination rule 10 load-balance backend 198.51.100.103 weight 15
set nat destination rule 10 load-balance backend 198.51.100.104 weight 35

Zweiter Szenario: Quell-NAT für alle ausgehenden Verbindungen aus LAN 10.0.0.0/8, mit drei öffentlichen Adressen und gleicher Verteilung. Wir generieren den Hash zufällig.

set nat source rule 10 outbound-interface name eth0
set nat source rule 10 source address 10.0.0.0/8
set nat source rule 10 load-balance hash random
set nat source rule 10 load-balance backend 192.0.2.251 weight 33
set nat source rule 10 load-balance backend 192.0.2.252 weight 33
set nat source rule 10 load-balance backend 192.0.2.253 weight 34

Beispielnetzwerk

Hier ist ein Beispiel eines Netzwerks für einen ASP. Der ASP verlangt, dass alle Verbindungen aus diesem Unternehmen von 172.29.41.89 stammen – eine Adresse, die vom ASP zugewiesen wird und nicht am Kundensite verwendet wird.

Konfiguration

Die erforderliche Konfiguration kann in vier Hauptteile zerlegt werden:

  • Eine Dummy-Schnittstelle für die vom Anbieter zugewiesene IP;

  • NAT (speziell, Quell-NAT);

  • IPSec IKE und ESP Gruppen;

  • IPSec VPN-Tunnel.

Dummy-Schnittstelle

Die Dummy-Schnittstelle ermöglicht uns, eine Äquivalenz der Cisco IOS Loopback-Schnittstelle zu haben – eine routerinterne Schnittstelle, die wir für IP-Adressen verwenden können, die der Router kennen muss, aber nicht tatsächlich einer echten Netzwerk zugewiesen sind.

Wir benötigen nur einen Schritt für diese Schnittstelle:

set interfaces dummy dum0 address '172.29.41.89/32'
NAT-Konfiguration
set nat source rule 110 description 'Internal to ASP'
set nat source rule 110 destination address '172.27.1.0/24'
set nat source rule 110 source address '192.168.43.0/24'
set nat source rule 110 translation address '172.29.41.89'
set nat source rule 120 description 'Internal to ASP'
set nat source rule 120 destination address '10.125.0.0/16'
set nat source rule 120 source address '192.168.43.0/24'
set nat source rule 120 translation address '172.29.41.89'
IPSec IKE und ESP

Der ASP hat seine IPSec-Anforderungen dokumentiert:

  • IKE Phase:

    • aes256 Verschlüsselung

    • sha256 Hashes

  • ESP Phase:

    • aes256 Verschlüsselung

    • sha256 Hashes

    • DH Group 14

Zusätzlich möchten wir nur auf unserer eth1-Schnittstelle (die externe Schnittstelle im Bild oben) VPNs verwenden

set vpn ipsec ike-group my-ike key-exchange 'ikev1'
set vpn ipsec ike-group my-ike lifetime '7800'
set vpn ipsec ike-group my-ike proposal 1 dh-group '14'
set vpn ipsec ike-group my-ike proposal 1 encryption 'aes256'
set vpn ipsec ike-group my-ike proposal 1 hash 'sha256'

set vpn ipsec esp-group my-esp lifetime '3600'
set vpn ipsec esp-group my-esp mode 'tunnel'
set vpn ipsec esp-group my-esp pfs 'disable'
set vpn ipsec esp-group my-esp proposal 1 encryption 'aes256'
set vpn ipsec esp-group my-esp proposal 1 hash 'sha256'

set vpn ipsec interface 'eth1'
IPSec VPN-Tunnel

Wir verwenden die oben erstellten IKE- und ESP-Gruppen für diesen VPN. Da wir Zugriff auf zwei verschiedene Subnetze auf der anderen Seite benötigen, benötigen wir zwei verschiedene Tunnel. Wenn Sie in den vorherigen Schritten die Namen der ESP-Gruppe und IKE-Gruppe geändert haben, stellen Sie sicher, dass Sie hier auch die richtigen Namen verwenden.

set vpn ipsec authentication psk vyos id '203.0.113.46'
set vpn ipsec authentication psk vyos id '198.51.100.243'
set vpn ipsec authentication psk vyos secret 'MYSECRETPASSWORD'
set vpn ipsec site-to-site peer branch authentication local-id '203.0.113.46'
set vpn ipsec site-to-site peer branch authentication mode 'pre-shared-secret'
set vpn ipsec site-to-site peer branch authentication remote-id '198.51.100.243'
set vpn ipsec site-to-site peer branch connection-type 'initiate'
set vpn ipsec site-to-site peer branch default-esp-group 'my-esp'
set vpn ipsec site-to-site peer branch ike-group 'my-ike'
set vpn ipsec site-to-site peer branch ikev2-reauth 'inherit'
set vpn ipsec site-to-site peer branch local-address '203.0.113.46'
set vpn ipsec site-to-site peer branch remote-address '198.51.100.243'
set vpn ipsec site-to-site peer branch tunnel 0 local prefix '172.29.41.89/32'
set vpn ipsec site-to-site peer branch tunnel 0 remote prefix '172.27.1.0/24'
set vpn ipsec site-to-site peer branch tunnel 1 local prefix '172.29.41.89/32'
set vpn ipsec site-to-site peer branch tunnel 1 remote prefix '10.125.0.0/16'
Testen und Validieren

Wenn Sie alle oben genannten Schritte abgeschlossen haben, möchten Sie sicherlich sehen, ob es funktioniert.

Beginnen Sie mit der Überprüfung von IPSec SAs (Security Associations) mit:

$ show vpn ipsec sa

Peer ID / IP                            Local ID / IP
------------                            -------------
198.51.100.243                          203.0.113.46

    ------  -----  -------------  -------  ----    -----  ------  ------  -----
