Synchronisation de configuration

La synchronisation de configuration (config-sync) est un service VyOS qui réplique les sections sélectionnées de la configuration d'un routeur vers un autre routeur. Elle élimine le besoin de miroir manuellement les modifications de configuration d'un routeur principal vers un secondaire.

La synchronisation est effectuée par un hook post-commit sur le routeur principal. Le hook surveille les sections sélectionnées pour la synchronisation. Lorsqu'une de ces sections est modifiée par un commit, le hook appelle l'API HTTPS sur le routeur secondaire et envoie l'état actuel de toutes les sections sélectionnées dans l'une des modes suivants :

  • load: Remplace les sections sélectionnées sur le secondaire avec la version du principal. Tout ce qui existe uniquement sur le secondaire à l'intérieur de ces sections est supprimé.

  • set: Fusionne la version du principal des sections sélectionnées dans le secondaire. Les valeurs en conflit sont remplacées par le principal. Les entrées qui existent uniquement sur le secondaire sont conservées.

La synchronisation est strictement unidirectionnelle du principal au secondaire; les modifications apportées au secondaire ne sont pas envoyées en arrière.

Les deux routeurs doivent être en ligne pendant un commit sur le principal qui modifie une section configurée. Si le secondaire est inatteignable, le commit du principal réussit, mais la configuration n'est pas synchronisée, et l'échec est enregistré dans le journal système.

Configuration

Paramètres du routeur secondaire

set service config-sync secondary address <address>

Configurez l'adresse du routeur secondaire.

Le routeur principal envoie la configuration synchronisée à cette adresse via l'API HTTPS du secondaire. La valeur peut être une adresse IPv4, une adresse IPv6 ou un FQDN. Cette valeur est obligatoire.

Note

L'adresse doit être définie chaque fois que service config-sync est configuré. Sinon, le commit est rejeté.

Exemple :

set service config-sync secondary address 192.0.2.112
set service config-sync secondary port <1-65535>

Configurez le port TCP sur lequel l'API HTTPS du routeur secondaire écoute.

La valeur doit correspondre au port configuré sous service https port sur le routeur secondaire. Si elles diffèrent, le commit du principal réussit, mais la synchronisation post-commit échoue. Le secondaire n'est pas mis à jour, et le principal enregistre l'erreur dans le journal système.

La valeur par défaut est 443, correspondant à la valeur par défaut de service https port.

Exemple :

set service config-sync secondary port 8443
set service config-sync secondary key <key>

Configurez la clé API HTTPS que le routeur principal utilise pour s'authentifier à l'API HTTPS du routeur secondaire.

La valeur doit correspondre à une clé configurée sous service https api keys id <ID> key sur le secondaire. Si aucune clé correspondante n'existe sur le secondaire, le commit du principal réussit, mais la synchronisation post-commit échoue. Le secondaire n'est pas mis à jour, et le principal enregistre l'erreur dans le journal système.

Note

Cette valeur doit être définie chaque fois que service config-sync est configuré. Sinon, le commit est rejeté.

Exemple :

set service config-sync secondary key 'foo'
set service config-sync secondary timeout <1-3600>

Configurez la durée, en secondes, pendant laquelle le routeur principal attend une réponse HTTPS du secondaire après avoir envoyé la configuration.

La valeur par défaut est de 60 secondes.

Exemple :

set service config-sync secondary timeout 120

Mode de synchronisation

set service config-sync mode <load | set>

Configurez comment le routeur secondaire applique la configuration poussée par le principal :

  • load: Remplace les sections sélectionnées sur le secondaire par la version du principal. Tout ce qui existe uniquement sur le secondaire à l'intérieur de ces sections est supprimé.

  • set: Fusionne la version du principal des sections sélectionnées dans le secondaire. Les valeurs en conflit sont remplacées par le principal. Les entrées qui existent uniquement sur le secondaire sont conservées.

Note

Cette valeur doit être définie chaque fois que service config-sync est configuré. Sinon, le commit est rejeté.

Exemple :

set service config-sync mode load

Sections à synchroniser

set service config-sync section <section>

Configurez une ou plusieurs sections de configuration à synchroniser du principal vers le routeur secondaire.

Répétez la commande pour ajouter des sections supplémentaires. Si une section configurée a été modifiée par un commit sur le principal, le hook envoie l'état actuel de toutes les sections configurées au secondaire. Si aucune des sections configurées n'a été modifiée, le hook ne fait rien.

Sections prises en charge :

  • firewall

  • interfaces <bonding | bridge | dummy | ethernet | geneve | input | l2tpv3 | loopback | macsec | openvpn | pppoe | pseudo-ethernet | sstpc | tunnel | virtual-ethernet | vti | vxlan | wireguard | wireless | wwan>

  • nat

  • nat66

  • pki

  • policy

  • protocols <babel | bfd | bgp | failover | igmp-proxy | isis | mpls | nhrp | ospf | ospfv3 | pim | pim6 | rip | ripng | rpki | segment-routing | static>

  • qos <interface | policy>

  • service <console-server | dhcp-relay | dhcp-server | dhcpv6-relay | dhcpv6-server | dns | lldp | mdns | monitoring | ndp-proxy | ntp | snmp | tftp-server | webproxy>

  • system <conntrack | flow-accounting | login | option | sflow | static-host-mapping | sysctl | time-zone>

  • vpn

  • vrf

Note

Au moins une section doit être configurée chaque fois que service config-sync est configuré. Sinon, le commit est rejeté.

Exemple :

set service config-sync section protocols ospf
set service config-sync section system time-zone

Fonctionnement

show configuration secondary sync [commands] [running | candidate | saved [<config-node-path>]]

Affiche la différence entre la configuration locale sur le principal et la configuration en cours sur le secondaire.

La commande récupère la configuration en cours du secondaire en temps réel via l'API HTTPS, donc le secondaire doit être accessible.

La configuration locale par défaut est running et peut être définie sur candidate (changements non commis) ou saved (dernière configuration sauvegardée). Le côté distant est toujours la configuration en cours du secondaire.

Par défaut, la différence est affichée au format de configuration avec - devant les lignes qui existent uniquement sur le secondaire et + devant les lignes qui existent uniquement sur le principal. Le mot-clé optionnel commands affiche la même différence sous forme d'une séquence de commandes set et delete de configuration, où set liste les chemins présents uniquement sur le principal, et delete liste les chemins présents uniquement sur le secondaire.

L'argument optionnel <config-node-path> limite la différence à une seule section et doit être l'une des sections déjà configurées sous set service config-sync section. Si omis, la différence couvre toutes les sections configurées.

Exemples :

# Comparer la configuration complète en cours avec le secondaire
show configuration secondary sync

# Comparer uniquement la configuration du protocole OSPF avec le secondaire
show configuration secondary sync running protocols ospf

# Comparer la configuration candidate avec le secondaire,
# affichée sous forme de commandes
show configuration secondary sync commands candidate

Exemple

L'exemple suivant synchronise les sections system time-zone et protocols ospf du Routeur A (principal, 192.0.2.1) vers le Routeur B (secondaire, 192.0.2.112). L'API HTTPS du Routeur B écoute sur le port TCP 8443.

Activez et configurez le service d'API HTTPS sur le Routeur B :

set service https listen-address '192.0.2.112'
set service https port '8443'
set service https api keys id primary key 'foo'
set service https api rest

Configurez le service de synchronisation de configuration sur le Routeur A :

set service config-sync mode 'load'
set service config-sync secondary address '192.0.2.112'
set service config-sync secondary port '8443'
set service config-sync secondary key 'foo'
set service config-sync section protocols 'ospf'
set service config-sync section system 'time-zone'

Apportez des modifications sur le Routeur A qui relèvent d'une des sections synchronisées. Le hook post-commit s'active automatiquement lors du commit :

vyos@vyos-A# set system time-zone 'America/Los_Angeles'
vyos@vyos-A# commit
INFO:vyos_config_sync:Config synchronization: Mode=load, Secondary=192.0.2.112
vyos@vyos-A# save

vyos@vyos-A# set protocols ospf area 0 network '198.51.100.0/30'
vyos@vyos-A# commit
INFO:vyos_config_sync:Config synchronization: Mode=load, Secondary=192.0.2.112
vyos@vyos-A# save

Chaque commit sur le Routeur A modifie une section, mais comme le hook envoie toutes les sections configurées chaque fois qu'une de celles-ci est modifiée, les deux commits remplacent l'état complet de system et protocols ospf sur le Routeur B.

Vérifiez que les modifications ont été appliquées sur le Routeur B :

vyos@vyos-B:~$ show configuration commands | match time-zone
set system time-zone 'America/Los_Angeles'

vyos@vyos-B:~$ show configuration commands | match ospf
set protocols ospf area 0 network '198.51.100.0/30'
