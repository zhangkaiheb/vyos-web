Aperçu

Cette section fournit des informations sur la configuration du pare-feu pour les flowtables.

set firewall flowtable …

Pour en savoir plus sur le flux général du trafic dans les pare-feux VyOS, voir Pare-feu.

- set firewall
    * flowtable
         - custom_flow_table
            + ...

Les flowtables vous permettent de définir un chemin rapide à travers le datapath du flowtable. Les flowtables prennent en charge les protocoles de couche 3 (IPv4 et IPv6) et de couche 4 (TCP et UDP).

Après que le premier paquet traverse avec succès le chemin de routage IP (chemin en cercles noirs), vous pouvez décharger les paquets suivants vers le flowtable via votre règlement. Vous spécifiez quand ajouter un flux au flowtable pendant le filtrage de transfert (cercle rouge numéro 6).

Lorsqu'un paquet trouve une entrée correspondante dans le flowtable (hit de flowtable), le système l'envoie vers le périphérique réseau de sortie. Cela signifie que les paquets évitent le chemin de routage IP classique et utilisent le chemin rapide (chemin en cercles orange). En conséquence, vous ne voyez pas ces paquets depuis aucun hook Netfilter après l'ingress. Si aucune entrée correspondante n'existe dans le flowtable (miss de flowtable), le paquet traverse le chemin de routage IP classique.

Note

Référence Flowtable: https://docs.kernel.org/networking/nf_flowtable.html

Configuration du flowtable

Pour utiliser les flowtables, vous devez configurer les éléments suivants :

  • Créer un flowtable qui inclut les interfaces qui seront utilisées par le flowtable.

  • Créer une règle de pare-feu. Définir l'action sur offload et utiliser votre flowtable souhaité pour offload-target.

Création d'un flow table :

set firewall flowtable <flow_table_name> interface <iface> Spécifier les interfaces à utiliser dans le flowtable.
set firewall flowtable <flow_table_name> description <text>

Fournir une description pour le flow table.

set firewall flowtable <flow_table_name> offload <hardware | software>

Spécifier le type de déchargement utilisé par le flowtable : hardware ou software. La valeur par défaut est software déchargé.

Note

Déchargement matériel : Assurez-vous que votre contrôleur d'interface réseau (NIC) prend en charge le déchargement matériel et que vous avez les pilotes nécessaires installés avant d'activer cette option.

Création de règles pour utiliser les flow tables :

set firewall [ipv4 | ipv6] forward filter rule <1-999999> action offload

Créer une règle de pare-feu dans la chaîne forward avec l'action définie sur offload.

set firewall [ipv4 | ipv6] forward filter rule <1-999999> offload-target <flowtable>

Créer une règle de pare-feu dans la chaîne forward et spécifier quel flowtable utiliser. Applicable uniquement si l'action est offload.

Sélection de l'interface

Important

Configurez toujours le flowtable avec l'interface que VyOS observe au niveau du hook forward — ce n'est pas nécessairement l'interface physique. Lorsque le trafic est reçu ou transmis via une interface logique, VyOS suit cette interface logique, et non le périphérique physique sous-jacent. Inscrire la mauvaise interface dans le flowtable entraîne un échec de toutes les recherches de flux, revenant au chemin de routage classique et contredisant l'objectif du déchargement rapide.

Exemple de configuration

Considérez les éléments suivants dans cette configuration :

  • Cet exemple utilise deux interfaces dans les flowtables : eth0 et eth1.

  • L'exemple propose un ensemble minimal de règles de pare-feu avec des règles de filtrage et des règles pour utiliser les capacités de déchargement du flowtable.

Le premier paquet est évalué par le chemin du pare-feu, donc une connexion souhaitée doit être explicitement acceptée. La même chose doit se produire pour le trafic dans l'ordre inverse. Dans la plupart des cas, les politiques d'état sont utilisées pour accepter une connexion dans le chemin inverse.

Dans l'exemple suivant, seul le trafic provenant de l'interface eth0, avec le protocole TCP et le port de destination 1122 est accepté. Tout autre trafic vers le routeur est supprimé.

Commandes

set firewall flowtable FT01 interface 'eth0'
set firewall flowtable FT01 interface 'eth1'
set firewall ipv4 forward filter default-action 'drop'
set firewall ipv4 forward filter rule 10 action 'offload'
set firewall ipv4 forward filter rule 10 offload-target 'FT01'
set firewall ipv4 forward filter rule 10 state 'established'
set firewall ipv4 forward filter rule 20 action 'accept'
set firewall ipv4 forward filter rule 20 state 'established'
set firewall ipv4 forward filter rule 20 state 'related'
set firewall ipv4 forward filter rule 110 action 'accept'
set firewall ipv4 forward filter rule 110 destination address '192.0.2.100'
set firewall ipv4 forward filter rule 110 destination port '1122'
set firewall ipv4 forward filter rule 110 inbound-interface name 'eth0'
set firewall ipv4 forward filter rule 110 protocol 'tcp'

Explication

Voici ce qui se produit pour une connexion souhaitée :

  1. Un paquet arrive sur eth0 avec l'adresse de destination 192.0.2.100, le protocole TCP et le port de destination 1122. Supposons que cette adresse soit accessible via l'interface eth1.

  2. Pour ce premier paquet, l'état de la connexion est nouveau. Ni la règle 10 ni la règle 20 ne s'appliquent.

  3. La règle 110 correspond, donc la connexion est acceptée.

  4. Lorsque le serveur 192.0.2.100 répond, l'état de la connexion devient établi, et la règle 20 accepte la réponse.

  5. Le routeur reçoit le deuxième paquet pour cette connexion. Comme l'état de la connexion est établi, la règle 10 correspond et ajoute une nouvelle entrée dans le flowtable FT01 pour cette connexion.

  6. Les paquets suivants passent par le chemin traditionnel et utilisent le chemin rapide pour le déchargement.

Configuration du flowtable sur les interfaces logiques et sous-interfaces

Configurez le flowtable avec le nom de l'interface que vous avez utilisé dans la configuration VyOS. Lorsque des VLANs, des liaisons ou des ponts sont impliqués, c'est l'interface logique (bond0, br0, eth0.10) — pas le port physique sous-jacent.

Par exemple :

  • Si bond0 est configuré, VyOS voit bond0 — pas eth0 ou eth1

  • Si br0 est configuré, VyOS voit br0 — pas ses interfaces membres

  • Le flowtable doit faire référence au même nom d'interface que VyOS observe

Deux formes sont acceptées, mais l'enregistrement du parent est recommandé :

  • Enregistrer bond1 décharge l'interface parente et toutes ses sous-interfaces VLAN (bond1.10, bond1.20, etc.) — le noyau découvre automatiquement celles-ci en analysant les en-têtes L2 (Linux 5.13+).

  • Enregistrer directement bond1.10 décharge uniquement le trafic VLAN 10. Mais la sous-interface doit exister au moment de l'application ; si elle n'est pas encore présente lors du chargement de la règlementation, la configuration pourrait échouer.

# Décharger bond1 et toutes les sous-interfaces (bond1.10, bond1.20, ...)
set firewall flowtable FT01 interface 'bond1'

# Décharger uniquement le VLAN 10 : enregistrer la sous-interface directement
set firewall flowtable FT01 interface 'bond1.10'

Exemple : Déchargement mixte des interfaces parentes et sous-interfaces

Considérons une configuration où :

  • Le trafic entre par bond1.10 (VLAN 10)

  • Le trafic sort par bond2.20 (VLAN 20)

set firewall flowtable FT01 interface 'bond1'
set firewall flowtable FT01 interface 'bond2.20'
set firewall ipv4 forward filter default-action 'drop'
set firewall ipv4 forward filter rule 10 action 'offload'
set firewall ipv4 forward filter rule 10 offload-target 'FT01'
set firewall ipv4 forward filter rule 10 state 'established'
set firewall ipv4 forward filter rule 20 action 'accept'
set firewall ipv4 forward filter rule 20 state 'established'
set firewall ipv4 forward filter rule 20 state 'related'
set firewall ipv4 forward filter rule 200 action 'accept'
set firewall ipv4 forward filter rule 200 inbound-interface name 'bond*'

Dans cette configuration :

  • bond1 couvre l'ingress de bond1.10 et toutes les autres sous-interfaces bond1.

  • bond2.20 décharge uniquement le VLAN 20 — les autres sous-interfaces bond2 restent sur le chemin de routage standard. Cela illustre comment décharger sélectivement un seul VLAN tout en laissant les autres sur le chemin lent.

  • La règle 200 utilise un joker pour accepter tout trafic arrivant sur toute interface de liaison ou sous-interface avant que le flux n'atteigne l'état établi et soit éligible au déchargement

  • Dès qu'un flux est établi, la règle 10 l'ajoute au flowtable et les paquets suivants évitent entièrement le hook forward via le chemin rapide

Note

Les directions d'interface dans cet exemple proviennent de la perspective du trafic client-vers-serveur. En pratique, chaque interface gère le trafic dans les deux sens, et le flowtable gère le déchargement de manière symétrique une fois le flux établi. Pour confirmer les interfaces d'ingress et d'égress, activez log sur une règle dans le hook forward et vérifiez les journaux du pare-feu — voir la section Pare-feu pour la configuration.

Identification de l'interface

Pour vérifier que VyOS identifie le trafic par sa sous-interface logique et non par le périphérique physique sous-jacent, inspectez le journal du pare-feu :

vyos@FlowTables:~$ show log firewall
Jun 18 22:22:00 kernel: [ipv4-FWD-filter-200-A] IN=bond1.10 OUT=bond2.20 \
  MAC=00:53:00:00:00:02:00:53:00:00:00:01:08:00 SRC=192.168.10.2 \
  DST=192.168.20.2 LEN=84 PROTO=ICMP TYPE=8 CODE=0 ID=3572 SEQ=1

Les champs IN et OUT montrent bond1.10 et bond2.20 — les sous-interfaces logiques — et non le périphérique physique ou le périphérique de liaison sous-jacent.

Déchargement du flowtable

Exécutez la commande suivante pour vérifier que les connexions sont déchargées vers le chemin rapide du flowtable :

vyos@FlowTables:~$ show conntrack table ipv4
Original src        Original dst       Reply src          Reply dst           Protocol    State    Timeout    Mark    Zone
------------------  -----------------  -----------------  ------------------  ----------  -------  ---------  ------  ------
192.168.10.2:45140  192.168.20.2:5201  192.168.20.2:5201  192.168.10.2:45140  tcp                  n/a        0
192.168.10.2:45124  192.168.20.2:5201  192.168.20.2:5201  192.168.10.2:45124  tcp                  n/a        0


vyos@FlowTables:~$ show conntrack table ipv4
Original src        Original dst       Reply src          Reply dst           Protocol    State      Timeout    Mark    Zone
------------------  -----------------  -----------------  ------------------  ----------  ---------  ---------  ------  ------
192.168.10.2:45124  192.168.20.2:5201  192.168.20.2:5201  192.168.10.2:45124  tcp         TIME_WAIT  105        0

Les entrées avec Timeout affiché comme n/a et un State vide confirment que les flux sont déchargés vers le chemin rapide du flowtable — les paquets suivants évitent entièrement le pare-feu. Une fois que la session TCP se ferme, l'entrée passe à TIME_WAIT et le compteur de délai reprend.
