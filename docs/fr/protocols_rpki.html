RPKI

RPKI est une architecture conçue pour sécuriser l'infrastructure de routage d'internet. Elle associe cryptographiquement les préfixes d'adresses IP aux ASNs (numéros de système autonome) corrects. Les routeurs BGP peuvent utiliser ces données pour vérifier l'origine de chaque itinéraire par rapport à la ROA (Autorisation d'origine de routage) correspondante afin de vérifier sa validité. Le RPKI est décrit dans RFC 6480.

Les routeurs BGP peuvent récupérer les informations ROA depuis le logiciel RPKI Relying Party, également appelé serveur RPKI ou validateur, en utilisant le protocole RTR. Les implémentations open source incluent Routinator (Rust) de NLnet Labs, rpki-client (C) d'OpenBSD et StayRTR (Go). Le protocole RTR est décrit dans RFC 8210.

Conseil

Si vous débutez en sécurité de routage, la Documentation RPKI maintenue par NLnet Labs vous aidera rapidement à comprendre les bases. Elle couvre tout, des concepts fondamentaux à la mise en production.

Prise en main

En premier lieu, vous devez déployer un validateur RPKI pour vos routeurs. La Documentation RPKI maintenue par NLnet Labs fournit une liste complète des logiciels open source que vous pouvez comparer et choisir. Une fois votre serveur choisi en marche, vos routeurs peuvent commencer à valider les annonces.

Après validation, les routes importées peuvent avoir l'une des états suivants :

  • valid: Le préfixe et l'ASN d'origine correspondent à une ROA signée. Ces annonces de routage sont considérées comme fiables.

  • invalid: Le préfixe, la longueur du préfixe ou l'ASN d'origine ne correspondent à aucune ROA existante. Cela peut indiquer une usurpation de préfixe ou une configuration incorrecte et doit être traité comme non fiable.

  • notfound: Aucune ROA ne couvre le préfixe. À partir du début de 2024, cela s'applique à environ 40 % à 50 % des préfixes annoncés au DFZ.

Note

Si vous gérez des adresses IP globales pour votre réseau, assurez-vous que leurs préfixes ont des ROAs associés pour éviter qu'ils ne soient marqués comme notfound par le RPKI.

Pour la plupart des opérateurs de réseau, cela implique de publier des ROAs via leur RIR, tels qu'ARIN, RIPE NCC, APNIC, LACNIC ou AFRINIC. Il est fortement recommandé de créer des ROAs pour tout préfixe d'IP que vous prévoyez d'annoncer dans le DFZ.

Les réseaux particulièrement importants peuvent choisir d'exécuter leur propre autorité de certification RPKI et serveur de publication au lieu de publier des ROAs via leur RIR. Ce sujet dépasse le cadre de la documentation VyOS. Pour plus d'informations, envisagez de consulter des ressources sur Krill.

Implémentation actuelle

L'implémentation actuelle inclut les fonctionnalités suivantes :

  • Le routeur BGP se connecte à un ou plusieurs serveurs de cache RPKI pour recevoir les mappages de préfixe à l'origine AS validés. Un basculement avancé peut être mis en œuvre en configurant plusieurs serveurs de cache avec différentes valeurs de priorité.

  • Si aucune connexion à un serveur de cache RPKI n'est établie après un délai prédéfini, le routeur traite les itinéraires sans validation de l'origine du préfixe. Il continuera à essayer de se connecter à un serveur de cache RPKI en arrière-plan.

  • Par défaut, l'activation du RPKI n'affecte pas le choix du meilleur chemin. Les préfixes invalides sont toujours pris en compte lors du choix du meilleur chemin, mais vous pouvez configurer le routeur pour les ignorer.

  • Vous pouvez configurer des cartes de route pour correspondre à un état de validation RPKI spécifique. Cela permet de créer des politiques locales qui gèrent les itinéraires BGP en fonction des résultats de la validation de l'origine des préfixes.

  • Mises à jour provenant des serveurs de cache RPKI sont appliquées directement, et le choix du chemin est mis à jour en conséquence. Remarque : la reconfiguration douce BGP doit être activée pour que cette fonctionnalité fonctionne.

Configuration

set protocols rpki polling-period <1-86400>

Configurez l'intervalle, en secondes, pendant lequel le routeur interroge le serveur de cache RPKI pour obtenir des mises à jour.

La valeur par défaut est de 300 secondes.

Exemple :

set protocols rpki polling-period 600
set protocols rpki expire-interval <600-172800>

Configurez l'intervalle, en secondes, après lequel le routeur expire ses données RPKI mises en cache.

La valeur par défaut est de 7200 secondes.

Exemple :

set protocols rpki expire-interval 14400
set protocols rpki retry-interval <1-7200>

Configurez l'intervalle, en secondes, avant lequel le routeur réessaie une connexion ratée au serveur de cache RPKI.

La valeur par défaut est de 600 secondes.

Exemple :

set protocols rpki retry-interval 60
set protocols rpki cache <address> port <1-65535>

Configurez l'adresse et le port d'un serveur de cache RPKI.

L'adresse peut être spécifiée sous forme d'une adresse IPv4 ou IPv6, ou d'un FQDN.

Note

Vous devez configurer à la fois port et preference pour chaque adresse IP du serveur de cache.

Exemple :

set protocols rpki cache 192.0.2.1 port 3323
set protocols rpki cache <address> preference <1-255>

Configurez la valeur de préférence pour un serveur de cache RPKI.

Lorsque plusieurs serveurs de cache sont configurés, le routeur privilégie la connexion au serveur ayant la plus faible valeur de préférence.

Note

Vous devez configurer à la fois port et preference pour chaque adresse IP du serveur de cache.

Note

Les valeurs de preference doivent être uniques entre les serveurs de cache.

Exemple :

set protocols rpki cache 192.0.2.1 preference 1

SSH

Vous pouvez vous connecter au serveur de cache RPKI en utilisant le protocole RTR sur TCP simple ou sur SSH. SSH offre une intégrité et une confidentialité de transport. Utilisez SSH si votre logiciel de validation le supporte.

Pour utiliser l'authentification SSH, effectuez les étapes suivantes :

Étape 1. Générez une paire de clés SSH client :

generate ssh client-key /config/auth/id_rsa_rpki

Étape 2. Extrayez la partie base64 des deux clés, ainsi que l'identificateur d'algorithme de la clé publique :

   grep -v "PRIVATE KEY" /config/auth/id_rsa_rpki | tr -d '\n'
   awk '{print $2}' /config/auth/id_rsa_rpki.pub
   awk '{print $1}' /config/auth/id_rsa_rpki.pub

Note

Le sous-système PKI accepte uniquement la partie base64 de chaque clé, sans en-têtes PEM/OpenSSH, pieds de page ou sauts de ligne. Si vous colliez le contenu du fichier directement, l'import échoue.

Étape 3. Importez la paire de clés dans le sous-système PKI :

   set pki openssh <name> private key <base64-encoded-private-key>
   set pki openssh <name> public key <base64-encoded-public-key>
   set pki openssh <name> public type <type>

Une fois la paire de clés importée, configurez la connexion SSH en utilisant les commandes ci-dessous.

set protocols rpki cache <address> ssh username <user>

Configurez le nom d'utilisateur SSH pour l'authentification au serveur de cache RPKI.

Exemple :

set protocols rpki cache 192.0.2.1 ssh username rpki-user
set protocols rpki cache <address> ssh key <name>

Configurez le nom de la paire de clés OpenSSH utilisée pour l'authentification au serveur de cache RPKI.

Le <name> doit correspondre à un nom de paire de clés défini précédemment sous les commandes set pki openssh.

Exemple :

set protocols rpki cache 192.0.2.1 ssh key rpki

Exemple

L'exemple suivant montre comment se connecter à un serveur de cache RPKI (comme Routinator) et créer une carte de route d'importation pour filtrer les préfixes en fonction de leur état de validation.

En premier lieu, configurez la connexion au serveur de cache RPKI à 192.0.2.1 :

set protocols rpki cache 192.0.2.1 port '3323'
set protocols rpki cache 192.0.2.1 preference '1'

Ensuite, créez une carte de route à appliquer à vos mises à jour BGP entrantes. Cette politique définit le comportement suivant :

  • Permet les préfixes valid et attribue une haute préférence locale (300).

  • Permet les préfixes notfound mais attribue une préférence locale plus faible (125).

  • Rejette les préfixes avec un état invalid.

set policy route-map ROUTES-IN rule 10 action 'permit'
set policy route-map ROUTES-IN rule 10 match rpki 'valid'
set policy route-map ROUTES-IN rule 10 set local-preference '300'

set policy route-map ROUTES-IN rule 20 action 'permit'
set policy route-map ROUTES-IN rule 20 match rpki 'notfound'
set policy route-map ROUTES-IN rule 20 set local-preference '125'

set policy route-map ROUTES-IN rule 30 action 'deny'
set policy route-map ROUTES-IN rule 30 match rpki 'invalid'

Après avoir configuré vos routeurs pour rejeter les préfixes RPKI invalides, vérifiez la configuration en utilisant le site web de test de Cloudflare.

Note

Assurez-vous qu'il n'y ait pas de routes par défaut ou d'autres chemins qui dirigent le trafic vers des destinations RPKI invalides. Sinon, le test pourrait indiquer que le routeur est dangereux.
