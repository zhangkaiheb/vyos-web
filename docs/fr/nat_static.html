NAT44

NAT est une méthode courante de redimensionnement d'un espace d'adresses IP en un autre en modifiant les informations d'adresse réseau dans l'en-tête IP des paquets pendant qu'ils transitent à travers un dispositif de routage de trafic. La technique a été initialement utilisée comme un raccourci pour éviter le besoin de réadresser chaque hôte lorsqu'un réseau était déplacé. Elle est devenue un outil populaire et essentiel pour conserver l'espace d'adresses global face à l'épuisement des adresses IPv4. Une adresse IP Internet routable d'une passerelle NAT peut être utilisée pour un réseau privé entier.

La masquarade IP est une technique qui cache un espace d'adresses IP, généralement composé d'adresses IP privées, derrière une seule adresse IP dans un autre espace d'adresses, généralement public. Les adresses cachées sont transformées en une seule (publique) adresse IP comme adresse source des paquets IP sortants afin qu'ils semblent provenir non pas de la machine cachée mais du dispositif de routage lui-même. En raison de la popularité de cette technique pour économiser l'espace d'adresses IPv4, le terme NAT est devenu presque synonyme de masquarade IP.

Comme la traduction d'adresse réseau modifie les informations d'adresse IP dans les paquets, les implémentations NAT peuvent varier dans leur comportement spécifique dans divers cas d'adressage et leur impact sur le trafic réseau. Les spécificités du comportement NAT ne sont pas souvent documentées par les fournisseurs d'équipements contenant des implémentations NAT.

Les ordinateurs sur un réseau interne peuvent utiliser n'importe quelle adresse définie par l'IANA pour l'adressage privé (voir RFC 1918). Ces adresses IP réservées ne sont pas utilisées sur Internet, donc une machine externe ne les routera pas directement. Les adresses suivantes sont réservées pour une utilisation privée :

  • 10.0.0.0 à 10.255.255.255 (CIDR : 10.0.0.0/8)

  • 172.16.0.0 à 172.31.255.255 (CIDR : 172.16.0.0/12)

  • 192.168.0.0 à 192.168.255.255 (CIDR : 192.168.0.0/16)

Si un FAI déploie un CGN, et utilise RFC 1918 pour numéroter les passerelles clients, le risque de collision d'adresses, et donc d'échec de routage, apparaît lorsque le réseau client utilise déjà un espace d'adresses RFC 1918.

Cela a poussé certains FAIs à développer une politique au sein de l'ARIN pour allouer un nouvel espace d'adresses privées pour les CGN, mais ARIN s'est référé à l'IETF avant d'implémenter la politique indiquant que la question n'était pas un problème d'allocation typique mais une réservation d'adresses pour des raisons techniques (selon RFC 2860).

L'IETF a publié RFC 6598, détaillant un espace d'adresses partagé à utiliser dans les déploiements de CGN des fournisseurs d'accès internet pouvant gérer les mêmes préfixes réseau sur les interfaces entrantes et sortantes. ARIN a renvoyé l'espace d'adresses à l'IANA pour cette allocation.

Le bloc d'adresses alloué est 100.64.0.0/10.

Les appareils évaluant si une adresse IPv4 est publique doivent être mis à jour pour reconnaître l'espace d'adresses nouveau. Allouer plus d'espace d'adresses IPv4 privé pour les appareils NAT pourrait prolonger la transition vers IPv6.

Aperçu

Différents types de NAT

SNAT

SNAT est la forme la plus courante de NAT et est généralement appelée simplement NAT. Pour être plus précis, ce que la plupart des gens appellent NAT est en fait le processus de PAT, ou NAT overload. SNAT est généralement utilisé par les utilisateurs internes/les hôtes privés pour accéder à Internet - l'adresse source est traduite et reste donc privée.

DNAT

DNAT change l'adresse de destination des paquets passant par le routeur, tandis que SNAT change l'adresse source des paquets. DNAT est généralement utilisé lorsqu'un hôte externe (public) doit initier une session avec un hôte interne (privé). Un client doit accéder à un service privé derrière les adresses IP publiques des routeurs. Une connexion est établie avec l'adresse IP publique du routeur sur un port bien connu et ainsi tout le trafic pour ce port est réécrit pour adresser l'hôte interne (privé).

NAT bidirectionnel

C’est une situation courante où à la fois SNAT et DNAT sont configurés en même temps. Il est couramment utilisé lorsqu’un hôte interne (privé) doit établir une connexion avec des ressources externes et que des systèmes externes doivent accéder à des ressources internes (privées).

Règles de NAT

NAT est configuré entièrement sur une série de règles appelées règles. Les règles sont numérotées et évaluées par le système d'exploitation sous-jacent dans l'ordre numérique ! Le numéro des règles peut être changé en utilisant les commandes rename et copy.

Note

Les modifications du système NAT n'affectent que les connexions nouvellement établies. Les connexions déjà établies ne sont pas affectées.

Conseil

Lors de la conception de votre ensemble de règles NAT, laissez de l'espace entre les règles consécutives pour une extension ultérieure. Votre ensemble de règles pourrait commencer par les numéros 10, 20, 30. Ainsi, vous pouvez étendre ultérieurement l'ensemble de règles et placer de nouvelles règles entre les existantes.

Des règles seront créées à la fois pour SNAT et DNAT.

Pour NAT bidirectionnel, une règle pour SNAT et DNAT doit être créée.

Filtres de trafic

Les filtres de trafic sont utilisés pour contrôler quels paquets auront les règles NAT définies appliquées. Cinq filtres différents peuvent être appliqués dans une règle NAT.

  • sortant-interface - applicable uniquement à SNAT. Il configure l'interface qui est utilisée pour le trafic sortant auquel cette règle de traduction s'applique. Les groupes d'interfaces, la sélection inversée et les caractères génériques sont également pris en charge.

    Exemples :

    set nat source rule 20 outbound-interface name eth0
set nat source rule 30 outbound-interface name bond1*
set nat source rule 20 outbound-interface name !vtun2
set nat source rule 20 outbound-interface group GROUP1
set nat source rule 20 outbound-interface group !GROUP2

  • entrant-interface - applicable uniquement à DNAT. Il configure l'interface qui est utilisée pour le trafic entrant auquel la règle de traduction s'applique. Les groupes d'interfaces, la sélection inversée et les caractères génériques sont également pris en charge.

    Exemple :

    set nat destination rule 20 inbound-interface name eth0
set nat destination rule 30 inbound-interface name bond1*
set nat destination rule 20 inbound-interface name !vtun2
set nat destination rule 20 inbound-interface group GROUP1
set nat destination rule 20 inbound-interface group !GROUP2

  • protocole - spécifier les types de protocoles auxquels cette règle de traduction s'applique. Seuls les paquets correspondant au protocole spécifié sont traduits. Par défaut, cela s'applique à tous les protocoles.

    Exemple :

    • Définir la règle SNAT 20 pour ne traduire que les paquets TCP et UDP

    • Définir la règle DNAT 20 pour ne traduire que les paquets UDP

    set nat source rule 20 protocol tcp_udp
set nat destination rule 20 protocol udp

  • source - spécifie les paquets auxquels la règle de traduction NAT s'applique en fonction de l'adresse IP source et/ou du port source des paquets. Seuls les paquets correspondants sont considérés pour la NAT.

    Exemple :

    • Définir la règle SNAT 20 pour ne NAT que les paquets arrivant du réseau 192.0.2.0/24

    • Définir la règle SNAT 30 pour ne NAT que les paquets arrivant du réseau 203.0.113.0/24 avec un port source de 80 et 443

    set nat source rule 20 source address 192.0.2.0/24
set nat source rule 30 source address 203.0.113.0/24
set nat source rule 30 source port 80,443

  • destination - spécifier les paquets auxquels la traduction sera appliquée, uniquement en fonction de l'adresse et/ou du port de destination configurés.

    Note

    Si aucune destination n'est spécifiée, la règle matchera toutes les adresses et ports de destination.

    Exemple :

    • Configurer la règle SNAT (40) pour ne NAT que les paquets ayant une adresse de destination de 192.0.2.1.

    set nat source rule 40 destination address 192.0.2.1

Conversion d'adresse

Chaque règle NAT a une commande de traduction définie. L'adresse définie pour la traduction est l'adresse utilisée lorsqu'informations d'adresse d'un paquet sont remplacées.

Adresse source

Pour les règles SNAT, l'adresse source des paquets sera remplacée par l'adresse spécifiée dans la commande de traduction. Une traduction de port peut également être spécifiée et fait partie de l'adresse de traduction.

Note

L'adresse de traduction doit être définie à l'une des adresses disponibles sur l'interface sortant configurée ou elle doit être définie à masquerade, qui utilisera l'adresse IP principale de l'interface sortant comme adresse de traduction.

Note

Lors de l'utilisation de NAT pour un grand nombre de systèmes hôte, il est recommandé d'utiliser un minimum de 1 adresse IP pour NAT chaque 256 systèmes hôte privés. Cela est dû à la limite de 65 000 numéros de port disponibles pour des traductions uniques et une réserve moyenne de 200-300 sessions par système hôte.

Exemple :

  • Définir une adresse IP source discrète de 100.64.0.1 pour la règle SNAT 20

  • Utiliser l'adresse masquerade (l'adresse principale de l'interface) sur la règle 30

  • Pour un grand nombre de machines privées derrière le NAT, votre pool d'adresses pourrait être plus important. Utilisez toute adresse dans la plage 100.64.0.10 - 100.64.0.20 sur la règle SNAT 40 lors de la traduction

set nat source rule 20 translation address 100.64.0.1
set nat source rule 30 translation address 'masquerade'
set nat source rule 40 translation address 100.64.0.10-100.64.0.20

Adresse de destination

Pour les règles DNAT, l'adresse de destination des paquets sera remplacée par l'adresse spécifiée dans la commande translation address.

Exemple :

  • La règle DNAT 10 remplace l'adresse de destination d'un paquet entrant par 192.0.2.10

set nat destination rule 10 translation address 192.0.2.10

De plus, dans DNAT, la redirection vers localhost est prise en charge. La commande de redirigement est une forme particulière de dnats qui traduit toujours l'adresse de destination vers celle de l'hôte local.

Exemple de redirection :

set nat destination rule 10 translation redirect port 22

Équilibrage de charge NAT

Une configuration avancée peut être utilisée afin d'appliquer le NAT source ou destination, et dans une seule règle, définir plusieurs adresses traduites, de sorte que le NAT équilibre les traductions entre elles.

L'équilibrage de charge NAT utilise un algorithme qui génère un hachage et, en fonction de celui-ci, applique la traduction correspondante. Ce hachage peut être généré aléatoirement, ou peut utiliser des données de l'en-tête IP : adresse source, adresse destination, port source et/ou port destination. Par défaut, il générera le hachage aléatoirement.

Lors de la définition de l'adresse traduite, appelée backends, un weight doit être configuré. Cela permet à l'utilisateur de définir la distribution d'équilibrage de charge selon leurs besoins. La somme de tous les poids définis pour les backends doit être égale à 100. Autrement dit, le poids défini pour le backend est le pourcentage de connexions qui recevront ce backend.

set nat [source | destination] rule <rule> load-balance hash [source-address | destination-address | source-port | destination-port | random]
set nat [source | destination] rule <rule> load-balance backend <x.x.x.x> weight <1-100>

Exemples de configuration

Pour configurer le SNAT, nous avons besoin de savoir :

  • Les adresses IP internes que nous voulons traduire

  • L'interface de sortie à utiliser pour effectuer la traduction

  • L'adresse IP externe vers laquelle traduire

Dans l'exemple utilisé pour la configuration rapide ci-dessus, nous démontrons la configuration suivante :

set nat source rule 100 outbound-interface name 'eth0'
set nat source rule 100 source address '192.168.0.0/24'
set nat source rule 100 translation address 'masquerade'

Cela génère la configuration suivante :

rule 100 {
    outbound-interface {
        name eth0
    }
    source {
        address 192.168.0.0/24
    }
    translation {
        address masquerade
    }
}

Dans cet exemple, nous utilisons masquerade comme adresse de traduction au lieu d'une adresse IP. L'objectif de masquerade est en fait un alias pour dire « utilisez l'adresse IP qui se trouve sur l'interface de sortie », plutôt qu'une adresse IP configurée statiquement. Cela est utile si vous utilisez DHCP pour votre interface de sortie et que vous ne savez pas quelle sera l'adresse externe.

Lors de l'utilisation du NAT pour un grand nombre de systèmes hôte, il est recommandé d'utiliser un minimum de 1 adresse IP pour NAT chaque 256 systèmes hôte. Cela est dû à la limite de 65 000 numéros de port disponibles pour des traductions uniques et à la réserve moyenne de 200-300 sessions par système hôte.

Exemple : Pour un réseau de ~8 000 hôtes, un pool de 32 adresses IP est recommandé.

Un pool d'adresses peut être défini en utilisant un tiret entre deux adresses IP :

set nat source rule 100 translation address '203.0.113.32-203.0.113.63'

Éviter le NAT "leaky"

Le netfilter Linux ne NAT pas le trafic marqué comme INVALID. Cela confond souvent les gens en pensant que Linux (ou spécifiquement VyOS) a une implementation de NAT cassée car le trafic non NATé est vu sortant d'une interface externe. Cela fonctionne en réalité comme prévu, et une capture de paquet du trafic "leaky" devrait révéler que le trafic est soit un supplémentaire TCP "RST", "FIN,ACK", ou "RST,ACK" envoyé par les systèmes clients après que Linux netfilter considère la connexion fermée. Le plus commun est le supplémentaire TCP RST que certains implémentations d'hôte envoient après la fermeture d'une connexion (ce qui est spécifique à l'implémentation).

En d'autres termes, le suivi des connexions a déjà observé la fermeture de la connexion et a transféré le flux à INVALID pour empêcher les attaques tentant de réutiliser la connexion.

Vous pouvez éviter le comportement "leaky" en utilisant une politique de pare-feu qui supprime les paquets d'état "invalid".

Avoir le contrôle de la correspondance du trafic d'état "invalid", par exemple, la capacité à journaliser sélectivement, est un outil important pour observer un comportement de protocole défectueux. Pour cette raison, VyOS ne supprime pas globalement le trafic d'état invalid, mais permet à l'opérateur de déterminer comment le trafic est géré.

Hairpin NAT/NAT Reflection

Un problème typique avec l'utilisation de NAT et de serveurs publics est la capacité des systèmes internes à atteindre un serveur interne en utilisant son adresse IP externe. La solution à cela est généralement l'utilisation de DNS séparé pour pointer correctement les systèmes hôtes vers l'adresse interne lorsqu'ils font des demandes internes. Comme beaucoup de petits réseaux manquent d'infrastructure DNS, un contournement est souvent déployé pour faciliter le trafic en NATant la demande des hôtes internes vers l'adresse source de l'interface interne du pare-feu.

Cette technique est couramment appelée NAT Reflection ou Hairpin NAT.

Exemple :

  • Rediriger le trafic RDP Microsoft depuis le monde externe (WAN, externe) via DNAT dans la règle 100 vers l'hôte privé interne 192.0.2.40.

  • Rediriger le trafic RDP Microsoft depuis le réseau interne (LAN, privé) via DNAT dans la règle 110 vers l'hôte privé interne 192.0.2.40. Nous avons également besoin d'une règle SNAT 110 pour le chemin inverse du trafic. Le réseau interne 192.0.2.0/24 est accessible via l'interface eth0.10.

set nat destination rule 100 description 'Regular destination NAT from external'
set nat destination rule 100 destination port '3389'
set nat destination rule 100 inbound-interface name 'pppoe0'
set nat destination rule 100 protocol 'tcp'
set nat destination rule 100 translation address '192.0.2.40'

set nat destination rule 110 description 'NAT Reflection: INSIDE'
set nat destination rule 110 destination port '3389'
set nat destination rule 110 inbound-interface name 'eth0.10'
set nat destination rule 110 protocol 'tcp'
set nat destination rule 110 translation address '192.0.2.40'

set nat source rule 110 description 'NAT Reflection: INSIDE'
set nat source rule 110 destination address '192.0.2.0/24'
set nat source rule 110 outbound-interface name 'eth0.10'
set nat source rule 110 protocol 'tcp'
set nat source rule 110 source address '192.0.2.0/24'
set nat source rule 110 translation address 'masquerade'

Cela donne une configuration de :

         }

 }

NAT de destination

DNAT est généralement appelé Redirection de port. Lorsque VyOS est utilisé comme routeur et pare-feu NAT, une tâche de configuration courante est de rediriger le trafic entrant vers un système derrière le pare-feu.

Dans cet exemple, nous utiliserons la configuration Quick Start ci-dessus comme point de départ.

Pour configurer une règle NAT de destination, nous devons rassembler :

  • L'interface par laquelle le trafic arrivera ;

  • Le protocole et le port que nous souhaitons rediriger ;

  • L'adresse IP du système interne vers lequel nous souhaitons rediriger le trafic.

Dans notre exemple, nous redirigeons le trafic du serveur web vers un serveur web interne sur 192.168.0.100. Le trafic HTTP utilise le protocole TCP sur le port 80. Pour d'autres numéros de port courants, voir : https://en.wikipedia.org/wiki/List_of_TCP_and_UDP_port_numbers

Nos commandes de configuration seraient :

set nat destination rule 10 description 'Port Forward: HTTP to 192.168.0.100'
set nat destination rule 10 destination port '80'
set nat destination rule 10 inbound-interface name 'eth0'
set nat destination rule 10 protocol 'tcp'
set nat destination rule 10 translation address '192.168.0.100'

Cela génère la configuration NAT suivante :

nat {
    destination {
        rule 10 {
            description "Port Forward: HTTP to 192.168.0.100"
            destination {
                port 80
            }
            inbound-interface {
                name eth0
            }
            protocol tcp
            translation {
                address 192.168.0.100
            }
        }
    }
}

Note

Si vous redirigez le trafic vers un port différent de celui sur lequel il arrive, vous pouvez également configurer le port de traduction en utilisant set nat destination rule [n] translation port.

Cela établit notre règle de redirection de port, mais si nous avons créé une politique de pare-feu, elle bloquera probablement le trafic.

Règles de pare-feu pour NAT de destination

Il est important de noter que lors de la création de règles de pare-feu, la traduction DNAT se produit avant que le trafic ne traverse le pare-feu. En d'autres termes, l'adresse de destination a déjà été traduite en 192.168.0.100.

Ainsi, dans notre ensemble de règles de pare-feu, nous voulons autoriser le trafic qui correspondait précédemment à une règle de NAT de destination. Pour éviter de créer de nombreuses règles, une pour chaque règle de NAT de destination, nous pouvons accepter toutes les connexions ‘dnat’ avec une seule règle simple, en utilisant le matcheur connection-status :

set firewall ipv4 forward filter rule 10 action accept
set firewall ipv4 forward filter rule 10 connection-status nat destination
set firewall ipv4 forward filter rule 10 state new

Cela génère la configuration suivante :

ipv4 {
    forward {
        filter {
            rule 10 {
                action accept
                connection-status {
                    nat destination
                }
                state new
            }
        }
    }
}

NAT 1-to-1

Un autre terme souvent utilisé pour le DNAT est NAT 1-to-1. Pour une configuration NAT 1-to-1, à la fois le DNAT et le SNAT sont utilisés pour NATer tout le trafic d'une adresse IP externe vers une adresse IP interne et vice versa.

Généralement, une règle NAT 1-to-1 omet le port de destination (tous les ports) et remplace le protocole par soit tous soit ip.

Ensuite, une règle SNAT correspondante est créée pour NATer le trafic sortant pour l'IP interne vers une adresse IP externe réservée. Cela dédie une adresse IP externe à une adresse IP interne et est utile pour les protocoles qui n'ont pas le concept de ports, tels que GRE.

Voici un extrait d'une configuration NAT 1-to-1 simple avec une interface interne et une interface externe :

set interfaces ethernet eth0 address '192.168.1.1/24'
set interfaces ethernet eth0 description 'Interface intérieure'
set interfaces ethernet eth1 address '192.0.2.30/24'
set interfaces ethernet eth1 description 'Interface extérieure'
set nat destination rule 2000 description 'Exemple de NAT 1-to-1'
set nat destination rule 2000 destination address '192.0.2.30'
set nat destination rule 2000 inbound-interface name 'eth1'
set nat destination rule 2000 translation address '192.168.1.10'
set nat source rule 2000 description 'Exemple de NAT 1-to-1'
set nat source rule 2000 outbound-interface name 'eth1'
set nat source rule 2000 source address '192.168.1.10'
set nat source rule 2000 translation address '192.0.2.30'

Les règles de pare-feu sont écrites normalement, en utilisant l'adresse IP interne comme source des règles sortantes et la destination des règles entrantes.

NAT avant le VPN

Certains fournisseurs de services d'application (ASPs) opèrent un passerelle VPN pour fournir un accès à leurs ressources internes, et exigent que les connexions d'une organisation soient traduites vers une adresse source fournie par l'ASP.

Équilibrage de charge

Ici, nous fournissons deux exemples sur la façon d'appliquer l'équilibrage de charge NAT.

Première scène : appliquer le NAT de destination pour tout le trafic HTTP venant de l'interface eth0, et utiliser 4 backends. Le premier backend devrait recevoir 30% des requêtes, le deuxième 20%, le troisième 15% et le quatrième 35%. Nous utiliserons l'adresse source et la destination pour générer le hachage.

set nat destination rule 10 inbound-interface name eth0
set nat destination rule 10 protocol tcp
set nat destination rule 10 destination port 80
set nat destination rule 10 load-balance hash source-address
set nat destination rule 10 load-balance hash destination-address
set nat destination rule 10 load-balance backend 198.51.100.101 weight 30
set nat destination rule 10 load-balance backend 198.51.100.102 weight 20
set nat destination rule 10 load-balance backend 198.51.100.103 weight 15
set nat destination rule 10 load-balance backend 198.51.100.104 weight 35

Deuxième scénario : appliquer le NAT source pour toutes les connexions sortantes du LAN 10.0.0.0/8, en utilisant 3 adresses publiques et une distribution égale. Nous générerons le hachage aléatoirement.

set nat source rule 10 outbound-interface name eth0
set nat source rule 10 source address 10.0.0.0/8
set nat source rule 10 load-balance hash random
set nat source rule 10 load-balance backend 192.0.2.251 weight 33
set nat source rule 10 load-balance backend 192.0.2.252 weight 33
set nat source rule 10 load-balance backend 192.0.2.253 weight 34

Réseau d'exemple

Voici un exemple de réseau pour un ASP. L'ASP demande que toutes les connexions de cette entreprise proviennent de 172.29.41.89 - une adresse assignée par l'ASP et non utilisée sur le site client.

Configuration

La configuration requise peut être divisée en 4 parties principales :

  • Une interface dummy pour l'adresse attribuée par le fournisseur ;

  • NAT (spécifiquement, NAT source) ;

  • Groupes IKE et ESP IPSec ;

  • Tunnels IPSec.

Interface dummy

L'interface dummy permet d'avoir une équivalence de l'interface Loopback de Cisco - une interface interne du routeur que nous pouvons utiliser pour des adresses IP que le routeur doit connaître, mais qui ne sont pas réellement attribuées à un réseau réel.

Nous n'avons besoin qu'étape unique pour cette interface :

set interfaces dummy dum0 address '172.29.41.89/32'
Configuration NAT
set nat source rule 110 description 'Internal to ASP'
set nat source rule 110 destination address '172.27.1.0/24'
set nat source rule 110 source address '192.168.43.0/24'
set nat source rule 110 translation address '172.29.41.89'
set nat source rule 120 description 'Internal to ASP'
set nat source rule 120 destination address '10.125.0.0/16'
set nat source rule 120 source address '192.168.43.0/24'
set nat source rule 120 translation address '172.29.41.89'
IKE et ESP IPSec

L'ASP a documenté ses exigences IPSec :

  • Phase IKE :

    • Chiffrement aes256

    • Hashes sha256

  • Phase ESP :

    • Chiffrement aes256

    • Hashes sha256

    • Groupe DH 14

En outre, nous voulons utiliser des VPN uniquement sur notre interface eth1 (l'interface externe dans l'image ci-dessus)

set vpn ipsec ike-group my-ike key-exchange 'ikev1'
set vpn ipsec ike-group my-ike lifetime '7800'
set vpn ipsec ike-group my-ike proposal 1 dh-group '14'
set vpn ipsec ike-group my-ike proposal 1 encryption 'aes256'
set vpn ipsec ike-group my-ike proposal 1 hash 'sha256'

set vpn ipsec esp-group my-esp lifetime '3600'

Tunnels VPN IPSec

Nous utiliserons les groupes IKE et ESP créés ci-dessus pour ce VPN. Comme nous avons besoin d'accéder à 2 sous-réseaux différents de l'autre côté, nous aurons besoin de deux tunnels différents. Si vous avez changé les noms des groupes ESP et IKE à l'étape précédente, assurez-vous d'utiliser les bons noms ici aussi.

set vpn ipsec authentication psk vyos id '203.0.113.46'
set vpn ipsec authentication psk vyos id '198.51.100.243'
set vpn ipsec authentication psk vyos secret 'MYSECRETPASSWORD'
set vpn ipsec site-to-site peer branch authentication local-id '203.0.113.46'
set vpn ipsec site-to-site peer branch authentication mode 'pre-shared-secret'
set vpn ipsec site-to-site peer branch authentication remote-id '198.51.100.243'
set vpn ipsec site-to-site peer branch connection-type 'initiate'
set vpn ipsec site-to-site peer branch default-esp-group 'my-esp'
set vpn ipsec site-to-site peer branch ike-group 'my-ike'
set vpn ipsec site-to-site peer branch ikev2-reauth 'inherit'
set vpn ipsec site-to-site peer branch local-address '203.0.113.46'
set vpn ipsec site-to-site peer branch remote-address '198.51.100.243'
set vpn ipsec site-to-site peer branch tunnel 0 local prefix '172.29.41.89/32'
set vpn ipsec site-to-site peer branch tunnel 0 remote prefix '172.27.1.0/24'
set vpn ipsec site-to-site peer branch tunnel 1 local prefix '172.29.41.89/32'
set vpn ipsec site-to-site peer branch tunnel 1 remote prefix '10.125.0.0/16'
