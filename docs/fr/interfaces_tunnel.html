Tunnel

Les interfaces de tunnel sont des liens virtuels qui transmettent du trafic encapsulé entre des réseaux privés ou des hôtes via une infrastructure publique, telle qu'Internet. Elles fonctionnent en utilisant des protocoles d'encapsulation pour envelopper le trafic original pour le transport. Les protocoles pris en charge comprennent GRE, IPIP, IPIP6, IP6IP6 et 6in4 (SIT).

Alors que GRE est souvent la solution idéale universelle en raison de sa flexibilité, d'autres protocoles d'encapsulation peuvent être plus adaptés à des cas d'utilisation spécifiques.

VyOS utilise un seul type d'interface de tunnel pour tous ces protocoles. Il n'y a pas de types d'interfaces séparés pour GRE, IPIP ou IP6IP6 ; au lieu de cela, le protocole d'encapsulation souhaité est sélectionné dans la configuration set interfaces tunnel.

Les options de configuration pour chaque protocole sont décrites ci-dessous.

Avertissement

Ne modifiez pas le type d'encapsulation pour les interfaces de tunnel déjà configurées, car cela peut perturber leurs configurations dépendantes.

Configuration commune de l'interface

set interfaces tunnel <interface> address <address>

Configurez une ou plusieurs adresses IP d'interface.

<address> prend en charge IPv4 et IPv6 en notation CIDR. Par exemple, utilisez 192.0.2.1/24 pour IPv4 ou 2001:db8::1/64 pour IPv6.

Exemple :

set interfaces tunnel tun0 address 192.0.2.1/24
set interfaces tunnel tun0 address 2001:db8::1/64
set interfaces tunnel <interface> description <description>

Configurez un alias clair et descriptif pour l'interface.

Cet alias apparaît dans la commande show interfaces et les outils de surveillance basés sur SNMP.

Exemple :

set interfaces tunnel tun0 description 'This is an interface running on VyOS.'
set interfaces tunnel <interface> disable

Désactivez l'interface.

L'interface sera définie sur l'état administrativement down (A/D).

Exemple :

set interfaces tunnel tun0 disable
set interfaces tunnel <interface> disable-flow-control

Désactivez le contrôle de flux Ethernet (IEEE 802.3x pause frames) sur l'interface.

Le contrôle de flux Ethernet, défini par le standard IEEE 802.3x, temporairement arrête la transmission de données pour éviter la perte de paquets lors de la congestion réseau. Par exemple, lorsque l'émetteur transmet des données plus rapidement que le récepteur ne peut les traiter.

La désactivation du contrôle de flux Ethernet signifie que l'interface ne signalera pas à l'appareil connecté de suspendre la transmission et supprimera les paquets si elle est submergée.

Exemple :

set interfaces tunnel tun0 disable-flow-control
set interfaces tunnel <interface> disable-link-detect

Désactivez la détection d'état physique de lien sur l'interface, comme lorsque un câble est débranché.

Par défaut, l'interface détecte les changements d'état physique du lien.

Exemple :

set interfaces tunnel tun0 disable-link-detect
set interfaces tunnel <interface> mtu <mtu>

Configurez le MTU sur l'interface.

Cette valeur définit la taille maximale du paquet, en octets, que l'interface transmet sans fragmentation.

Exemple :

set interfaces tunnel tun0 mtu 1600
set interfaces tunnel <interface> ip adjust-mss <mss | clamp-mss-to-pmtu>

Configurez la MSS annoncée dans les paquets TCP SYN sortants sur l'interface spécifiée.

En limitant la valeur de la MSS dans les paquets TCP SYN, vous informez explicitement l'autre côté qu'il ne doit pas envoyer de paquets plus grands que cette taille. Cela empêche les problèmes de connexion qui surviennent lorsqu'une découverte de MTU de chemin échoue.

Les options suivantes sont disponibles :

  • mss : Définit la MSS à une valeur spécifique, en octets. Utilisez cette option si vous avez besoin d'imposer une MSS spécifique, par exemple pour résoudre des problèmes de connectivité ou satisfaire des exigences réseau spécifiques.

  • clamp-mss-to-pmtu : Le routeur calcule automatiquement la MSS à être la MTU de l'interface moins 40 octets pour le trafic IPv4 (20 octets pour l'en-tête IPv4 et 20 octets pour l'en-tête TCP). Cette option est recommandée pour configurer automatiquement la bonne valeur.

set interfaces tunnel <interface> ip arp-cache-timeout

Configurez pendant combien de temps un enregistrement ARP reste valide après avoir appris une correspondance IP-MAC sur cette interface.

La durée par défaut est de 30 secondes.

Un enregistrement ARP reste valide s'il reçoit un feedback positif des protocoles de niveau supérieur.

Exemple :

set interfaces tunnel tun0 ip arp-cache-timeout 180
set interfaces tunnel <interface> ip disable-arp-filter

Configurez le filtrage ARP sur cette interface.

Comportement par défaut : Le noyau répond aux demandes ARP sur cette interface uniquement si le trafic serait routé de retour à l'expéditeur ARP via cette interface spécifique.

Si configuré : Le noyau répond aux demandes ARP sur cette interface pour toute adresse IP configurée sur l'hôte local, indépendamment de l'interface spécifique à laquelle cette adresse IP est assignée, et indépendamment de la table de routage. Cela reflète le concept Linux selon lequel les adresses IP appartiennent à l'hôte, et non aux interfaces individuelles.

Exemple :

set interfaces tunnel tun0 ip disable-arp-filter
set interfaces tunnel <interface> ip disable-forwarding

Configurez l'interface pour un comportement d'hôte ou de routeur.

Si configuré, l'interface passe en mode hôte, et le transfert IPv4 est désactivé sur celle-ci.

Exemple :

set interfaces tunnel tun0 ip disable-forwarding
set interfaces tunnel <interface> ip enable-directed-broadcast

Configurez si les paquets broadcast directs IP reçus sur cette interface doivent être transmis.

Comportement par défaut : Les paquets broadcast directs IP sont supprimés.

Si configuré : Les paquets broadcast directs IP sont transmis à tous les hôtes sur le sous-réseau de destination, conformément à RFC 1812 et RFC 2644.

Exemple :

set interfaces tunnel tun0 ip enable-directed-broadcast
set interfaces tunnel <interface> ip enable-arp-accept

Configurez comment traiter les ARPs gratuit sur cette interface.

Si configuré, une correspondance IP-MAC est ajoutée au tableau ARP en fonction des demandes ou réponses ARP gratuit.

Note

Si le tableau ARP contient déjà l'adresse IP provenant d'un ARP gratuit, son entrée est mise à jour, indépendamment de la configuration de ce paramètre.

Exemple :

set interfaces tunnel tun0 ip enable-arp-accept
set interfaces tunnel <interface> ip enable-arp-announce

Configurez la sélection de l'adresse IP source pour les demandes ARP sur cette interface.

Comportement par défaut : Le noyau peut utiliser n'importe quelle adresse IP possédée par l'hôte comme adresse IP source dans les demandes ARP sur cette interface.

Si configuré : Le noyau essaie d'abord de sélectionner une adresse IP configurée sur l'interface partageant un sous-réseau commun avec l'adresse IP cible. Si aucun tel sous-réseau n'existe, le noyau sélectionne l'adresse IP qu'il utiliserait normalement (en fonction de la table de routage pour atteindre la destination cible).

Exemple :

set interfaces tunnel tun0 ip enable-arp-announce
set interfaces tunnel <interface> ip enable-arp-ignore

Configurez quelles demandes ARP seront ignorées sur cette interface.

Comportement par défaut : Le noyau répond aux demandes ARP pour toutes les adresses IP locales, indépendamment de l'interface à laquelle elles sont assignées.

Si configuré : Le noyau répond aux demandes ARP uniquement si l'adresse IP cible est assignée à cette interface spécifique.

Exemple :

set interfaces tunnel tun0 ip enable-arp-ignore
set interfaces tunnel <interface> ip enable-proxy-arp

Configurez le proxy ARP sur cette interface.

Si configuré, le routeur (noyau) intercepte les demandes ARP pour des adresses IP non locales et répond avec l'adresse MAC de l'interface qui a reçu la demande. Les paquets suivants destinés à ces adresses IP sont ensuite transmis vers leurs destinations réelles sur des sous-réseaux distants.

Exemple :

set interfaces tunnel tun0 ip enable-proxy-arp
set interfaces tunnel <interface> ip proxy-arp-pvlan

Configurez le proxy ARP local sur l'interface.

Si configuré, le routeur (noyau) répond aux demandes ARP sur cette interface VLAN même si l'adresse IP cible se trouve sur le même sous-réseau et interface.

Cela est utilisé pour soutenir les exigences de séparation réseau (RFC 3069) pour les VLAN privés (PVLANs). Dans les configurations PVLAN, les hôtes sur des ports isolés ne sont PAS autorisés à communiquer directement entre eux au niveau 2, mais ils peuvent communiquer avec le routeur supérieur.

En répondant aux demandes ARP inter-hôtes avec sa propre adresse MAC, le routeur (noyau) dirige le trafic inter-hôtes via lui-même plutôt que directement entre les hôtes.

Note

Cette commande fonctionne indépendamment et ne nécessite pas l'activation du proxy ARP standard sur l'interface.

Le proxy ARP local est également connu sous les noms suivants :

  • Aggregation de VLAN (RFC 3069).

  • VLAN privé (Cisco, Allied Telesyn).

  • Filtrage de port source ou isolation de port (Hewlett-Packard).

  • Transfert forcé MAC (Ericsson).

set interfaces tunnel <interface> ip source-validation <strict | loose | disable>

Configurez la validation de l'adresse IP source en utilisant RPF sur cette interface, comme spécifié dans RFC 3704.

Les options suivantes sont disponibles :

  • strict : Chaque adresse IP source des paquets entrants est vérifiée contre la FIB. Si l'interface n'est pas le meilleur chemin de retour vers cette source, la validation échoue et le paquet est supprimé.

  • loose : Chaque adresse IP source des paquets entrants est vérifiée contre la FIB. Si l'adresse IP source est inatteignable via n'importe quelle interface, la validation échoue.

  • disable : Aucune validation d'adresse IP source n'est effectuée. Tous les paquets entrants sont acceptés.

Le RFC 3704 recommande d'activer le mode strict pour empêcher la falsification d'IP, comme les attaques DDoS. Pour les scénarios de routage asynchrones ou autres scénarios complexes, utilisez le mode loose.

set interfaces tunnel <interface> ipv6 address autoconf

Configurez l'interface pour obtenir automatiquement une adresse IPv6 à l'aide de SLAAC, comme spécifié dans RFC 4862.

Les hôtes IPv6 peuvent se configurer automatiquement lorsqu'ils sont connectés à un réseau IPv6 à l'aide du protocole de découverte de voisins via des messages ICMPv6 de découverte de routeur. Lorsqu'ils se connectent pour la première fois à un réseau, un hôte envoie une demande multicast de demande de routeur link-local pour ses paramètres de configuration. Le routeur répond avec un paquet d'annonce de routeur contenant les paramètres de configuration du niveau Internet.

Note

Cette méthode désactive automatiquement le transfert de trafic IPv6 sur l'interface.

Exemple :

set interfaces tunnel tun0 ipv6 address autoconf
set interfaces tunnel <interface> ipv6 address eui64 <prefix>

Configurez l'interface pour lui attribuer une adresse IPv6 à l'aide de la méthode EUI-64 , comme spécifié dans RFC 4291.

Exemple :

set interfaces tunnel tun0 ipv6 address eui64 2001:db8:beef::/64
set interfaces tunnel <interface> ipv6 address no-default-link-local

Désactivez l'attribution automatique d'une adresse IPv6 link-local à cette interface.

Exemple :

set interfaces tunnel tun0 ipv6 address no-default-link-local
set interfaces tunnel <interface> ipv6 disable-forwarding

Configurez l'interface pour un comportement d'hôte ou de routeur.

Si configuré, l'interface passe en mode hôte, et le transfert IPv6 est désactivé sur celle-ci.

Exemple :

set interfaces tunnel tun0 ipv6 disable-forwarding
set interfaces tunnel <interface> ipv6 adjust-mss <mss | clamp-mss-to-pmtu>

Configurez la MSS annoncée dans les paquets TCP SYN sortants sur l'interface spécifiée.

En limitant la valeur de la MSS dans les paquets TCP SYN, vous informez explicitement l'autre côté qu'il ne doit pas envoyer de paquets plus grands que cette taille. Cela empêche les problèmes de connexion lorsqu'une découverte de MTU de chemin échoue.

Les options suivantes sont disponibles :

  • mss : Définissez la MSS à une valeur spécifique, en octets. Utilisez cette option pour imposer une MSS spécifique, par exemple pour résoudre des problèmes de connectivité ou satisfaire des exigences réseau spécifiques.

  • clamp-mss-to-pmtu : Le routeur calcule la MSS à être la MTU de l'interface moins 60 octets pour le trafic IPv6 (40 octets pour l'en-tête IPv6 et 20 octets pour l'en-tête TCP). Cette option est recommandée pour configurer automatiquement la bonne valeur.

set interfaces tunnel <interface> ipv6 accept-dad <0 | 1 | 2>

Configurez le DAD IPv6 sur l'interface.

Les options suivantes sont disponibles :

  • 0 : Désactive le DAD. Aucune détection de duplication d'adresse n'est effectuée.

  • 1 : Active le DAD (par défaut). Les adresses dupliquées sont détectées. L'opération IPv6 de l'interface continue pour les adresses IPv6 valides.

  • 2 : Active le DAD et, si une adresse link-local dupliquée basée sur le MAC est trouvée, désactive l'opération IPv6 sur cette interface.

Exemple :

set interfaces tunnel tun0 ipv6 accept-dad 2
set interfaces tunnel <interface> ipv6 dup-addr-detect-transmits <n>

Configurez le nombre de DAD messages que le routeur (noyau) envoie pendant l'attribution d'adresse IPv6 sur cette interface.

La valeur par défaut est 1.

Exemple :

set interfaces tunnel tun0 ipv6 dup-addr-detect-transmits 5
set interfaces tunnel <interface> vrf <vrf>

Assignez l'interface à une instance spécifique de VRF .

Voir aussi

Pour plus d'informations sur la configuration d'un VRF, consultez la section VRF.

Exemple :

set interfaces tunnel tun0 vrf red

IPIP

IPIP est un protocole d'encapsulation simple défini dans le RFC 2003. Il encapsule un paquet IPv4 dans un autre paquet IPv4.

Les tunnels avec l'encapsulation IPIP n'ont pas d'options de configuration spécifiques au protocole, à l'exception de la définition explicite du type d'encapsulation comme IPIP (voir l'exemple ci-dessous).

Exemple :

set interfaces tunnel tun0 encapsulation ipip
set interfaces tunnel tun0 source-address 192.0.2.10
set interfaces tunnel tun0 remote 203.0.113.20
set interfaces tunnel tun0 address 192.168.100.200/24

IP6IP6

IP6IP6 est le counterpart IPv6 de IPIP. Il encapsule un paquet IPv6 dans un autre paquet IPv6.

De la même manière que leurs homologues IPIP, les tunnels avec l'encapsulation IP6IP6 n'ont pas d'options de configuration spécifiques au protocole, à l'exception de la définition explicite du type d'encapsulation comme IP6IP6.

Exemple :

set interfaces tunnel tun0 encapsulation ip6ip6
set interfaces tunnel tun0 source-address 2001:db8:aa::1
set interfaces tunnel tun0 remote 2001:db8:aa::2
set interfaces tunnel tun0 address 2001:db8:bb::1/64

IPIP6

IPIP6 est un protocole d'encapsulation qui enveloppe les paquets IPv4 dans des paquets IPv6.

De la même manière qu'IPIP et IP6IP6, la configuration spécifique au protocole pour les tunnels avec l'encapsulation IPIP6 n'exige que la définition du type d'encapsulation comme IP6IP6.

Exemple :

set interfaces tunnel tun0 encapsulation ipip6
set interfaces tunnel tun0 source-address 2001:db8:aa::1
set interfaces tunnel tun0 remote 2001:db8:aa::2
set interfaces tunnel tun0 address 192.168.70.80/24

6in4 (SIT)

6in4, également appelé SIT, est un protocole d'encapsulation défini dans RFC 4213 qui enveloppe les paquets IPv6 dans des paquets IPv4. Les en-têtes IPv4 de l'encapsulation utilisent le numéro de protocole IP 41, qui est exclusivement réservé à l'encapsulation IPv6.

Le processus d'encapsulation ajoute un en-tête IPv4 de 20 octets à chaque paquet IPv6. En conséquence, les interfaces de tunnel 6in4 peuvent transmettre des paquets IPv6 de jusqu'à 1480 octets sur un réseau sous-jacent avec une MTU standard de 1500 octets sans fragmentation.

Les interfaces de tunnel 6in4 sont fréquemment utilisées par les fournisseurs de tunnels IPv6 (tels que Hurricane Electric) pour connecter des réseaux IPv6 isolés ou des hôtes individuels à Internet IPv6.

Exemple :

set interfaces tunnel tun0 encapsulation sit
set interfaces tunnel tun0 source-address 192.0.2.10
set interfaces tunnel tun0 remote 192.0.2.20
set interfaces tunnel tun0 address 2001:db8:bb::1/64

Voir aussi

Pour un exemple de configuration pratique, voir la section Tunnelbroker.net (IPv6).

Encapsulation de Routage Général (GRE)

GRE est un protocole d'encapsulation polyvalent défini dans le RFC 2784. Contrairement à des protocoles plus simples tels que IPIP, il permet le transport à la fois de IPv4 et IPv6 à travers le même tunnel.

GRE encapsule les paquets de données originaux en ajoutant un en-tête GRE, suivi d'un en-tête IP (l'en-tête de livraison). L'en-tête de livraison utilise le numéro de protocole IP 47 pour identifier le trafic encapsulé GRE.

Dans VyOS, les tunnels GRE peuvent être établis sur des réseaux de transport IPv4 (encapsulation gre) et IPv6 (encapsulation ip6gre).

Configuration

Pour configurer un tunnel GRE, vous devez définir une adresse IP source de tunnel, une adresse IP de destination de tunnel, un type d'encapsulation (GRE) et une adresse IP d'interface de tunnel.

Exemple :

L'exemple suivant montre comment configurer un tunnel GRE IPv4/IPv6 sur IPv6 entre un routeur VyOS et un hôte Linux exécutant systemd-networkd.

Routeur VyOS :

set interfaces tunnel tun101 address '2001:db8:feed:beef::1/126'
set interfaces tunnel tun101 address '192.168.5.1/30'
set interfaces tunnel tun101 encapsulation 'ip6gre'
set interfaces tunnel tun101 source-address '2001:db8:babe:face::3afe:3'
set interfaces tunnel tun101 remote '2001:db8:9bb:3ce::5'

Linux systemd-networkd :

La configuration systemd-networkd nécessite deux fichiers de configuration : xxx.netdev pour créer l'interface de tunnel GRE, et xxx.network pour lui attribuer des adresses IP.

# cat /etc/systemd/network/gre-example.netdev
[NetDev]
Name=gre-example
Kind=ip6gre
MTUBytes=14180

[Tunnel]
Remote=2001:db8:babe:face::3afe:3


# cat /etc/systemd/network/gre-example.network
[Match]
Name=gre-example

[Network]
Address=2001:db8:feed:beef::2/126

[Address]
Address=192.168.5.2/30

Clés GRE

Une clé GRE est un champ optionnel de 32 bits dans l'en-tête GRE qui permet à plusieurs tunnels GRE de fonctionner entre les mêmes points de terminaison source et destination. Lorsqu'un paquet arrive, le récepteur vérifie la clé GRE pour déterminer quelle interface de tunnel doit le traiter.

Même si cela semble lié à la sécurité, la clé GRE n'est qu'un identifiant et ne fournit aucune cryptage ou protection des données.

Exemple :

set interfaces tunnel tun0 source-address 192.0.2.10
set interfaces tunnel tun0 remote 192.0.2.20
set interfaces tunnel tun0 address 10.40.50.60/24
set interfaces tunnel tun0 parameters ip key 10

set interfaces tunnel tun1 source-address 192.0.2.10
set interfaces tunnel tun1 remote 192.0.2.20
set interfaces tunnel tun1 address 172.16.17.18/24
set interfaces tunnel tun1 parameters ip key 20

GRETAP

Contrairement au GRE, qui encapsule uniquement le trafic de couche 3 (IP), GRETAP encapsule les trames de couche 2 (Ethernet).

Cela signifie que les interfaces de tunnel GRETAP peuvent être membres d'une interface de pont. Cela permet à deux sites géographiquement distants de se connecter comme s'ils étaient sur le même LAN.

Les tunnels GRETAP peuvent être établis sur des réseaux de transport IPv4 et IPv6.

Exemple :

set interfaces bridge br0 member interface eth0
set interfaces bridge br0 member interface tun0
set interfaces tunnel tun0 encapsulation gretap
set interfaces tunnel tun0 source-address 198.51.100.2
set interfaces tunnel tun0 remote 203.0.113.10

Résolution des problèmes

GRE est un protocole de tunneling standardisé utilisé dans de nombreux environnements réseau.

Bien que la configuration d'un tunnel GRE soit simple, les échecs de connectivité surviennent fréquemment car les ACLs ou les règles de pare-feu bloquent le protocole IP 47 ou empêchent la communication directe entre les points de terminaison du tunnel.

Si votre tunnel GRE échoue à se connecter, effectuez ces étapes de diagnostic :

1. Vérifiez que le pair distant est accessible depuis l'adresse source-address configurée.

Cela garantit que le chemin physique entre les deux extrémités est fonctionnel.

64 bytes from 203.0.113.10: icmp_seq=3 ttl=254 time=0.624 ms
64 bytes from 203.0.113.10: icmp_seq=4 ttl=254 time=1.41 ms

4 packets transmitted, 4 received, 0% packet loss, time 3007ms
