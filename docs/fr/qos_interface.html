Politique de trafic

QoS

Le nom générique de la Qualité de Service ou du Contrôle de Trafic implique des choses comme le contrôle du trafic, l'ordonnancement ou la suppression de paquets, qui sont les types de choses que vous pourriez vouloir expérimenter lorsque vous avez, par exemple, un goulot d'étranglement de bande passante sur un lien et que vous souhaitez prioriser certains types de trafic par rapport à d'autres.

tc est un outil puissant pour le Contrôle de Trafic trouvé dans le noyau Linux. Cependant, sa configuration est souvent considérée comme une tâche fastidieuse. Heureusement, VyOS facilite cette tâche grâce à son CLI, tout en utilisant tc comme backend.

Comment faire fonctionner

Pour que le Contrôle de Trafic de VyOS fonctionne, vous devez suivre 2 étapes :

  1. Créer une politique de trafic.

  2. Appliquer la politique de trafic à une interface entrée ou sortie.

Mais avant d'apprendre à configurer votre politique, nous vous mettons en garde sur les différentes unités que vous pouvez utiliser et aussi vous montrons ce que classes sont et comment elles fonctionnent, car certaines politiques peuvent nécessiter que vous configuriez les classes.

Unités

Lors de la configuration de votre politique de trafic, vous devrez définir des valeurs de débit de données, faites attention aux unités que vous utilisez, il est facile de se confondre avec les différents préfixes et suffixes que vous pouvez utiliser. VyOS affichera toujours les différentes unités que vous pouvez utiliser.

Préfixes

Ils peuvent être des précisions décimales.

kbit  (10^3)    kilobit par seconde
mbit  (10^6)    megabit par seconde
gbit  (10^9)    gigabit par seconde
tbit  (10^12)   terabit par seconde

kbps  (8*10^3)  kilo-octet par seconde
mbps  (8*10^6)  mégaoctet par seconde
gbps  (8*10^9)  gigaoctet par seconde
tbps  (8*10^12) téraoctet par seconde

Ou des préfixes binaires.

kibit (2^10 = 1024)    kibibit par seconde
mibit (2^20 = 1024^2)  mébibit par seconde
gibit (2^30 = 1024^3)  gibibit par seconde
tbit  (2^40 = 1024^4)  tébibit par seconde

kibps (1024*8)         kibioctet (KiB) par seconde
mibps (1024^2*8)       mébioctet (MiB) par seconde
gibps (1024^3*8)       gibioctet (GiB) par seconde
tibps (1024^4*8)       tébioctet (TiB) par seconde

Suffixes

Un bit s'écrit comme bit,

kbit (kilobits par seconde)
mbit (megabits par seconde)
gbit (gigabits par seconde)
tbit (terabits par seconde)

tandis qu'un octet s'écrit comme un seul b.

kbps (kilooctets par seconde)
mbps (mégaoctets par seconde)
gbps (gigaoctets par seconde)

Classes

Dans la section Création d'une politique de trafic, vous verrez que certaines politiques utilisent des classes. Ces politiques vous permettent de distribuer le trafic dans différentes classes selon différents paramètres que vous pouvez choisir. Ainsi, une classe est simplement un type spécifique de trafic que vous sélectionnez.

L'objectif ultime de la classification du trafic est de donner à chaque classe un traitement différent.

Correspondance du trafic

Pour définir quel trafic va dans quelle classe, vous définissez des filtres (c'est-à-dire les critères de correspondance). Les paquets passent à travers ces règles de correspondance (comme les règles d'un pare-feu) et, si un paquet correspond au filtre, il est attribué à cette classe.

Dans VyOS, une classe est identifiée par un nombre que vous pouvez choisir lors de sa configuration.

Note

Le sens de l'ID de classe n'est pas le même pour chaque type de politique. Normalement, les politiques n'ont besoin que d'un nombre sans signification pour identifier une classe (ID de classe), mais cela ne s'applique pas à toutes les politiques. Le nombre d'une classe dans une file d'attente prioritaire ne définit pas seulement son identité, mais aussi sa priorité.

set qos policy <policy> <policy-name> class <class-ID> match <class-matching-rule-name>

Dans la commande ci-dessus, nous définissons le type de politique que nous allons utiliser et le nom que nous choisissons pour celle-ci ; une classe (afin de différencier certains trafics) et un numéro identifiable pour cette classe ; puis nous configurons une règle de correspondance (ou filtre) et un nom pour celle-ci.

Une classe peut avoir plusieurs filtres de correspondance :

set qos policy shaper MY-SHAPER class 30 match HTTP
set qos policy shaper MY-SHAPER class 30 match HTTPs

Un filtre de correspondance peut contenir plusieurs critères et correspondra au trafic si tous ces critères sont vrais.

Par exemple :

set qos policy shaper MY-SHAPER class 30 match HTTP ip protocol tcp
set qos policy shaper MY-SHAPER class 30 match HTTP ip source port 80

Cela correspondra au trafic TCP avec le port source 80.

Il existe de nombreux paramètres que vous pourrez utiliser pour correspondre au trafic que vous souhaitez pour une classe :

  • Ethernet (protocole, adresse de destination ou adresse source)

  • Nom de l'interface

  • IPv4 (valeur DSCP, longueur maximale du paquet, protocole, adresse source, adresse de destination, port source, port de destination ou drapeaux TCP)

  • IPv6 (valeur DSCP, longueur maximale du payload, protocole, adresse source, adresse de destination, port source, port de destination ou drapeaux TCP)

  • Marque du pare-feu

  • ID VLAN

Lors de la configuration de votre filtre, vous pouvez utiliser la touche Tab pour voir les nombreux paramètres différents que vous pouvez configurer.

vyos@vyos# set qos policy shaper MY-SHAPER class 30 match MY-FIRST-FILTER 
Possible completions:
   description  Description
 > ether        En-tête Ethernet
   interface    Interface à utiliser
 > ip           Correspondance de l'en-tête du protocole IP
 > ipv6         Correspondance de l'en-tête du protocole IPv6
   mark         Correspondance sur la marque appliquée par le pare-feu
   vif          Identifiant de réseau local virtuel (VLAN) pour cette correspondance

Comme indiqué dans l'exemple ci-dessus, l'une des possibilités de correspondance des paquets est basée sur les marques effectuées par le pare-feu, ce qui peut vous offrir un grand degré de flexibilité.

Vous pouvez également écrire une description pour un filtre :

set qos policy shaper MY-SHAPER class 30 match MY-FIRST-FILTER description "Ma description de filtre"

Note

Un filtre TCP IPv4 ne correspondra qu'aux paquets avec une longueur d'en-tête IPv4 de 20 octets (ce qui est la majorité des paquets IPv4).

Note

Les filtres TCP IPv6 ne correspondent qu'aux paquets IPv6 sans extension d'en-tête, voir https://en.wikipedia.org/wiki/IPv6_packet#Extension_headers

Groupe de correspondance de trafic

Dans certains cas où nous avons besoin d'une organisation de notre sélection de correspondance, afin d'être plus flexible et d'organiser avec notre définition de filtre. Nous pouvons appliquer des groupes de correspondance de trafic, nous permettant de créer des groupes de filtres distincts dans notre politique et de définir divers paramètres pour chaque groupe :

set qos traffic-match-group <group_name> match <match_name>
Possible completions:
   description          Description
 > ip                   Correspondance de l'en-tête du protocole IP
 > ipv6                 Correspondance de l'en-tête du protocole IPv6
   mark                 Correspondance sur la marque appliquée par le pare-feu
   vif                  Identifiant de réseau local virtuel (VLAN) pour cette correspondance

hériter les correspondances d'un autre groupe

set qos traffic-match-group <group_name> match-group <match_group_name>

Un groupe de correspondance peut contenir plusieurs critères et hériter d'eux dans la même politique.

Par exemple :

set qos traffic-match-group Mission-Critical match AF31 ip dscp 'AF31'
set qos traffic-match-group Mission-Critical match AF32 ip dscp 'AF42'
set qos traffic-match-group Mission-Critical match CS3 ip dscp 'CS3'
set qos traffic-match-group Streaming-Video match AF11 ip dscp 'AF11'
set qos traffic-match-group Streaming-Video match AF41 ip dscp 'AF41'
set qos traffic-match-group Streaming-Video match AF43 ip dscp 'AF43'
set qos policy shaper VyOS-HTB class 10 bandwidth '30%'
set qos policy shaper VyOS-HTB class 10 description 'Multimedia'
set qos policy shaper VyOS-HTB class 10 match CS4 ip dscp 'CS4'
set qos policy shaper VyOS-HTB class 10 match-group 'Streaming-Video'
set qos policy shaper VyOS-HTB class 10 priority '1'
set qos policy shaper VyOS-HTB class 10 queue-type 'fair-queue'
set qos policy shaper VyOS-HTB class 20 description 'MC'
set qos policy shaper VyOS-HTB class 20 match-group 'Mission-Critical'
set qos policy shaper VyOS-HTB class 20 priority '2'
set qos policy shaper VyOS-HTB class 20 queue-type 'fair-queue'
set qos policy shaper VyOS-HTB default bandwidth '20%'
set qos policy shaper VyOS-HTB default queue-type 'fq-codel'

Dans cet exemple, nous pouvons observer que différents critères DSCP sont définis en fonction de notre configuration QoS dans le même groupe de politique.

Défaut

Vous devrez souvent configurer votre défaut de trafic de la même manière que vous le faites avec une classe. Défaut peut être considéré comme une classe car il fonctionne comme tel. Il contient tout le trafic qui n'a pas correspondu à aucune des classes définies, donc c'est comme une classe ouverte, une classe sans filtres de correspondance.

Traitement de la classe

Dès qu'une classe a un filtre configuré, vous devrez également définir ce que vous voulez faire avec le trafic de cette classe, quel traitement spécifique de contrôle du trafic vous souhaitez lui donner. Vous aurez différentes possibilités en fonction de la politique de trafic que vous configurez.

Intégration d'une politique dans une autre

Très souvent, nous devons intégrer une politique dans une autre. Il est possible de le faire sur des politiques avec classes, en attachant une nouvelle politique à une classe. Par exemple, vous pourriez vouloir appliquer différentes politiques aux différentes classes d'une politique Round-Robin que vous avez configurée.

Un exemple courant est le cas de certaines politiques qui, afin d'être efficaces, doivent être appliquées à une interface directement connectée là où se trouve le goulot d'étranglement. Si votre routeur n'est pas directement connecté au goulot d'étranglement, mais à un saut avant, vous pouvez imiter le goulot d'étranglement en intégrant votre politique non-shaping dans une politique de shaping avec classes afin qu'elle prenne effet.

Vous pouvez configurer une politique dans une classe via le paramètre queue-type.

set qos policy shaper FQ-SHAPER bandwidth 4gbit
set qos policy shaper FQ-SHAPER default bandwidth 100%
set qos policy shaper FQ-SHAPER default queue-type fq-codel

Comme indiqué dans la dernière commande de l'exemple ci-dessus, le paramètre queue-type permet ces combinaisons. Vous pourrez l'utiliser dans de nombreuses politiques.

Note

Certaines politiques incluent déjà d'autres politiques intégrées à l'intérieur. C'est le cas du Shaper : chaque classe utilise fair-queue sauf si vous la changez.

Création d'une politique de trafic

VyOS vous permet de contrôler le trafic de nombreuses manières différentes, ici nous couvrirons toutes les possibilités. Vous pouvez configurer autant de politiques que vous le souhaitez, mais vous ne pourrez appliquer qu'une seule politique par interface et direction (entree ou sortie).

Certaines politiques peuvent être combinées, vous pourrez intégrer une différente politique qui sera appliquée à une classe de la politique principale.

Conseil

Si vous cherchez une politique pour votre trafic sortant mais vous ne savez pas laquelle vous avez besoin et vous ne voulez pas passer par toutes les politiques possibles présentées ici, nous pensons que vous êtes très probablement à la recherche d'une Politique de Formage et vous voulez configurer ses files comme FQ-CoDel.

Drop Tail

Discipline de file d'attente : PFIFO (Premier arrivé, premier servi).
Applicable à : Trafic sortant.

C'est la file d'attente la plus simple que vous puissiez appliquer à votre trafic. Le trafic doit passer par une file d'attente finie avant d'être envoyé. Vous devez définir combien de paquets cette file d'attente peut contenir.

Lorsqu'un paquet doit être envoyé, il doit passer par cette file d'attente, donc le paquet sera placé à la fin de celle-ci. Lorsque le paquet a complètement passé par celle-ci, il sera défile et videra sa place dans la file d'attente et sera finalement transmis à la carte réseau pour être envoyé.

Malgré le fait que la politique Drop-Tail ne ralentisse pas les paquets, si beaucoup de paquets doivent être envoyés, ils pourraient être supprimés lors de l'ajout à la fin. Cela peut se produire si la file d'attente n'a pas encore été capable de libérer suffisamment de paquets depuis son début.

C'est la politique qui nécessite les moindres ressources pour le même volume de trafic. Mais très probablement vous n'en avez pas besoin car vous ne pouvez pas en tirer grand chose. Parfois, elle est utilisée juste pour activer la journalisation.

set qos policy drop-tail <policy-name> queue-limit <number-of-packets>

Utilisez cette commande pour configurer une politique Drop-Tail (PFIFO). Choisissez un nom unique pour cette politique et la taille de la file d'attente en définissant le nombre de paquets qu'elle peut contenir (maximum 4294967295).

File d'attente équitable

Discipline de file d'attente : SFQ (File d'attente équitable stochastique).
Applicable à : Trafic sortant.

La File d'attente équitable est un planificateur consommant des ressources qui programme l'envoi des paquets en fonction des flux, c'est-à-dire qu'il équilibre le trafic en le distribuant à travers différentes sous-files d'attente afin de garantir l'équité afin que chaque flux puisse envoyer des données tour à tour, empêchant un seul de noyer les autres.

set qos policy fair-queue <policy-name>

Utilisez cette commande pour créer une politique de File d'attente équitable et lui donner un nom. Elle est basée sur la File d'attente équitable stochastique et peut être appliquée au trafic sortant.

Afin de séparer le trafic, la File d'attente équitable utilise un classifieur basé sur l'adresse source, l'adresse de destination et le port source. L'algorithme place les paquets dans des cases de hachage en fonction de ces trois paramètres. Chaque case devrait représenter un flux unique. Comme plusieurs flux peuvent être hachés vers la même case, l'algorithme de hachage est perturbé à des intervalles configurables afin que l'inégalité ne dure que pendant un court moment. La perturbation peut cependant causer un réordonnancement involontaire des paquets. Une valeur conseillée pourrait être de 10 secondes.

L'une des utilisations de la File d'attente équitable pourrait être la mitigation des attaques de refus de service.

set qos policy fair-queue <policy-name> hash-interval <seconds>

Utilisez cette commande pour définir une politique de File d'attente équitable, basée sur la File d'attente équitable stochastique, et définir le nombre de secondes à partir duquel une nouvelle perturbation d'algorithme de file d'attente aura lieu (maximum 4294967295).

Lors de la défile, chaque case avec des données est interrogée de manière cyclique. Vous pouvez configurer la longueur de la file d'attente.

set qos policy fair-queue <policy-name> queue-limit <limit>

Utilisez cette commande pour définir une politique de File d'attente équitable, basée sur la File d'attente équitable stochastique, et définir le nombre maximum de paquets permis d'attendre dans la file d'attente. Tout autre paquet sera supprimé.

Note

La File d'attente équitable est une politique non-shaping (consommant des ressources), donc elle ne sera utile que si votre interface sortante est vraiment pleine. Si ce n'est pas le cas, VyOS ne possèdera pas la file d'attente et la File d'attente équitable n'aura aucun effet. Si la bande passante est disponible sur le lien physique, vous pouvez intégrer la File d'attente équitable dans une politique de shaping avec classes pour vous assurer qu'elle possède la file d'attente.

FQ-CoDel

Discipline de file d'attente : File d'attente équitable / CoDel.
Applicable à : Trafic sortant.

La politique FQ-CoDel distribue le trafic en 1024 files FIFO et essaie de fournir un bon service entre toutes. Il essaie également de maintenir la longueur de toutes les files courte.

FQ-CoDel lutte contre le bufferbloat et réduit la latence sans avoir besoin de configurations complexes. Il est devenu la nouvelle discipline de file d'attente par défaut pour les interfaces de certaines distributions GNU/Linux.

Il utilise un modèle stochastique pour classer les paquets entrants en différents flux et est utilisé pour fournir une part équitable de la bande passante à tous les flux utilisant la file d'attente. Chaque flux est géré par la discipline de file d'attente CoDel. Le réordonnancement au sein d'un flux est évité car CoDel utilise internement une file d'attente FIFO.

FQ-CoDel est basé sur un planificateur de file d'attente Deficit Round Robin (DRR) modifié avec l'algorithme de gestion active de file d'attente (AQM) CoDel opérant sur chaque file d'attente.

Note

FQ-Codel est une politique non-shaping (consommant des ressources), donc elle ne sera utile que si votre interface sortante est vraiment pleine. Si ce n'est pas le cas, VyOS ne possèdera pas la file d'attente et FQ-Codel n'aura aucun effet. Si la bande passante est disponible sur le lien physique, vous pouvez intégrer FQ-Codel dans une politique de shaping avec classes pour vous assurer qu'elle possède la file d'attente. Si vous n'êtes pas sûr si vous avez besoin d'intégrer votre politique FQ-CoDel dans un Shaper, faites-le.

FQ-CoDel est réglé pour fonctionner correctement avec ses paramètres par défaut à 10Gbit de vitesse. Il pourrait fonctionner correctement aussi à d'autres vitesses sans configurer rien, mais ici nous expliquerons quelques cas où vous pourriez vouloir ajuster ses paramètres.

Lorsque vous l'exécutez à 1Gbit et moins, vous pouvez vouloir réduire la queue-limit à 1000 paquets ou moins. À des vitesses comme 10Mbit, vous pouvez vouloir la fixer à 600 paquets.

Si vous utilisez FQ-CoDel intégré dans Shaper et que vous avez des taux élevés (100Mbit et plus), vous pouvez envisager d'augmenter quantum à 8000 ou plus afin que le planificateur économise le processeur.

À des vitesses faibles (en dessous de 40Mbit), vous pouvez vouloir ajuster quantum à environ 300 octets.

À des vitesses très basses (en dessous de 3Mbit), en plus d'ajuster quantum (300 reste valable), vous pouvez également augmenter target à environ 15ms et augmenter interval à environ 150 ms.

set qos policy fq-codel <policy name> codel-quantum <bytes>

Utilisez cette commande pour configurer une politique fq-codel, définissez son nom et le nombre maximum d'octets (par défaut : 1514) à défile d'une file d'attente à la fois.

set qos policy fq-codel <policy name> flows <number-of-flows>

Utilisez cette commande pour configurer une politique fq-codel, définissez son nom et le nombre de sous-files (par défaut : 1024) dans lesquelles les paquets sont classés.

set qos policy fq-codel <policy name> interval <milliseconds>

Utilisez cette commande pour configurer une politique fq-codel, définissez son nom et la période de temps utilisée par la boucle de contrôle de CoDel pour détecter quand un problème de file d'attente persistante se développe, en s'assurant que le délai minimum mesuré ne devient pas trop obsolète (par défaut : 100ms).

set qos policy fq-codel <policy-name> queue-limit <number-of-packets>

Utilisez cette commande pour configurer une politique fq-codel, définissez son nom, et définir une limite rigoureuse sur la taille réelle de la file d'attente. Lorsque cette limite est atteinte, les nouveaux paquets sont supprimés (par défaut : 10240 paquets).

set qos policy fq-codel <policy-name> target <milliseconds>

Utilisez cette commande pour configurer une politique fq-codel, définissez son nom, et définir le délai minimum acceptable pour la file d'attente persistante. Ce délai minimum est identifié en surveillant le délai minimum de la file d'attente que les paquets subissent (par défaut : 5ms).

Exemple

Un exemple simple d'une politique FQ-CoDel fonctionnant à l'intérieur d'une politique Shaper.

set qos policy shaper FQ-CODEL-SHAPER bandwidth 2gbit
set qos policy shaper FQ-CODEL-SHAPER default bandwidth 100%
set qos policy shaper FQ-CODEL-SHAPER default queue-type fq-codel

Limiter

Discipline de file d'attente : policier d'entrée.
Applicable à : Trafic entrant.

Le limiter est l'une de ces politiques qui utilise des classes (la discipline d'entrée n'est en réalité qu'une politique sans classe mais les filtres fonctionnent dedans).

Le limiter effectue une police d'entrée de base du trafic. Plusieurs classes de trafic peuvent être définies et des limites de trafic peuvent être appliquées à chaque classe. Bien que le policier utilise un mécanisme de jauge à jetons internement, il n'a pas la capacité de retarder un paquet comme un mécanisme de mise en forme. Le trafic excédant les limites de bande passante définies est directement supprimé. Une taille maximale de dépassement peut également être configurée.

Vous pouvez configurer des classes (jusqu'à 4090) avec des paramètres différents et une politique par défaut qui sera appliquée à tout trafic ne correspondant à aucune des classes configurées.

Note

Dans le cas où vous souhaitez appliquer un type de mise en forme à votre trafic entrant, consultez la section sur la mise en forme d'entrée.

set qos policy limiter <policy-name> class <class ID> match <match-name> description <description>

Utilisez cette commande pour configurer un policier d'entrée, en définissant son nom, un identifiant de classe (1-4090), un nom de règle de correspondance de classe et sa description.

Dès que les règles de correspondance sont définies pour une classe, vous pouvez commencer à configurer comment vous souhaitez que le trafic correspondant se comporte.

set qos policy limiter <policy-name> class <class-ID> bandwidth <rate>

Utilisez cette commande pour configurer un policier d'entrée, en définissant son nom, un identifiant de classe (1-4090) et la bande passante maximale autorisée pour cette classe.
